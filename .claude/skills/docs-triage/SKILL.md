# docs-triage — 情報の置き場所判定

設計の正本は [docs/plan/Template/20260807_template-design.md](../../../docs/plan/Template/20260807_template-design.md)（§1 三層構造 / §6 docs 配置 / §7 コンテキスト予算）。ここは判定手順の正本。

## 0. 前提原則: コードで表現できるものは散文に書かない

散文（AGENTS.md・skill・docs）は**コードで表現できないものの最後の手段**。分類質問の前に必ず問う。

- **検査可能な規則**（違反を機械が検出できる）→ oxlint ルール / `tools/architecture`（ts-morph checker）/ `tests/policy/`
- **決定的な実行手順**（コマンド列・入出力が機械的）→ `mise.toml` の task。散文にコマンド列を書き写さず、task を切って散文側は呼び出し 1 行にする

コードにできないもの（判断分岐・文脈依存の選択・トレードオフの記録）だけが散文の対象になり、次の分類質問へ進む。

## 1. 参照タイミングによる大分類

> **この情報を見落としたエージェントは、どのタスクで失敗するか?**

答えに応じて上から排他で分類する（§7「コンテキスト予算」のロード機構表と 1 対 1 対応）。

| 答え                                                         | 種類         | 置き場所                                        | ロード機構                                 |
| ------------------------------------------------------------ | ------------ | ----------------------------------------------- | ------------------------------------------ |
| （散文不要）コードで表現できる                               | コード表現   | linter / checker / CI ゲート / `mise.toml` task | 実行時強制。**散文に書かない**（§0）       |
| すべてのタスク                                               | 普遍規範     | ルート `AGENTS.md`                              | 常時ロード。**最も希少な枠**（§7）         |
| そのディレクトリを触るすべてのタスク                         | 近接規範     | nested `AGENTS.md`                              | ディレクトリ近接                           |
| 特定種類のタスクのみ                                         | 手順知識     | skill（`.claude/skills/`）                      | タスクトリガーで on-demand                 |
| それ以外すべて（要件・レシピ・決定履歴・現行設計・実装計画） | `docs/` 配下 | §2 参照                                         | **blume MCP で on-demand**。潤沢な枠（§7） |

「それ以外すべて」が `docs/` に落ちるのは範囲が広すぎるように見えるが、`docs/` 自体が §6 の構成でさらに排他分類されるため、次節で 1 段掘る。

## 2. `docs/` 配下の三層判定

`docs/` に落ちた情報は、**寿命**で三層に分ける（§1）。三層は同じことを書いてはならない。リンクの向きは 原則層 → レシピ層 → 実体層 の一方通行で、逆向きの要約は禁止する。

| 問い                                                                                     | Yes の行き先                                  | 書く内容                                                                    |
| ---------------------------------------------------------------------------------------- | --------------------------------------------- | --------------------------------------------------------------------------- |
| ツール名を出さずに「何が満たされていれば準拠か」だけで言えるか（寿命: 数年）             | `docs/principles/`                            | 要件 / 機械強制の受け皿 / レビュー観点 の 3 節（この 3 点セットは省略不可） |
| 「今それをどのツールでどう満たしているか」（バージョン込み。寿命: 数ヶ月・差し替え前提） | `docs/recipes/`                               | 原則へのリンク 1 行 + 今の実装。原則の要約をここに書き直さない              |
| 「なぜその決定に至ったか・何を捨てたか」                                                 | `docs/adr/NNNN-kebab-case.md`                 | 決定・理由・捨てた代替案。索引（`docs/adr/README.md`）の更新を同梱          |
| 「今どうなっているか」（「なぜ」ではない）                                               | `docs/design/`                                | 現行設計のスナップショット                                                  |
| 「この実装単位の計画と受入証跡」                                                         | `docs/plan/{Component}/{YYYYMMDD}_{topic}.md` | 計画そのもの。完了後も削除せず証跡として残す                                |

判定に迷ったら「原則層に具体的なツール名を書きたくなっていないか」を自問する。書きたくなった時点でその文はレシピ層の内容であり、原則層からは締め出す。

## 3. skill 化の合格基準（卒業 3 テスト）

ADR・AGENTS.md・docs 内の記述は、次の **3 つすべて**を満たすとき skill へ卒業する。

0. **前提（コード化テスト）**: §0 を先に通す。決定的な手順は skill ではなく `mise.toml` task。skill は**判断を含む手順**（分岐・文脈依存の選択）のみ
1. **トリガーテスト**: 「〜するとき」というタスク形の description が書ける（発動条件がディレクトリではなくタスク種別である）
2. **手順テスト**: 1 行の規範ではなく、複数ステップの手順・判断フローである
3. **現在形テスト**: 「今どうやるか」だけで書ける（経緯・却下案は ADR へのリンク 1 行に落とす）

さらに本テンプレート固有の卒業テストを 1 つ加える。

4. **トリガー一致テスト**: description のタスク形トリガーが、実際にその skill を使ってほしい作業のタイミングと一致しているか。ずれていて「実装時には自発的に適用されない」のような補足を後から散文で書き足したくなったら、補足を書く代わりに description を直す（§7「description のトリガー設計」）

卒業時の処理:

- 元の場所には **skill へのリンク 1 行だけ**残す
- ルート `AGENTS.md`「スキル参照」節に**発動条件つきで必ず登録する**。この節がエージェント横断の発見可能性の正本（特定エージェントの自動発見機構に依存しない。`.agents/skills/` へは `mise run sync:agents` が機械的に複製する）
- 手順の**正本は skill 側**（`.claude/skills/`）。ADR・AGENTS.md・docs に同じ表・手順を複製して残さない（drift の元）

## 4. ルート `AGENTS.md` のセクション運用とコンテキスト予算

ルート `AGENTS.md` が持つ節は「絶対規約」「Stack 索引」「コマンド」「スキル参照」「現在の状態」のみ（§7）。

| セクション | 責務                                 | 更新トリガー                                       | 肥大シグナル → 退避先                                         |
| ---------- | ------------------------------------ | -------------------------------------------------- | ------------------------------------------------------------- |
| 絶対規約   | 機械強制できない普遍規範のみ         | 対応する ADR / 原則が先にあること                  | 個数が増えすぎた → ディレクトリ限定の話は nested AGENTS.md へ |
| Stack 索引 | 索引。1 行要約 + レシピ層リンクのみ  | レシピ追加・差し替え時                             | 説明文が増えた → `docs/recipes/` へ                           |
| コマンド   | 薄い表。正本は `mise.toml`           | task 追加時                                        | 手順の散文化 → skill へ                                       |
| スキル参照 | skill へのポインタ集（発動条件つき） | skill 追加・改名・発動条件の変更時                 | 手順本文が書かれた → skill 側で保守                           |
| 現在の状態 | 進捗のスナップショット               | マイルストーン完了時に**全文上書き**（追記しない） | 追記して肥大している → 削除（履歴は git log と ADR が持つ）   |

**現在の状態を上書き専用にする理由**: 追記すると `AGENTS.md` が第二の決定ログになり、原則5（決定ログと現行規範の二層モデル）が崩れる。

`AGENTS.md` には**行数の上限**があり、超過は `tests/policy/` の policy-as-test が落とす（§7・原則11）。追記する PR は「なぜ on-demand（`docs/`）ではなく常時ロードが必要か」を書く。nested `AGENTS.md` にも同じ原理を適用する（近接規範のみ・手順知識は skill・経緯は ADR）。

## 5. PR チェックリスト

- [ ] 新しい知見・規約・手順を書いた → §0（コードで表現できないか）→ §1（大分類）→ 必要なら §2（`docs/` の三層判定）の順で置き場所を決めたか
- [ ] 決定的なコマンド列を散文に書いていないか（`mise.toml` の task 化して呼び出し 1 行にする）
- [ ] `docs/principles/` に書いた内容にツール名が出ていないか（出ていたらレシピ層へ）
- [ ] `docs/recipes/` が原則の要約を書き直していないか（リンク 1 行 + 今の実装だけか）
- [ ] skill を追加・改名した → ルート `AGENTS.md` スキル参照節へ発動条件つきで登録したか、description のトリガーテスト（§3-4）を通したか
- [ ] ADR を追加・変更した → 対応する `AGENTS.md` / 原則 / レシピの更新を同梱したか（原則11: 参照先が変わったのに正本が触られていない状態を作らない）
- [ ] 手順・表を 2 箇所以上に書いていないか（正本 1 箇所 + リンク）
