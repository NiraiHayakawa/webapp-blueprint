# webapp-blueprint の設計

- 日付: 2026-08-07
- 状態: 承認済み（実装計画は別ファイル）

## 目的

新しい webapp プロジェクトを始めるとき、**clone してドメインを足すだけで、規約が機械強制された状態から書き始められる**テンプレートを作る。

テンプレートが運ぶのは技術選定そのものではなく、**規約をどこに置き・何で強制し・何をレビューに残すかを決める手続き**である。この手続きは言語やクラウドが変わっても生き残る。

本テンプレートは、複数の本番 Web アプリケーション開発から得られた設計パターン・運用知見・ガードレールを集約し、原則（Principles）とレシピ（Recipes）として再構成したものである。

各所で独立に到達した「規約はプロンプトではなく機械で縛る」という共通方針を基盤とし、**普遍的な設計規律を原則層、スタックやツール固有の工夫をレシピ層**として整理している。

例えば「公開 7 日未満の新規バージョンは自動採用しない」という依存 cooldown 規律のように、エコシステムやツールが異なっても同一の結論に至ったプラクティスを原則層へ昇格させている。

## 非対象

- 実用に足るアプリケーション（ドメインは各プロジェクトが足す。同梱するのはゲートが噛むことを実証する最小の縦切りだけで、これは削除して始めてよい。§9）
- 契約層の具体実装（レシピを 2 つ持ち、プロジェクト開始時に ADR で選ぶ）
- UI コンポーネントライブラリの選定（規律だけ持ち、システムは選ばない）
- デプロイパイプラインの実体（Terraform の骨格と方針のみ）
- 外部のエージェント記憶製品（mem0 / Zep / Letta 等）。理由は §7「記憶レイヤー」に記す

## 1. 三層構造

テンプレートの中身を**寿命の違い**で三層に分ける。

| 層       | 場所                         | 内容                                                       | 寿命                 |
| -------- | ---------------------------- | ---------------------------------------------------------- | -------------------- |
| 原則層   | `docs/principles/`           | ツール名を書かない。「何が満たされていれば準拠か」だけ     | 数年                 |
| レシピ層 | `docs/recipes/`              | 「今それをどのツールでどう満たしているか」。バージョン込み | 数ヶ月・差し替え前提 |
| 実体層   | repo root の設定・スクリプト | レシピ層の現在の具現化                                     | レシピと同時に動く   |

**三層が同じことを書かないことが本テンプレートの最重要制約**である。ADR 0022（docs-triage）の「コードで表現できるものは散文に書かない」をテンプレート自身に再帰適用する:

- 原則層に `oxlint` と書いた瞬間にテンプレートが腐り始める。原則層は「未使用 export と未使用依存が CI で遮断されていること」までしか書かない
- レシピ層は原則を要約し直さない。原則へのリンク 1 行 + 「今の実装」だけを書く
- 実体層は設定ファイルそのもの。散文でコマンド列を書き写さず、task を切って散文側は呼び出し 1 行にする

リンクの向きは原則層 → レシピ層 → 実体層の一方通行とする。逆向きの要約を禁止する。

## 2. 原則層（`docs/principles/`）

1 原則 = 1 ファイル。各ファイルは必ず次の 3 点セットで構成する。

| 節               | 内容                                                                                                          |
| ---------------- | ------------------------------------------------------------------------------------------------------------- |
| 要件             | 何が満たされていれば準拠か。ツール名を書かない                                                                |
| 機械強制の受け皿 | どの種類の仕組み（型 / linter / アーキテクチャテスト / CI ゲート / task）が担うか。具体名はレシピ層へのリンク |
| レビュー観点     | 機械化できずに残る判断。質問形で書く                                                                          |

「レビュー観点」節を必須にすることで、「全部機械で守れる」という嘘と「散文の山」の両方を防ぐ。

### 原則 12（観測性）の要件詳細

**message は散文ではなくフィールドからの描画である。**

```
"GET /tasks → 200 (123ms)"  ←  { route, status, durationMs } から組み立てる
```

人が読む 1 行と機械が読むフィールドが**同じ値から作られる**ので、片方だけを書き換えられない。「メッセージ文字列を監視条件にしない」という規約を、規約ではなく**構造**にしたもの。描画関数を 1 つに絞り、それ以外で message を作れないことを architecture checker が強制する。

**失敗理由は閉じた語彙のコードであり、かつ合成可能**にする。単一の `reason` に潰さない理由は Envoy の response flags と同じで、「upstream が落ちていて、かつリトライ上限にも達した」のように**複数の理由が同時に成り立つのが現実**だから。

**機密の分離は型で行う。** client に返す `details` と server にだけ残す `logDetails` を別の型にすることで、レビューやマスキングに頼らずに分離する。マスキングして通すのは silent な加工であり原則 2 に反するので、混入したら**隠さず落とす**。

**メトリクスとアラートは対象外**とする。レベル戦略はログの出力規約までに留まることが多く、それがオンコール条件にどう繋がるかはプロジェクト固有の監視基盤側に依存する。一般化された解がない問題を、原則に書いて守れるふりをしない。

**空スロットにするのは exporter（送り先）だけである（2026-08-09 改訂）。** 当初は「送り先は契約層と同じく空スロットにする」としていたが、これは誤りだった。OpenTelemetry はベンダー中立が設計目的であり、**API(`@opentelemetry/api`) と SDK(`@opentelemetry/sdk-node` 等) が分離**されている。API/SDK を常時ロードしてもクラウド選定を強制しない——空スロットにすべきは、実際の送り先(Cloud Trace / OTLP / Datadog 等)を選ぶ **exporter だけ**だった。今すぐ配線するのは「ログの形の規約」「OpenTelemetry API/SDK + 既定 exporter(`ConsoleSpanExporter`)」「機械強制」の 3 つになる。選択肢・実体層への配線の詳細は `docs/recipes/tools/observability.md` にある。

### 原則 11（知見の還流）の要件詳細

原則 5（二層モデル）は「どこに書くか」を決めるが、**書く行為そのものには機械強制が無い**。規範ファイルは起動時に注入されるだけで、作業中に得た知見がそこへ書き戻される保証がない。結果として正本は静かに古くなる。

| 項目         | 内容                                                                                                                                                                                                                       |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 要件         | ① 作業で得た知見が machine-local な記憶に留まらず、repo の正本へ昇格する経路が存在する ② 昇格していない記憶は「候補」であって正本ではない（第二の正本を作らない） ③ 正本の記述が実体から乖離していないことが機械検査される |
| 機械強制     | 正本が言及する対象（パス・コマンド・バージョン）の実在性検査 / **同一 PR 内で参照先が変わったのに正本が触られていなければ落とす** / 昇格の契機を skill として持つ                                                          |
| レビュー観点 | この作業で得た知見のうち、次に同じ作業をするエージェントが知らないと失敗するものは何か                                                                                                                                     |

②が要点である。自動抽出された記憶をそのまま正本にすると、レビューを通っていない記述が規範の顔をして増殖し、二層モデルが崩れる。**記憶は候補、正本は昇格したものだけ**という非対称を保つ。

業界の立場は割れている（2026-08-07 時点の各社公式ドキュメントで確認）。Cursor / Windsurf / Claude Code は自動記憶を個人・ローカルに閉じ、チームの正本は明示的に書くファイルに限る。GitHub Copilot Memory と Devin Knowledge は逆に、自動生成された記憶を既定でリポジトリ / 組織共有にする。Zed は記憶機能をコアに持たず外部に委ねる。**本テンプレートは前者を採る** — 正本の記述はレビューを経たものだけ、という原則 5 との一貫性を優先する。

なお Anthropic の公式ドキュメントは、規範ファイルの位置づけについて次を明言している。

> Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead.

**規範ファイルは強制ではなく文脈である。確実に止めたいなら別レイヤー（hook / linter / テスト）を使う。** これは原則 4 が言っていることと同じであり、規範を書けば守られるという期待を持たないための一次情報として引く。

### 原則 4（機械強制）の要件詳細 — policy-as-test

「規約を機械で縛る」を規約そのものにも適用する。**lint ルールではなくテストとして書く**ことで、違反が「警告」ではなく「落ちる」形になる。

| 対象             | 検証内容                                                                                                 |
| ---------------- | -------------------------------------------------------------------------------------------------------- |
| CI の構造        | ゲートジョブが存在し、他の全ジョブがそれに依存していること。ジョブが増えたときにゲートを迂回できないこと |
| CI matrix の同期 | `ci.yml` の matrix タスク一覧と `mise.toml` の `[tasks.check].depends` が集合として完全一致していること  |
| 依存の pin       | すべての依存が完全 pin であること。コンテナイメージがタグまたは digest で固定されていること              |
| 規範ファイル     | `AGENTS.md` と workflow の文言が一致していること。プロンプト・ポリシー文言の drift 検出                  |
| 生成物           | 正本から再生成した結果が、コミットされている内容とバイト単位で一致すること                               |

背景: CI のジョブ依存グラフや全依存の pin をテストとして固定する発想と、規範ファイル（`AGENTS.md`）と workflow 文言の整合性を突き合わせる発想は、いずれも「規約のメタレベルをテストで落とす」という同一の考え方の別適用であり、テンプレートでは 1 つの原則にまとめる。

### 原則 4（機械強制）の要件詳細 — 抑制には理由を書く

lint ルールの無効化・checker の除外・baseline への追加は、**必ず理由を添える**。「うるさいから」での抑制を禁止する。

抑制の形は、影響範囲の狭い順に選ぶ。行単位の抑制 → ファイル単位の除外 → ルールごと off、の順で、右に行くほど強い理由を要求する。ルールごと off にするのは「そのルールが本プロジェクトの設計と構造的に噛み合わない」と説明できるときだけ。

背景: linter の disable リスト、未使用検出の除外、Dockerfile lint など、複数領域で「inline suppression に理由を必須にする」という同一の規律が必要になる。個別のツール設定に閉じず横断的に適用するため原則層に置く。

機械強制できる場合はする（理由の無い抑制を検出して落とす）。できない場合はレビュー観点に残す。**抑制が増えること自体は悪ではない。理由の書かれていない抑制が悪い** — 前者は設計の記録になり、後者はゲートの空洞化になる。

### 原則 9（Secrets）の要件詳細

| 項目         | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 要件         | ① repo に入るのは `op://vault/item/field` 形式の参照のみ ② ローカルは `op run` / `op inject` で注入し `.env` の実ファイルを作らない ③ CI は 1Password Service Account トークン 1 本だけを GitHub Secrets に置き、そこから展開する ④ クラウドランタイムの資格情報は鍵レス（Workload Identity Federation / Application Default Credentials / attached service account）で、長期鍵を発行しない ⑤ 秘密の追加は vault item の作成が先、repo 変更が後 |
| 機械強制     | secret スキャナを pre-push と CI に置く / `.env*` を ignore（`.env.example` は参照文字列のみ許可）/ CI workflow の `env:` に平文が直書きされていないことを検査                                                                                                                                                                                                                                                                                  |
| レビュー観点 | ローテーションが repo の変更を伴う設計になっていないか（なっていたら参照化できていないサイン）                                                                                                                                                                                                                                                                                                                                                  |

暗号化した `.env` をコミットする方式（dotenvx 等）は採らない。復号鍵の配布問題を repo の外に残したまま、repo の中に暗号文という余分な状態を増やすため。

### 原則 10（依存 pin）の要件詳細

| 項目         | 内容                                                                                                                                                                                                                                                                            |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 要件         | ① アプリ依存・開発依存・ビルドツール・コンテナイメージのすべてが完全 pin されている（レンジ指定と `latest` を許さない） ② 公開から一定期間（既定 7 日）未満のバージョンは自動採用しない ③ セキュリティ更新はこの待機を迂回してよい ④ 更新は自動 PR で提案され、人間がマージする |
| 機械強制     | pin 方針を policy-as-test で検証 / lockfile の整合を CI ゲートの最初に置き、他の全ジョブをそれに依存させる / 依存更新 bot の設定                                                                                                                                                |
| レビュー観点 | 待機期間を外す判断をしたとき、その理由が PR に書かれているか                                                                                                                                                                                                                    |

待機期間は、公開直後に取り下げられる版や supply chain 攻撃の初動を避けるためのもの。エコシステムを問わず一般的に 7 日間の cooldown が有効に機能するため、既定値を 7 日にする。

## 3. 構造

### monorepo（前提）

テンプレートは pnpm workspace の monorepo である。単一パッケージ構成は選択肢に置かない。

```
apps/
  web/            フロントエンド（再帰的 features）
  api/            バックエンド（DDD + Clean Architecture）
packages/         共有パッケージ（exports は "." のみ）
contract/         契約層のスロット（空。ADR 0001 で中身が決まる）
e2e/              playwright-bdd の .feature と step 定義
tools/
  architecture/   ts-morph architecture checker
  ramune/          検証付きタスクグラフ実行機構（既定で組み込み。§7「ramune を既定で組み込む理由」）
    graph/          DAG モデル・不変条件検査・差分操作の適用
    mcp-server/     ramune_read_graph 等の MCP ツール実装
    hooks/          Planner/Worker の権限を機械強制する PreToolUse hook
    viewer/         .ramune/graph.json を読み取り専用で表示するビューア
tests/policy/     policy-as-test
scripts/          agent 資産同期
docs/
infra/
```

`tools/ramune/` は `tools/architecture/` と同じ階層に置く。`apps/`（削除して始めてよい最小の縦切り）ではなく `tools/`（ハーネス。§9 の「最小の縦切り」とは性質が違い、削除されては困る）に置く理由は §7「ramune を既定で組み込む理由」参照。

monorepo の配当は「契約と実装の原子的変更」と「単一のタスク語彙」であり、それを毀損する方向を規約で塞ぐ:

- **one-version rule**: 共有依存は workspace の catalog でルートに一元宣言し、パッケージ間のバージョン分裂を構造的に禁止する
- **契約横断の変更は 1 PR で原子的に行う**。契約だけを先行させる PR を作らない（main が「契約はあるが実装がない」中間状態を持たない）
- **deep import 禁止**（後述の「workspace パッケージの公開面」）
- タスクグラフの正本は mise 一本に寄せる（`mise run check` の形を変えない）。パッケージ単位の入力追跡キャッシュだけを Turborepo に持たせ、mise の下位レイヤに留める（Nx は入れない。§5「Turborepo を採用する理由」）

### フロントエンド: 再帰的 features

```
src/
  routes/       ルーティング。薄く、feature を並べるだけ
  features/     API / 状態の境界。公開面は index のみ
  components/   共有 props-only UI
  lib/<名詞>/   横断的な実装（transport 生成・query client・env 検証 など）
```

- 子 feature は親の `features/` 配下に置く。ネストしても境界規則は変わらない
- feature / component の判定は「テストに API モックが要るか」。要るなら feature
- 迷ったら component から始め、API 依存が生えた時点で feature に昇格する
- `lib/` 直下へのファイル直置きを禁止する。必ず責務名詞のディレクトリを切る

### バックエンド: DDD + Clean Architecture

```
domain/          aggregate / entity / value object / domain event / repository interface
application/     use case + port（interface 集約）
infrastructure/  driven adapter（port の実装）
presentation/    driving adapter（HTTP / RPC ハンドラ）
```

- 依存方向は一方通行。`domain/` は外部パッケージを import しない
- repository は aggregate root にのみ生やす
- DI はコンストラクタ手組み。DI コンテナを使わない
- **サードパーティ SDK / SaaS クライアントの import は合成ルート 1 ファイルに閉じる。** 実行パスによっては当該パッケージに一切触れない状態を作れるようにする（例: SaaS SDK を合成ルートの関数内 import 等に隔離し、ローカル実行では SDK を読み込まない形にする）
- hexagonal はレシピ層に変種として置く（driving 側の input port を立てるかどうかの差分として記述する）

### workspace パッケージの公開面

パッケージ間参照は workspace 依存経由のみとし、`exports` で公開面を宣言して deep import を構造的に不能にする。**`"./*"` のようなワイルドカードを書かない**（書くと内部の任意ファイルが外から参照可能になり、宣言が形骸化する）。全パッケージで `"./*": "./src/*"` のようなワイルドカード宣言を許すと公開面の絞り込みが効かなくなるため、原則 7 に従い明示的なエントリポイントのみを export する。

**DDD 戦術パターンを既定にする理由**: LLM コーディングエージェントの普及により、aggregate / value object / domain event を書く式典コストが大きく下がった。少人数・短期開発において式典過剰と見なされがちだったパターンも、LLM の支援を前提とすると実装・保守の負荷が大幅に軽減される。原則層にはこの経緯を**「却下理由が前提の変化で覆るケース」**として位置づけ、ADR の決定が永続でないことの具体例にする。

## 4. テスト戦略

原則 6（公開契約と外部から観測可能な振る舞いのみ）の具体形。**Behavior Driven を既定とし、振る舞いは Gherkin（`.feature`）で書く。**

### 何を Gherkin で書き、何を書かないか

判定基準を 1 つに固定する: **外部境界のフィクスチャ（API モック・emulator・ブラウザ）が要るなら `.feature` を持たせる。要らないなら素の Vitest テストにする。**

（table-driven はこの判定の反対側ではない。テーブルはどちらの側でも使う — 後述）

これはフロントの feature / component 判定（「テストに API モックが要るなら feature」）と同じ基準である。テンプレート内で覚えるべき判定基準を増やさないために、意図的に同じ形にしている。

| 層                               | 形                                                           | 道具                    |
| -------------------------------- | ------------------------------------------------------------ | ----------------------- |
| domain（純粋なルール・状態遷移） | table-driven（object table + `$field` 補間）+ property-based | Vitest                  |
| use case / 契約（振る舞い）      | `.feature` を spec と colocate                               | Vitest + Gherkin レイヤ |
| E2E                              | `.feature` を Playwright テストに変換して実行                | playwright-bdd          |

どの層でもパラメータ化はテーブルで書く。**違うのはテーブルを Gherkin の文法で書くか、テストランナーの API で書くか**だけである（次節）。

domain が Gherkin の外に残る理由は**構造的なもの**である。property-based testing の性質（「任意のイベント列で不正遷移しない」等）は入力空間が有界でないため、`Examples` の行として書き下せない。好みではなく書けない。

これとは別に「`Examples` が長大化すると `.feature` が仕様書ではなく網羅表になる」という劣化があるが、こちらは規則ではなく**レビュー観点**に置く（`Examples` が 30 行を超えたら、それは仕様の記述か網羅表か、と問う）。

### Gherkin と table-driven は対立しない

テーブル機構は 3 つあり、`Scenario Outline` + `Examples` は**Gherkin の文法で書いた table-driven そのもの**である。選択基準は「Gherkin か table か」ではなく、**行ごとに独立した pass / fail が要るか**。

| 機構                            | 実行単位              | 使うとき                                                                |
| ------------------------------- | --------------------- | ----------------------------------------------------------------------- |
| `Scenario Outline` + `Examples` | **1 行 = 1 テスト**   | 振る舞いのパラメータ化。**これが既定**                                  |
| step 引数の Data Table          | 1 シナリオ = 1 テスト | 前提データ・期待集合を 1 シナリオ内でまとめて扱う。行単位の結果は出ない |
| 素の `test.each`                | 1 行 = 1 テスト       | `.feature` を持たない層                                                 |

Data Table を選ぶと、1 行だけ失敗してもレポート上は Scenario 全体が 1 件の失敗になる。**行単位で結果を分けたいなら `Scenario Outline` を使う**。

「Data Table を受け取った step の中で `test.each` を回して行ごとにテストを作る」形は**取れない**。Vitest は収集フェーズと実行フェーズを分離しており、実行中の test の内部から test を定義するとエラーになる（`describe` のネストも v4.0.16 で拒否されるようになった）。行単位の結果が要るなら `Scenario Outline` 一択である。

### ツール（2026-08-07 に一次情報で確認）

| 用途      | 採用                       | 版                                              | 根拠                                                                                                                                                           |
| --------- | -------------------------- | ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| E2E       | `playwright-bdd`           | 9.2.0（2026-06-18 公開 / 直近 push 2026-08-06） | 未定義 step は `bddgen` が失敗してスニペットを出力し、未使用 step は `bddgen export --unused-steps` で列挙できる。drift を CI で落とせる唯一の Playwright 統合 |
| Vitest 層 | `@amiceli/vitest-cucumber` | 7.0.0（2026-06-24 公開）                        | プラグインではなく `describe` / `test` を包む薄い層で、Vitest の実行系を壊さない                                                                               |

**退避先**: `@cucumber/cucumber`（13.2.1、2026-08-04 公開。4 者の中で最も活発）。`--dry-run` + usage formatter で未定義・未使用の双方を検出できるが、Playwright との結合は自前になる。

**採らないもの**: `quickpickle` — Playwright 統合パッケージを作者自身が "NOT STABLE / not achieved a full release" と明言しており、dry run も非対応と README に記載されている。

両ツールとも `Scenario Outline` / `Examples` / Data Table / Doc String / `Background` / `Rule` をサポートしている（2026-08-07 に公式ドキュメントで確認）。**`.feature` の書き方はツール間で揃う。**

引き受けるトレードオフ: Gherkin レイヤが E2E と Vitest で 2 本になり、step 定義レジストリが分かれる。共通言語は `.feature` の文法だけで、step 定義は共有されない。1 本に寄せるには E2E を `@cucumber/cucumber` + 自前の Playwright 結合にするしかなく、そちらの方が高くつくと判断した。

step 定義が共有できない具体的な内実は、引数の受け取り方が違うこと:

|                   | `@amiceli/vitest-cucumber`                                                                      | `playwright-bdd`                                         |
| ----------------- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| Data Table        | 行オブジェクトの配列が step 引数の末尾に素で渡る。自前でキャストする                            | `DataTable` クラスが渡り、`.hashes()` 等のアクセサを持つ |
| `Examples` の変数 | **常に文字列**（`1` や `true` と書いても string）。型が要るなら `mappedExamples` 設定で変換する | コード生成時に各行が独立した test に展開される           |

### 落とし穴（レシピ層に記録する）

- `@amiceli/vitest-cucumber` の `Rule` は**インデントを見ない**。`Rule:` ブロックの後にインデントなしで書いた `Scenario` が、意図せず直前の `Rule` に取り込まれる
- `@amiceli/vitest-cucumber` の `Examples` 変数は常に文字列。数値比較や真偽判定をする step では明示的な変換が要る
- `playwright-bdd` は生成テストのタイトルが `Examples` の行の増減でずれる。タイトル固定手段（Scenario 名への `<column>` 埋め込み、`examplesTitleFormat` 等）を最初から使う
- step 引数の順序は「step expression の引数 → Data Table → Doc String」。両方使う step では末尾 2 つの順序を間違えやすい

### 機械強制

`@amiceli/vitest-cucumber` には未使用 step の検出が無い。本テンプレートではこれを **architecture checker と negative fixture** で埋める。

| ルール                                                            | 受け皿                                                                                  |
| ----------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `.feature` と spec の対応（片方だけ存在する状態を禁止）           | architecture checker                                                                    |
| step 定義から import できるのは公開エントリポイントのみ           | architecture checker。**「公開契約のみテストする」を Gherkin 層で機械強制するのがここ** |
| tuple 形式の `test.each` 禁止 / object table は `$field` 補間必須 | architecture checker                                                                    |
| 未定義 step（E2E）                                                | `bddgen` の失敗                                                                         |
| 未使用 step（E2E）                                                | `bddgen export --unused-steps` を CI に配線                                             |
| 意図的にミスマッチさせた `.feature` / spec が構造的に落ちること   | policy-as-test                                                                          |

最後の 1 行が要で、**drift 検出の仕組み自体が空振りしていないことを確認するテスト**にあたる。受入条件 11 と同じ考え方を Gherkin 層に適用したもの。

### 外部境界の扱い

契約層の選択（ADR 0001）によって、外部境界の偽装方法が変わる。原則層には「外部境界は注入された境界の後ろに置く」までしか書かず、以下はレシピ層で分岐させる。

| 契約層                | 外部境界                                                                                                                |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| protobuf + ConnectRPC | 公式のインメモリ transport。**モックライブラリを入れない**（契約から型が生成されるためモック drift が構造的に起きない） |
| TypeSpec → OpenAPI    | HTTP モック（MSW 等）または pin した統合フィクスチャ                                                                    |

### 既存リポジトリへ後付けする場合

**convert-on-touch** を採る。既存の違反は baseline として残し、触ったファイルだけを変換する。一括変換は差分が巨大になりレビュー不能になるため行わない。

## 5. 実体層

### タスクとゲート

- `mise.toml` を唯一のタスク正本とする。`mise run check` が全ゲートの入口
- CI は matrix に mise task 名をそのまま列挙し、集約ジョブ 1 個を branch protection の required check にする。検査ロジックを CI 側に書かない
- `Taskfile.pkl`（pkfire）は git hook の配線だけに使う。pre-commit で空白エラー検査、pre-push で secret スキャン。実処理は mise task を呼ぶ

#### `check` の外に置くタスク

すべてのタスクが `mise run check` から呼ばれるわけではない。外す理由は一様ではないため、混同を避けるために一覧で示す。

### 観測性（トレース）を追加する理由 — 空スロットの範囲を引き直した

原則12を入れた当初、「トレースの送り先は契約層と同型の空スロットにする」と書き、OpenTelemetry の実体をまるごと保留していた。これは誤りだった。

**OpenTelemetry はベンダー中立が設計目的**であり、API(`@opentelemetry/api`) と SDK(`@opentelemetry/sdk-node` 等) が分離されている。ライブラリ作者は API だけに依存でき、SDK の選択・設定は合成ルートに閉じる——この構造は、本テンプレートの「契約は厳密に、実装は差し替え可能に」とそのまま噛み合う。API/SDK を常時ロードしても特定のクラウドを強制することにはならない。**空スロットにすべきなのは OTel 全体ではなく exporter（実際の送り先）だけ**だった。

線引きをやり直した結果:

| 層                                                                                                    | 扱い                                                                                                         |
| ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `@opentelemetry/api`                                                                                  | 常時ロード。ただし業務コードから直接使わせず、trace 相関目的で観測境界（`logging/`）からのみ使わせる（下記） |
| `@opentelemetry/sdk-node` + 既定 exporter（`@opentelemetry/sdk-trace-base` の `ConsoleSpanExporter`） | 常時ロード。ただし合成ルート 1 ファイルのみで import する                                                    |
| 実際の送り先（Cloud Trace / OTLP / Datadog 等）                                                       | 空スロットのまま                                                                                             |

**トレースは新しい並行系統として足さない。** 原則12が既に持っていた canonical observer（`observeResult`）と同じ境界で span を開閉し、canonical log line に `trace_id` / `span_id` を載せて相関させる。span 属性にも記録と同じ禁止キー検査を効かせる。既存の 14 個の architecture checker ルールのうち 2 つ（`third-party-sdk-composition-root` と `logging-implementation-location`）に実際のパッケージ名を設定として渡すだけで機械強制でき、新しいルールファイルは追加していない（原則8「検査ロジックの二重管理を禁止」）。詳細は [`docs/recipes/tools/observability.md`](../../recipes/tools/observability.md)「6. 実体層の配線」を参照。

### lint 設定は preset を extends する（言語ごとに作法が違う）

**「全ルールを有効にしてから引き算する」opt-out 方式は Go / golangci-lint の作法であり、TypeScript / oxlint には持ち込まない。**

Go 等の言語では `default: all` + 明示的 opt-out が成立するケースがある一方、TypeScript では **ultracite の preset を extends** する構成が適している。lint 設定は最小構成にし、厳格さは型情報付き診断と自作 checker で担う。**TS で全カテゴリ有効化は行わない。**

golangci-lint の `all` は curated set だが、oxlint のカテゴリを全部 error にすると、**同時に満たす書き方が存在しないルールのペア**が多数生じる（実測で 9 組確認: ガード節の `continue` とネスト深さ、`no-void` と floating promise の公式推奨修正、`require-await` と `promise-function-async`、vitest globals の import 要否など）。**規約として成立していない規約を掲げると、規約全体の信頼が落ちる。**

採る方針:

1. preset を extends する
2. **preset が off にしているもののうち、本テンプレートが必要とするルールだけを明示的に再有効化する**（和集合）。原則 7 の受け皿である複雑度・肥大系（`max-statements` / `max-lines` / `max-lines-per-function` / `max-depth` / `max-params` / `max-classes-per-file`）は必ず残す
3. 残る false positive は理由を添えて個別に無効化する

preset のバージョンは lint 本体のバージョンと対で pin する。preset 側が新しすぎると、lint 本体が知らないルール名を参照してパース時に loud fail する。**この失敗は静かでないので、対で pin してさえいれば CI が不整合を機械的に検出する。**

**採らないもの**:

- vp (VITE+) — pre-1.0 であり、安定性のリスクがあるためテンプレートの既定にはしない

### codopsy を追加する理由 — 原則7の受け皿にある2つの穴

原則7（拡張はファイル追加で表現される。既存ファイルの行数純増は分割サイン）の受け皿として、上記で oxlint の複雑度・肥大系ルール（`max-statements` / `max-lines` / `max-lines-per-function` / `max-depth` / `max-params` / `max-classes-per-file`）を明示的に再有効化した。しかしこれには2つの穴がある。

1. **TypeScript 専用**。契約層で Go や Python を選んだ瞬間、同じ原則の受け皿が消える
2. **行数と文の数しか見ない**。**認知的複雑度**（ネストの深さで重み付けした読みにくさ）を測れない

codopsy（tree-sitter で 35 言語を解析する AST レベルの静的コード品質アナライザ）はこの両方を埋める。言語横断・複雑度ベースで原則7を機械強制できる。本テンプレートにおいて新たに導入する。

**oxlint の複雑度ルールとの関係**: oxlint（ultracite preset）は循環的複雑度のみを見る ESLint 互換ルール `complexity` を既定で有効にしている（実測: 閾値は preset 側の override が無く ESLint 既定値の 20）。codopsy の `max-complexity`（既定閾値 10）と役割が重複するが、**閾値が異なり判定基準（cyclomatic のみ vs cyclomatic + cognitive + structure）も異なる**ため、どちらか一方を off にはせず両方を残す（原則8「検査ロジックの二重管理を禁止」には当たらないと判断した。同じロジックを同じ設定で二重に検査する場合のみ原則8の対象になる）。バージョン選定・除外設定の詳細・Go/Python を選んだ場合の再検討事項は [`docs/recipes/tools/quality-gates.md`](../../recipes/tools/quality-gates.md) に記録する。

### CodeQL / Trivy を追加する理由 — 「秘密の混入」の外側にある2つの穴

テンプレートが元々持っていたセキュリティ関連のゲートは secretlint（**秘密の混入**の検出）と、原則10「依存 pin」の**完全 pin + 7日 cooldown**（**新しすぎる依存を避ける**仕組み）の2つだけだった。この2つは互いに守備範囲が重ならず、かつ次の2つの穴を塞がない。

1. **コード自体の脆弱性を見ていない**。secretlint は秘密の実値しか見ず、SQL インジェクション・パストラバーサル・安全でない deserialization のような**コードの欠陥**は誰も検出していない
2. **pin した依存が後から脆弱と判明しても気づけない**。原則10の pin + cooldown は「新しすぎるものを入れない」ための仕組みであり、「入れたものが後から脆弱と判明する」ことには**無力**。むしろ完全 pin しているぶん、対策を挟まなければ古い脆弱なバージョンに固定され続ける

**CodeQL** が①を、**Trivy** が②を埋める。secretlint・CodeQL・Trivy の3者は「秘密の混入」「コードの欠陥」「依存の既知脆弱性」という互いに独立な軸を担当し、守備範囲が重ならない。

**CodeQL**: `security-extended` クエリセットで TypeScript / JavaScript を解析する。本テンプレートではコードの脆弱性・SAST 検査としてローカルタスク `mise run check:codeql`（CodeQL CLI を使用）に統合している（[`docs/recipes/tools/ci.md`](../../recipes/tools/ci.md)「4. 脆弱性 / SAST」参照）。データベース作成と AST 解析が重いため、高速な日常検証（`mise run check`）の対象外とし、独立タスクとして手動または必要に応じて実行する。公開 GitHub リポジトリ等で GitHub ホストの Code Scanning ワークフローを利用したい場合は、標準ワークフローを有効化する選択肢もある。

**Trivy**: `trivy fs`(filesystem スキャン)で依存(SCA。`pnpm-lock.yaml`)と Terraform 設定ミス(`infra/`)を検査する。コンテナイメージはビルドしないため対象外にし、秘密スキャンは secretlint と重複するため明示的に無効化する(既定は `[vuln, secret]`)。本テンプレートで新たに採用する([`docs/recipes/tools/ci.md`](../../recipes/tools/ci.md)「4. 脆弱性 / SAST」)。脆弱性 DB のダウンロードにネットワークが要るため `mise run check` の依存には含めず、CI 専用ジョブ(`ci.yml` の `check-vulnerabilities`)から呼ぶ。バージョン・閾値・抑制の詳細は `trivy.yaml` / `.trivyignore` / `mise.toml` の `[tasks."check:vulnerabilities"]` を参照。

### Turborepo を採用する理由

本テンプレートは Turborepo を採用する。タスクキャッシュの選定理由と境界を以下に整理する。

**前提の整理**: 本テンプレートは vp を採用していない（本節「採らないもの」の vp の行を参照）。

**実測（2026-08-08）**:

- パッケージ間の実行順序は `pnpm -r` が依存グラフ順で解決しており、**この部分はカバー済み**（Turborepo を入れる理由にならない）
- **`mise.toml` には `sources` / `outputs` の宣言が 1 つも無く、入力追跡キャッシュは存在しない**。同じソースに対して `mise run check` を繰り返しても、`typecheck` / `test` は毎回フルスキャンし直す

後者の欠落だけが Turborepo（または同種のツール）を入れる実質的な理由である。

**Nx ではなく Turborepo を選ぶ理由**: Nx が持つ generator / plugin エコシステムは本テンプレートの責務（mise が唯一のタスク正本であること）と重なりが大きく、Turborepo の方が「キャッシュ付きタスクランナー」という薄い機能に留まるため。Nx を導入すると `nx run-many -t typecheck,lint --all` のようにタスク実行そのものが Nx に一本化され、`mise.toml` が Nx コマンドを叩くだけの薄いラッパーになってしまうリスクがある —— 本テンプレートが守る「mise が唯一の入口であり続ける」設計（本節「境界」）とは逆方向に、Nx が事実上の正本になってしまう。実際に必要な機能もキャッシュがほぼ全てで、generator/sync 機能は本テンプレートが tsconfig の手動 `references` + CI drift 検査で代替できる範囲に収まる。詳細は [`docs/recipes/tools/typescript.md`](../../recipes/tools/typescript.md) の「Nx を採用しない理由」に記録している。

**境界**（原則 8「検証は 1 コマンド」を壊さないための線引き）:

- **mise が唯一の入口であり続ける。** `mise run check` の形は変えない。turbo は mise task から呼ばれる下位レイヤであり、turbo を直接叩く経路は用意しない
- **turbo に載せるのは per-package のタスクだけ**（`typecheck` / `test` / `build` のように各パッケージの `package.json` が持つもの）。**リポジトリ全体を 1 回舐めるツール**（oxlint / oxfmt / secretlint / similarity-ts / knip / architecture checker / policy-as-test）は turbo に載せず、mise が直接呼ぶ形のままにする。載せてもキャッシュが効かず、タスクグラフだけが mise と turbo の二重管理になるため
- `turbo.jsonc` の `inputs` / `outputs`（および各パッケージ外にあるルート `tsconfig.json` を拾うための `globalDependencies`）は慎重に宣言する。**宣言が雑だと「変えたのにキャッシュヒットして緑になる」という偽陽性が起きる**ため、確定させる前に実測した: 変更なしでの再実行がキャッシュヒットすること、1 パッケージのソース変更でそのパッケージだけがキャッシュミスすること、ルート `tsconfig.json` の変更が全パッケージをキャッシュミスさせることの 3 点を確認済み（2026-08-08）
- **リモートキャッシュは使わない**。`remoteCache.enabled = false` を明示し、既定値への暗黙依存を作らない
- バージョンは原則 10 に従って**完全 pin**し、公開から 7 日以上経過したものを採用する

### 検出系ツールの運用方針

`knip` と `similarity-ts` は、**見つけたものをどう扱うかを決めないと機能しない**。ツール名を選定表に並べるだけでは足りないので、方針をここで固定する。

#### similarity-ts（重複検出）

- AST 類似度の閾値と最小行数を明示し、**検出したら CI を落とす**。参考情報として垂れ流さない
- **検出は「共通化せよ」という指示ではない。「この重複は責務の所有者が間違っているサインではないか」を問い直すトリガーである**

取りうる対応は 3 つで、どれも正当:

| 対応                           | いつ                                                   |
| ------------------------------ | ------------------------------------------------------ |
| 所有レイヤを直す               | 同じ知識が 2 箇所にある。正しい層に 1 つ置き直す       |
| 重複を残し、理由つきで抑制する | 形が似ているだけで、変更理由が異なる。将来別々に変わる |
| 実際に共通化する               | 同じ知識であり、共通化先の責務が明確                   |

2 番目を**正当な選択肢として明示すること**が要点。偶然同じ形をしているだけのコードを共通化すると、別々に変わるときに剥がすコストを払う。

LLM エージェントは「重複を排除する」という規約を素直に受け取って誤った抽象を作りやすい。規約側で先に塞ぐ。

#### knip（未使用検出）

- 未使用 export・未使用依存をゼロに保ち、CI ゲートにする
- 除外は設定ファイルに**理由コメントつきで個別に**書く。ルールごと off にしない（原則 4 の抑制規律）
- エージェントが書いたコードは未使用 export と未使用依存が溜まりやすい。**毎 PR で遮断することがこのツールの主目的**であり、リファクタ支援として使うのではない
- 実行は既定モード（`pnpm exec knip`）。`--strict` は使わない — `--production` を含意するため、全ワークスペースが devDependencies のみを持つ本テンプレートでは未使用依存の検出が空振りし、かつ誤検出が出る。実測の詳細は [`docs/recipes/tools/typescript.md`](../../recipes/tools/typescript.md)「未使用検出」参照

どちらも閾値・除外リストの具体値はレシピ層に置く（寿命が短いため）。原則層に書くのは「重複と未使用が CI で遮断されていること」だけ。

### architecture checker

**checker は 1 本に統合し、ts-morph で実装する。** import specifier の解決（tsconfig paths・index 解決）が必要で、再帰的 features の「子孫・兄弟のみ許可」判定は正規表現ベースのツールに向かないため。AST パーサ直叩き（oxc-parser）は速いが解決層を自前で持つことになる。

強制するルール:

| ルール                                                                                                                | 目的・設計意図                                              |
| --------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| レイヤ依存方向（`domain` は外部 import ゼロ、以下一方通行）                                                           | クリーンアーキテクチャ・DDD 依存方向の保護                  |
| repository は aggregate root にのみ                                                                                   | DDD 既定化の帰結                                            |
| feature 間 import は公開面経由のみ。親・他 feature 内部への import 禁止                                               | feature カプセル化と疎結合の保護                            |
| `components/` から `features/` への import 禁止                                                                       | 共通 UI の独立性維持                                        |
| transport / client の生成は指定ディレクトリのみ                                                                       | 通信クライアント生成箇所の局所化                            |
| 禁止ディレクトリ / ファイル名（`common` `shared` `utils` `helpers` `misc` `types` `models` `constants` `interfaces`） | 曖昧な名前による責務の吹き溜まり防止（原則 7）              |
| 禁止ライブラリ（DI コンテナ・`effect`・`neverthrow`・`p-retry`）                                                      | 手組み DI と fail-fast の機械強制（原則 2）                 |
| サードパーティ SDK の import は合成ルートのみ                                                                         | 外部 SDK の局所化とローカル実行容易性の確保                 |
| `index` は re-export のみ                                                                                             | 公開面宣言の純粋性維持                                      |
| テスト記法（`it.each` のタプル形式禁止、テスト名に `$field` 補間必須）                                                | テストケースの可読性と意図の明示                            |
| `.feature` と spec の対応（片方だけ存在する状態を禁止）                                                               | 振る舞い仕様と実装テストの乖離防止（§4）                    |
| step 定義から import できるのは公開エントリポイントのみ                                                               | テストが公開契約のみに依存することの強制（原則 6）          |
| ログ実装の import は指定ディレクトリのみ                                                                              | 観測性基盤（logging 境界）の局所化（原則 12）               |
| `console.*` の直接呼び出し禁止（観測は横断境界のヘルパー経由）                                                        | パイプライン外の生ログ混入防止と構造化ログの強制（原則 12） |
| `@opentelemetry/sdk-node` / 既定 exporter の import は合成ルートのみ（サードパーティ SDK ルールの実配線）             | OTel SDK 設定の局所化（原則 12）                            |
| `@opentelemetry/api` の import は `logging/` 境界からのみ（ログ実装 import ルールの実配線）                           | OTel API 利用の局所化（原則 12）                            |

import 境界の制限（ログ実装ライブラリの import 制限）だけでは、`console` のようなグローバル API の直接呼び出しを捕まえられない。そのため `console.*` の直接呼び出し自体も禁止し、観測パイプラインを経由しない生ログの混入を構造的に防ぐ。

最後の 2 行は新しいルールファイルを追加したものではなく、既存の汎用ルール（「サードパーティ SDK の import は合成ルートのみ」「ログ実装の import は指定ディレクトリのみ」）に実際の OpenTelemetry パッケージ名を設定として渡しただけである（原則8「検査ロジックの二重管理を禁止」）。**「サードパーティ SDK の import は合成ルートのみ」ルールの合成ルート判定は、当初「`application` レイヤ配下」も要求していたが、この最小の縦切りの合成ルート（`apps/api/src/composition.ts`）は DDD レイヤの外側で全レイヤを束ねる 1 ファイルであり、この要件を満たさないため誤検知していた（2026-08-09 実測）。判定はファイル名（既定 `composition.ts`）のみに絞った。

**checker 自身が fixture テスト（許可ペア / 禁止ペア）を持つことを必須にする。** ルールを書く行為も TDD の対象とし、これは原則 4 に明記する。

### policy-as-test（`tests/policy/`）

原則 4 と原則 10 の受け皿。lint ではなくテストとして書き、違反時に CI が落ちる形にする。

| テスト           | 検証内容                                                                                                          |
| ---------------- | ----------------------------------------------------------------------------------------------------------------- |
| CI 構造          | `.github/workflows/*.yml` を解析し、ゲートジョブが存在すること・他の全ジョブが `needs` でそれに依存すること       |
| 依存 pin         | manifest と lockfile を解析し、レンジ指定が残っていないこと。コンテナイメージが digest かタグで固定されていること |
| レビュー契約     | `AGENTS.md` とレビュー workflow の文言が一致すること                                                              |
| secret 参照      | `.env.example` に `op://` 参照以外の値が無いこと。workflow の `env:` に平文が無いこと                             |
| 正本の鮮度       | 正本が言及するパス・コマンドが実在すること。同一 PR 内で参照先が変わったのに正本が触られていないこと（原則 11）   |
| コンテキスト予算 | ルート `AGENTS.md` が行数上限を超えていないこと（§7）                                                             |

### 生成物の drift 拒否

生成物は生成 → 差分検査（`git diff --exit-code`）で「手編集されていないこと」と「再生成し忘れていないこと」を同時に見る。契約層・DB 型・エージェント資産の同期すべてに同じ形を使う。

### CI の実行範囲

CI は全実行する。差分検出による affected 実行は導入しない（差分検出のバグ = 検査漏れを、速いうちから背負わない）。**見直しトリガーは「CI 所要 10 分超え」として明文化**し、超えた時点で差分検出を検討する。

resolve-affected-apps スクリプトで影響アプリを算出して matrix に渡す方式（マージコミットの第 1 親を基点にする工夫つき）は、テンプレートが手狭になったときの移行先として recipes に記録する。

## 6. docs 配置

```
docs/
  principles/                          原則層
  recipes/                             レシピ層
    contract-layer/                      protobuf 版と TypeSpec 版の 2 レシピ
  adr/
    README.md                            索引表 + テンプレート
    NNNN-kebab-case.md
  design/                              現行設計（「なぜ」ではなく「今どうなっているか」）
  plan/{Component}/{YYYYMMDD}_{topic}.md   実装単位の計画と受入証跡
```

ADR は `NNNN` 連番で命名する。日付ベースより安定した相互参照 ID を作れるため（`ADR 0009 決定 2` のような参照が壊れない）。廃止された ADR は削除せず、状態欄を「廃止（→ NNNN で上書き）」に変えて残す。

### docs の言語

**docs は日本語で書く。** 原則層・レシピ層・ADR・design・plan のすべて。

判断基準・却下理由・トレードオフのように**ニュアンスが結論を左右する文章**が docs の中身であり、それを母語で書く方が精度が高い。「なぜ却下したか」が曖昧に書かれた ADR は、後から前提が変わったときに再判断できない。

英語のままにするもの:

| 対象                                                        | 理由                           |
| ----------------------------------------------------------- | ------------------------------ |
| commit メッセージ                                           | 既存リポジトリの慣行に合わせる |
| コード内の識別子・型名・ファイル名                          | 言語の慣習に従う               |
| Gherkin のキーワード（`Feature` / `Scenario` / `Given` 等） | 下記                           |

Gherkin は Scenario 名と step の**文**を日本語で書き、キーワードは英語のままにする。Gherkin 自体は `# language: ja` による日本語キーワード（`機能:` `シナリオ:` `前提` `もし` `ならば`）に対応しているが、`@amiceli/vitest-cucumber` 側の対応を確認できていないため既定にしない。使いたくなった時点で先に検証する。

この決定は blume の `i18n: { defaultLocale: "ja" }` 宣言と対になっている。**docs が日本語である以上、検索が日本語で効かなければ docs 全体が死ぬ。**

### 契約層のレシピ

テンプレート本体は契約層を空スロットにし、プロジェクト開始時に ADR 0001 として選択する。

| レシピ                        | 内容                                                                                                                                                                   | 向き                                                         |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| protobuf + buf + ConnectRPC   | server / client とも TypeScript。unary は生成クエリフック、streaming は素の client。テストはインメモリ transport で MSW 不要。破壊的変更は buf breaking が CI ブロック | 将来 backend を他言語に逃がす道を残したい / streaming がある |
| TypeSpec → OpenAPI → zod 生成 | lock ディレクトリ + 差分検査で drift 拒否。TS エコシステムに素直                                                                                                       | HTTP API が主で streaming が不要                             |

どちらを選んでも原則 1 の要件（生成物を持たない・drift 拒否・破壊的変更の機械ブロック）を満たすことをレシピ側に明記する。

レシピは**手順と設定の雛形までを持ち、動く最小 API は持たない**。動く例を同梱すると、テンプレートが片方の契約層に事実上固定され、選択スロットである意味が失われるため。

| `tools/`                  | 言語・領域ごとのツール選択肢カタログ（[索引](../../recipes/tools/README.md)）。採用していないものも含めて網羅し、「検討したか」を毎回調べ直さないための記録。§7「コンテキスト予算」の on-demand 枠に置く    |
| `tools/observability.md`  | ログ・トレースの実体の選択肢。OpenTelemetry の API/SDK + 既定 exporter は常時ロードで配線済み。**空スロットなのは実際の送り先とローカル開発の実体（Jaeger testcontainer）だけ**（原則 12。2026-08-09 改訂） |

`visual-regression.md` はスクリーンショット回帰テストを成立させるための実践的な構成をまとめたもの。開発機（macOS 等）で生成した baseline は OS 差分により CI（Linux）環境と一致せず、silent no-op や恒常的なテスト失敗の原因となる。そのため「Linux CI 上で baseline を生成・commit するパイプライン」を前提とし、ゴールデン画像回帰の検知 workflow と手動トリガーの baseline 更新 workflow を対で運用する手順をレシピとして記録する。

### blume

ドキュメントビューア・エージェント連携基盤として blume を導入する。テンプレートでの設定方針と根拠は以下の通り:

| 項目         | 設定値                                 | 根拠                                                                                             |
| ------------ | -------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 版           | **exact pin**                          | 原則 10（依存 pin）に従い、完全固定する                                                          |
| 置き場所     | **repo root / `content.root: "docs"`** | ドキュメント正本（`docs/`）を一元的に配信する                                                    |
| 実行         | **mise task**                          | 原則 8（検証は 1 コマンド・タスク正本の一元化）に従い、mise task 経由で実行する                  |
| `i18n`       | **`defaultLocale: "ja"`**              | 日本語ドキュメントの検索で必須（下記）                                                           |
| `ai.llmsTxt` | **`true`**                             | `/llms.txt` と `/llms-full.txt` を自動生成する。手動維持と異なり派生物のため第二の正本化を防げる |
| `ai.mcp`     | **`enabled: true`**                    | エージェントが実行時にドキュメントを引けるようにする（下記）                                     |
| `ai.ask`     | **あり**                               | 開発者向けローカルアシスタントとして有効化                                                       |

**`i18n` の宣言は日本語ドキュメントで必須。** 宣言しないと Orama の標準トークナイザが空白区切りしか見ないため、日本語の複合語が 1 件もヒットしない（宣言前は日本語の検索語で 0 件、latin の略語だけがヒットする）。`defaultLocale: "ja"` を宣言すると `Intl.Segmenter` ベースの分割トークナイザに切り替わり、日本語検索が正常に機能する。踏まないと気づけない類であるため、テンプレートの既定に含めて再発を防ぐ。

**運用方針**: ローカル専用。デプロイせず、CI にも組み込まない。`deployment.site` を設定せず sitemap も出さない。理由は Ask AI のエンドポイントが blume の設計上ページ内アシスタントから叩かれるもので**認証を掛けられない**こと。公開するとそのままコスト濫用の口になる。この理由は config のコメントとして設定ファイルの隣に置く（原則 4 の「抑制には理由を書く」と同じ発想を、制約の記録にも適用する）。

- `mise run docs:dev` と `mise run docs:check` のみを持つ
- `.blume/` を ignore する
- Ask AI の API キーは環境変数名で参照し、実値は `op run` で注入する（原則 9）

MCP を有効にすると `search_docs` / `get_page` / `list_pages` / `get_navigation` が生える。**docs-triage が「どこに書くか」を決め、blume MCP が「書いたものを実行時に引ける」を担保する**という往復が閉じる。ここが本テンプレートの AI native の中核である。

**MCP は既定で導入する。** docs 管理のための基盤として扱い、オプション扱いにしない。**docs をどこに書くかの規律（docs-triage）を持つなら、その docs をエージェントが実行時に引ける状態まで作らないと片手落ちになる**という判断による。

### MCP をテンプレートに配線する

テンプレートは **`.mcp.json` を commit して clone した時点で docs MCP がエージェントから見えている状態にする**。手順書に「MCP を登録してください」と書くのは原則 4（コードで表現できるものを散文に書かない）の違反であり、登録そのものをリポジトリに置く。

- `.mcp.json` に blume の stdio サーバを 1 本だけ登録する
- 起動は mise task 経由にし、`.mcp.json` からはその task を呼ぶ（コマンド列を設定ファイルに散らさない）
- 接続の承認は各エージェントの承認フローに委ねる。テンプレートは登録するだけで自動承認はしない
- Ask AI と違い MCP はローカルのプロセス間通信なので、外部公開の懸念は発生しない（ローカル専用の制約は Ask AI 側の話である）

`ai.llmsTxt` は `/llms.txt` と `/llms-full.txt` を出力する。手で維持する場合は AGENTS.md 階層との二重管理になるが、blume の llms.txt は docs から生成される派生物であり第二の正本にならないため、安全に活用できる。

## 7. AI ハーネス

### 規範ファイル

- **`AGENTS.md` を正本**とし、薄く保つ。持つ節は「絶対規約」「Stack 索引」「コマンド」「スキル参照」「現在の状態」のみ
- 「現在の状態」節は**上書き専用**。追記すると AGENTS.md が第二の決定ログになり二層モデルが崩れる。履歴は git log と ADR が持つ
- `CLAUDE.md` は `@AGENTS.md` の 1 行だけ
- nested `AGENTS.md` で近接規範を持つ。**機械強制済みのルールを書かない**（重複した瞬間に drift が始まる）。残すのは機械化できない判断基準のみ

### コンテキスト予算 — AGENTS.md を薄く保つ

ロード機構ごとにコストが違う。**常時ロードされる枠は希少で、on-demand で引ける枠は潤沢**である。この非対称を予算として明示する。

| 層                 | ロード機構           | 枠           | 置くもの                                 |
| ------------------ | -------------------- | ------------ | ---------------------------------------- |
| ルート `AGENTS.md` | 常時                 | **最も希少** | 全タスクに効く普遍規範だけ               |
| nested `AGENTS.md` | ディレクトリ近接     | 希少         | そのディレクトリを触る全タスクに効くもの |
| skill              | タスクトリガー       | 中間         | 特定種類のタスクの手順知識               |
| `docs/`            | **MCP で on-demand** | 潤沢         | それ以外すべて                           |

**blume MCP を既定にした本当の理由はここにある。** 前節では「docs-triage が置き場所を決め、MCP が実行時に引ける」と書いたが、因果はむしろ逆向きに効く — **MCP で引けるから AGENTS.md を薄くできる**。引けなければ、読ませたい情報は全部常時ロード枠に押し込むしかなくなる。

機械強制:

- ルート `AGENTS.md` に**行数の上限**を設け、policy-as-test で超過を落とす。docs-triage のセクション運用表が持つ「肥大シグナル → 退避先」を、シグナル側だけ機械化したもの
- `AGENTS.md` への追記は**常時ロード枠を消費する**ため、原則 4 の抑制規律と同型の扱いにする。追記する PR は「なぜ on-demand ではなく常時ロードが必要か」を書く

### 記憶レイヤー

原則 11 の受け皿。記憶システムを 4 要素に分けると、テンプレートは 2 つを既に持ち、2 つを欠いている。

| 要素         | 実装                                                  |
| ------------ | ----------------------------------------------------- |
| 保存         | `docs/`（正本）+ machine-local な auto memory（候補） |
| 検索         | blume MCP                                             |
| **書き戻し** | **skill として作る**（下記）                          |
| **鮮度**     | **policy-as-test として作る**（下記）                 |

**外部の memory 製品は導入しない。** 記憶が不要だからではなく、**欠けているのが保存先ではなく還流の強制**だからである。保存先を足しても正本が古くなる問題は解けず、むしろ第二の正本ができて原則 5 の二層モデルが壊れる。導入を検討する条件は「複数ツールをまたいで同じ記憶を引きたい」という具体的な困りごとが出たときで、そのときの最小手は MCP 公式の memory server（ローカル JSON）である。

**書き戻し（skill）**: machine-local な auto memory と直近の差分から昇格候補を抽出し、docs-triage にかけて置き場所を決め、**人が承認してから**書く。承認を人が持つのは、レビューを経ていない記述が規範の顔をして増殖するのを防ぐため（原則 11 ②）。昇格先の既定は `docs/`。ルート `AGENTS.md` への昇格は上記のコンテキスト予算の対象になる。

**鮮度（policy-as-test）**: 正本（`AGENTS.md` 階層・`docs/recipes/`）が言及するパス・コマンド・バージョンについて、

1. **実在性** — 参照先が存在しない場合は落とす
2. **同期** — **同一 PR 内で参照先が変わったのに正本が触られていない場合は落とす**

2 が要点である。ADR 0019 の「ADR を変更する PR は対応する規範ファイルの更新を同梱する」はレビュー観点として書かれていたが、PR スコープに限れば機械判定できる。時間ベースの失効（GitHub Copilot の 28 日など）は採らない — 使われていないことと古いことは別であり、リポジトリの正本には時間より変更イベントの方が適した信号である。

**実行中の目的保持（goal drift）は ramune（後述「ramune を既定で組み込む理由」）が担う。** 当初の設計では「タスクグラフのような実行機構側の設計課題であり、記憶レイヤーでは解けない」として対象外に置いていたが、ramune を既定のハーネスとして統合したことでこの前提が変わった。長時間タスクで目的を見失う問題は、会話履歴ではなく `.ramune/graph.json` という外在化された構造化状態を Planner が読み返すことで緩和される（docs/adr/0001-ramune-architecture.md「理由と捨てた代替案」）。テンプレートが `docs/plan/` に書く受入条件と、ramune がグラフとして持つタスク分解は別レイヤーの話であり、前者を後者に置き換えるものではない。

### ramune を既定で組み込む理由

ramune（検証付きタスクグラフ実行機構。docs/adr/0001-ramune-architecture.md・docs/recipes/tools/ramune.md）は `tools/ramune/` 配下に**既定で組み込む**。プロジェクト開始後に選ぶ空スロット（`contract/` のような）ではなく、blume MCP・codegraph MCP と並ぶ「テンプレートが最初から持つ AI ネイティブなハーネス」の一部という位置づけである。

1. **ramune は AI ハーネスそのものであり、テンプレートの主題と一致する。** テンプレートが運ぶのは「規約をどこに置き・何で強制し・何をレビューに残すかを決める手続き」（目的節）であり、ramune が機械強制する Planner/Worker の権限分離（プロンプト上の取り決めではなく PreToolUse hook で強制する）はこの主題そのものである。§9「最小の縦切り」のようなドメインコードとは性質が異なり、削除して始めてよい対象に含めない
2. **blume MCP・codegraph MCP と同じカテゴリである。** どちらも「エージェントが実行時に引ける規範/コード理解のハーネス」であり、ramune はそれに「タスク実行の構造」を足すハーネスである。カテゴリが同じものを別リポジトリに分けておく理由がない
3. **repo を分けるとゲートが 2 セットになり drift する。** ramune 単体のリポジトリと webapp-blueprint のリポジトリで別々に `mise run check` 相当のゲートを持つと、`docs/principles/` の原則（fail-fast・機械強制・依存 pin 等）を 2 箇所で独立に維持することになり、一方だけ更新されて他方が古びる事故を構造的に防げない。1 つの repo に統合すれば `mise run check` 一本で両方が揃って緑になることを機械的に保証できる

### ramune モード — 権限強制を既定で全操作に効かせない理由

ramune の PreToolUse hook（`tools/ramune/hooks`）は、Planner/Worker の役割に応じて `Bash`/`Edit`/`Write` 等を fail-closed で拒否する。これを無条件で既定有効にすると、本テンプレートを clone しただけで ramune を使う意思のない利用者の Orchestrator（メインエージェント）が最初から何も編集できなくなり、通常の作業が成立しない。そのため hook は `.ramune/graph.json` の `session.active`（`tools/ramune/hooks/src/mode.ts`）を見て、`true` のときだけ role ベースの拒否を行い、ファイルが無い・`false` なら判定を下さず（exit 0・無出力）Claude Code の通常の権限フローに委ねる。グラフファイルが壊れている・形を満たさない場合は「非稼働」に丸めず判定不能として拒否する（fail-fast の対象を「ロール判定不能」だけでなく「モード判定不能」にも対称的に広げる）。`session.active` は Orchestrator 専用の MCP ツール `ramune_start`/`ramune_end` だけが切り替えられる。判定条件を当初は環境変数 `RAMUNE_MODE` にしていたが、hook が実行中の環境変数の書き換えを観測できないこと・ramune 自身の「状態の外在化」原則（ADR 0001）と矛盾することの2点で破綻したため、グラフに外在化する現行方式に置き換えた（経緯は ADR 0003）。判定条件の詳細・拒否理由文言・権限表は docs/recipes/tools/ramune.md と docs/adr/0001・0002・0003 を参照。

### skill

**正本は `.claude/skills/`**。`mise run sync:agents` で `.agents/skills/` へ複製し、CI が差分検査で drift を拒否する。

正本の向きが `AGENTS.md`（規範）と `.claude/skills/`（skill）で逆になるのは意図的である。`AGENTS.md` はツール横断の標準ファイルなので正本に置ける（`CLAUDE.md` は `@AGENTS.md` の 1 行で済み、生成が要らない）。一方 skill にはツール横断の標準的な配置が無く、作成・検証のツールチェーンが `.claude/skills/` を対象にしているため、そちらを正本にして他ツール向けにミラーする方が drift が少ない。

同期スクリプト（`scripts/sync-agent-assets.mjs`）は次の 3 つのガードを持つ:

1. 生成物の先頭に「これは生成物であり、正本を編集せよ」というマーカーを書く
2. **マーカーの無いファイルへの上書きを例外で拒否する**（手書きファイルの誤消去を構造的に防ぐ）
3. 対応する正本が消えた孤立生成物を検出して削除する。ただし削除対象はマーカー付きのものだけ

`check` サブコマンドは期待される生成結果を再計算してバイト単位で突合し、drift があれば非ゼロ終了する。これを CI ゲートに入れる。

同梱 skill:

| skill          | 発動条件                                                                                                            |
| -------------- | ------------------------------------------------------------------------------------------------------------------- |
| `docs-triage`  | 新しい知見・規約・手順を書くとき / 既存記述を skill へ切り出すか判定するとき / AGENTS.md のセクションを更新するとき |
| `adr`          | 技術決定を記録するとき。索引の更新と対応する AGENTS.md の更新を同梱させる                                           |
| `commit`       | commit を作るとき。gitmoji prefix、論理単位での分割                                                                 |
| `pull-request` | PR を作るとき                                                                                                       |
| `setup`        | 新しい checkout を動く状態にするとき                                                                                |

skill を追加・改名した PR は、`AGENTS.md` のスキル参照節への発動条件つき登録を同梱する。この節がエージェント横断の発見可能性の正本であり、特定エージェントの自動発見機構に依存しない。

**description のトリガー設計を skill 卒業基準に加える。** skill の description が発火してほしいタイミングとずれていると、プロンプトやドキュメントによる散文での後追い補正が必要になってしまう。docs-triage の卒業テストに「description のトリガーが、その skill を使ってほしい作業のタイミングと一致しているか」を追加し、補正が要る時点で description 側を直す規律とする。

### PR 自動レビュー

Claude と Codex の 2 系統を workflow で回す。設計方針:

- diff の SHA256 を隠しコメントに埋め、同一 diff への重複レビューを抑止する
- 変更行数・新規ファイル・sensitive path（auth / migrations / infra / workflows）で delta mode と full mode を切り替える。sensitive path があれば full mode を強制する
- レビュー実行後に「ターン数が 0 でないこと」と「要約マーカーが実際に投稿されたこと」を機械検証する。レビューが空振りしたまま緑になることを防ぐ

さらに以下の運用ルールを設ける:

- **PR コメントは marker upsert する**。`<!-- review-summary -->` のような HTML コメントで既存コメントを検索し、作成と更新を出し分ける。同じ内容のコメントが PR に溜まらない
- **新しいレビューの前に、前回の未解決 bot レビュースレッドを一括で resolve する**。指摘スレッドの蓄積を防ぎ、「今回の指摘」だけが未解決として残る状態を保つ
- **suggestion 適用だけのコミットではレビューを走らせない**。スキップした事実は専用マーカー付きコメントで通知し、再依頼の導線を出す
- **bot が起こしたイベントでも発火できるように許可リストを持つ**。自 workflow が作ったコミットで次のレビューが止まる事故を防ぐ

workflow ファイルはテンプレートに同梱するが、有効化には各プロジェクトでの認証情報の設定が必要になる。この前提を README に書く。

レビュー契約のメタテスト（`AGENTS.md` と workflow の文言の突き合わせ）は原則 4 の受け皿として `tests/policy/` に置く。

## 8. インフラ

Terraform は CI-only の production root とし、鍵レス認証（Direct Workload Identity Federation）で apply する。ローカルからの `terraform apply` は行わない。

infrastructure operator の権限は `operators.tf` で追跡し、追加・削除は PR と CI apply だけで行う。**テンプレートには空リストとプレースホルダを置く**（実メールアドレスが混入すると個人情報がテンプレートごと複製されるため）。

プロバイダの API トークンは 1Password から CI へ注入する。`op run` を通す入口は mise task に閉じ、**「この task だけが秘密に触れる」を task 定義上で明示する**。

## 9. 最小の縦切り

**空の repo では全ゲートが「対象ゼロで緑」になる。** それは緑ではなく空振りであり、ゲートが飾りになっている状態と区別がつかない。テンプレートが「規約が機械強制された状態」を謳う以上、**強制が実際に働いていることを clone した人が確認できなければならない**。

そこで、全ゲートが実際に噛む最小の縦切りを同梱する。

| 置き場所                       | 中身                                                                                    |
| ------------------------------ | --------------------------------------------------------------------------------------- |
| `apps/api/src/domain/`         | 値オブジェクト 1 つ + 不変条件                                                          |
| `apps/api/src/application/`    | use case 1 つ + port 1 つ                                                               |
| `apps/api/src/infrastructure/` | port のインメモリ実装 1 つ                                                              |
| `apps/api/src/presentation/`   | ハンドラ 1 つ                                                                           |
| `apps/web/src/features/`       | feature 1 つ + `components/` に props-only な component 1 つ                            |
| 各所                           | 振る舞いの `.feature` + spec、domain の table-driven テスト、property-based テスト 1 本 |
| `e2e/`                         | `.feature` + step 定義 1 組                                                             |

**この縦切りは契約層の境界を越えない。** フロントとバックエンドは配線せず、それぞれ注入された境界の後ろで完結させる。越えさせると契約層を選ばないと縦切りが成立せず、**空スロットであるはずの契約層が事実上片方に固定される**ため。フロントの API 接点は `lib/api/` に閉じ、そこがハンドラ 1 つを持つフェイクを返す。契約層を選んだ時点で、この 1 ファイルの中身だけが置き換わる。

同じ理由で `e2e/` の `.feature` はビルド済みフロントだけを対象にする。E2E は `mise run check` に含めず、main マージ時に回す（原則 8 の「1 コマンド」は `check` の話であり、E2E はその外）。

`README.md` に**「この縦切りは配線の実証であり、消して始めてよい」**と明記する。テンプレートの使い方の見本を兼ねさせる。

## 11. 受入条件

11. `tests/policy/` の各テストが、規約を意図的に破った状態で実際に赤になる（テストが常に緑を返す空振りでないことを、導入時に 1 度確認する）
