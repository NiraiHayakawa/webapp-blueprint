# 規約は機械で縛る

## 要件

- 規約は原則としてプロンプト（人間やエージェントへの散文の指示）で守らせるのではなく、機械的な仕組みで縛る。検査可能な性質を持つ規約は検査ルールとして書き、決定的な手順は手順として定義する。散文による指示は、機械化できない判断が残る場合の最後の手段とする
- 機械強制の対象は実装コードだけではない。**規約のメタレベル**（検証の実行構造そのものが壊れていないか・依存関係の固定方針が守られているか・規範ファイルに書かれた文言と実際の運用が一致しているか）も、検査ではなく失敗するテストとして落とす。これを「規約のメタテスト」と呼ぶ。lint の警告として出すのではなく、違反時に検証全体が失敗する形にすることで、「警告は無視されうる」を構造的に防ぐ
- 検査・除外の仕組み（違反の無効化・特定対象の除外・既知の違反を許容リストに載せること）自体には、必ず理由を書く。「頻繁に引っかかって邪魔だから」のような理由のない抑制は禁止する
- 抑制は影響範囲の狭い順に選ぶ。まず該当箇所だけの抑制、次に該当ファイルだけの除外、最後に規約そのものを無効化する、の順で右に行くほど強い理由を要求する。規約そのものを無効化してよいのは「その規約がプロジェクトの構造と根本的に噛み合わない」と説明できるときだけである
- 規約を検査する仕組み自体も検証の対象にする。検査ルールを書くこと自体を、許可されるべき例・禁止されるべき例の両方を使って確認する対象として扱う

## 機械強制の受け皿

- 検証の実行構造（検証の入口が単一であること・派生する各検査がその入口に依存していること・入口を経由せずに検査を迂回する経路がないこと）を、規約のメタテストとして検証する
- 依存関係の固定方針（原則 10）が実際に守られているかを、設定ファイルとロック情報を解析するテストとして検証する
- 規範ファイル（原則 5・11）に書かれた文言と、実際の運用（レビュー手順・実行される検証の内容）が一致しているかを、両者を突き合わせるテストとして検証する
- 生成物のドリフト検査（原則 1）も同種の仕組みで、生成 → 差分検査という決定的な手順として定義する
- 規約を検査する仕組み自体が、許可されるべき組み合わせと禁止されるべき組み合わせの双方に対する確認用の例（fixture）を持つこと。これにより「検査ルールを書く」という行為自体が確認済みの状態になる
- 理由のない抑制を検出できる形式（抑制のたびに理由を書く欄が構造的に必須である形式）を検査対象にする。形式で機械強制できない抑制（機械強制の対象になっていない規約への逸脱）は、レビュー観点に委ねる

## レビュー観点

- この抑制の理由は、選んだ抑制の強さ（該当箇所のみか・ファイル単位か・規約全体の無効化か）に対して十分な強さを持っているか
- 検査ルールを新しく書いたとき、それが許可されるべき例を誤って落とし、禁止されるべき例を誤って通していないか。確認用の例を先に用意してから検査ルールを書いているか
- 散文（規範ファイル・レビューコメント）で指示している内容のうち、実際には検査可能なものが混ざっていないか。混ざっていれば、それは機械強制へ移すべきサインである
