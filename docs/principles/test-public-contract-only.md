# テスト対象は公開契約のみ

## 要件

- テストが対象とするのは公開契約と、外部から観測可能な振る舞いだけである。内部実装の詳細（非公開の関数・内部状態・呼び出し順序・処理を内部で何回呼んだかの確認）に依存したテストを書かない
- 振る舞いは**実装用語ではなく仕様の言葉**で記述する。テストの記述を読んだときに、内部の関数名・クラス名・データ構造をなぞっているのではなく、「何が起きたら何が観測されるか」が仕様として読めることを基準にする
- テストコード自身も、本番コードと同じアーキテクチャ規律（層の依存方向・公開面を経由したアクセスのみ許可すること）に服する。テストだからという理由で内部への直接アクセスを許可しない
- 外部境界（他システム・保存領域・実行環境など、テストの中で本物を使うと重い・不安定・環境依存になるもの）を持つ振る舞いは、注入された境界の後ろで検証する。境界の偽装手段そのものは契約層の選択に依存するため、原則層では「境界の後ろに置く」という要件だけを持つ

## 機械強制の受け皿

- 公開契約を経由しないテスト（非公開のエントリポイントを直接 import して検証するテスト）を検出し遮断する構造検査
- 振る舞いの記述と対応する実装コードが、片方だけ存在する状態（記述だけあって実装がない、実装だけあって記述がない）を検出する検査
- 意図的に記述と実装をずらした確認用の例を使い、「ずれを検出する仕組み自体が実際に落ちること」を確認するテスト。検出器が空振りしたまま緑を返す状態を防ぐための、検査対象への確認である
- パラメータ化されたテストの記法自体（結果が「何番目のケースが落ちたか」を人間が読める形で報告されること）を構造検査の対象にする

## 仕様の言葉で書けない場合

純粋な計算規則（状態遷移・不変条件など、外部境界を持たないロジック）を検証する際、入力空間が有界でない性質（「どんな順序で操作しても不正な状態にならない」等）を確認したい場合がある。この性質は個々の具体例を有限に列挙する形では表現できない。これは好みの問題ではなく、有限の例の列挙という表現形式そのものが構造的に扱えないケースである。

この場合に限り、仕様の言葉で書いた個別の例の代わりに、入力をパラメータ化した表形式のテストや、入力を機械的に生成して不変条件を確認する手法を使ってよい。これは「実装用語で書いてよい」という例外ではない。検証したい性質は依然として外部から観測可能な振る舞い（不変条件が破れないこと）であり、表現形式だけが個別の例の列挙から変わっている。

## レビュー観点

- このテストは、実装の書き方を変えずに振る舞いだけを変えると失敗するか。逆に、振る舞いを変えずに実装の書き方だけを変えても失敗するなら、それは実装への依存であり書き直すべきサインである
- 記述を読んだときに、実装の内部名称（関数名・変数名・型名）が漏れ出していないか。読み手が実装を知らなくても意味が通るか
- 外部境界を持つ振る舞いの記述量が増えすぎて、仕様書ではなく網羅表になっていないか（境界のパターンを機械的に列挙しているだけで、読んで意味の分かる仕様になっていない状態）
