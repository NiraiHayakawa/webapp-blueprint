# 後方互換レイヤを作らない

## 要件

- 明示的な要求がない限り、後方互換のための実装（エイリアス・非推奨のまま残す旧 API・旧形式の受け入れ経路）を作らない
- 破壊的変更を行うときは、歴史的経緯を思わせる痕跡（旧名を偲ばせる命名・旧実装への言及コメント・「以前は〜だった」という説明）ごと消し、初めからそうであったかのようにコードベースを変更する
- 変更の経緯・理由そのものは失われてよいわけではない。経緯は決定ログ（原則 5）に残し、コード自身が経緯の記念碑になることを禁止する

この原則が禁止するのは「コードの中に歴史を残すこと」であり、「歴史を記録すること」自体ではない。記録先をコードから決定ログへ移す、という要件である。

## 機械強制の受け皿

- 「非推奨だが残す」ための再エクスポート・エイリアス定義を検査可能な禁止パターンとして遮断する
- 公開面の宣言（原則 7）と組み合わせ、廃止したはずの旧経路が公開面に残っていないかを検査する
- 変更前の名前・構造を検索して「痕跡」が残っていないかを確認する検査は機械化しづらく、レビュー観点に委ねる部分が大きい

## レビュー観点

- この変更は本当に「壊してよい」ものか。想定していない外部消費者がいないか
- コードのコメントや命名に、削除したはずの旧構造への言及が残っていないか
- この判断の理由は、コードではなく決定ログに書かれているか。コード側に「なぜ今の形なのか」を説明する長いコメントを残していないか

## 却下理由が前提の変化で覆るケース

原則の運用にあたって注意すべきなのは、「過去に不採用と決めた設計」が将来も不採用のままとは限らないことである。例えば、DDD の戦術的パターン（aggregate・value object・domain event を明示的な型として書く設計）を「少人数の開発規模には式典（ボイラープレート）が過剰である」として不採用にする決定があるとする。

この判断自体は、決定した当時の前提（人手でボイラープレートを書くコスト）のもとでは合理的である。しかし LLM コーディングエージェントの普及により、aggregate・value object・domain event を書く式典コストは大きく下がる。前提が変わったことで、同じ設計判断の結論が反転しうる。

これは「後方互換レイヤを作らない」原則そのものの適用例にとどまらず、**決定ログに書かれた却下理由には「その理由が成立する前提」が暗黙に含まれており、前提が変われば決定は再検討の対象になる**ことを示している。決定ログ（原則 5）の決定は永続的な正解ではなく、前提付きの判断であることを示すために、この原則層に記録する。後方互換レイヤを作らないこと自体は、決定を変えるときに「前の設計を残したまま新しい設計を足す」のではなく、決定を反転させた上で前の設計の痕跡を消す、という形で両者は接続する。
