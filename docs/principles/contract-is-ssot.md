# 契約が単一の真実源である

## 要件

- 契約（API の形・型・スキーマ）が単一の真実源（SSoT）であり、実装層（サーバー側の実装・クライアント側の型定義・呼び出しコード）は契約から再生成可能な状態を保つ
- 再生成可能な実装層のコードはリポジトリにコミットしない。コミットされているのは契約そのものと、再生成を行うための手順だけである
- コミットされた内容と「契約から今再生成した結果」が一致しない状態（drift）を検出し、検出したら止める
- 契約への変更が既存の呼び出し側を壊す場合（破壊的変更）、それをレビュー前に機械的に検出してブロックする。破壊的変更そのものを禁止するわけではなく、「気づかずに」通過することを禁止する
- 契約とそれを使う実装は、同じ変更のまとまり（1 つのプルリクエスト等）の中で原子的に変更する。契約だけを先行させて取り込み、実装が追いつくまでの間「契約はあるが実装がない」状態を主系列に残さない。契約と実装が別のタイミングで取り込まれると、その間は契約が単一の真実源として機能していない状態になるためである

契約層の具体的な実装方式（どの記述言語で契約を書き、どう配布するか）は複数の選択肢があってよい。どの方式を選んでも、上記の 3 要件（生成物を持たない・drift を拒否する・破壊的変更を機械ブロックする）を満たすことが必須条件であり、方式の選択はこの要件を満たす手段の違いにすぎない。

## 機械強制の受け皿

- 契約から実装層を再生成する手順が、決定的な単一の手続きとして定義されていること（手順の中身は環境や手作業に依存しない）
- 「再生成 → コミット済み内容との差分検査」を検証の入口に置き、差分があれば失敗させる。差分検査は「手で編集された」ケースと「契約を変えたのに再生成し忘れた」ケースの両方を同じ仕組みで捕まえる
- 契約の破壊的変更検出を検証の入口に置き、検出したらブロックする。検出の粒度は契約の記述形式に依存するため、具体的な検出手段はレシピ層に置く

## レビュー観点

- この変更は本当に破壊的か、それとも検出器が過敏に反応しているだけか。破壊的だと判定されたときに「例外扱いで通す」運用に流れていないか
- 再生成された実装層のコードに、生成元では説明できない差分（人間が後から書き足した形跡）が混ざっていないか
- 契約層の選択（記述形式・配布方式）を変える判断が出たとき、変更後も 3 要件を満たせるかを検証してから決めているか
