# fail fast

## 要件

- silent fallback（失敗を検知しながら黙って別の経路に切り替える実装）を作らない
- デフォルト値フォールバック（本来必須の設定値・入力値が欠けているときに、既定値で穴埋めして処理を継続する実装）を作らない
- 自動リトライによって失敗を隠蔽しない。リトライ自体を禁止するわけではないが、リトライが「失敗が起きたこと自体を呼び出し側から見えなくする」目的で使われてはならない
- プロバイダ・接続先の自動切替（主系が失敗したら黙って副系に切り替える実装）を作らない
- 処理を安全に継続できない状態を検知したら、型付きのエラーとして即座に失敗させる。エラーは「何が」「なぜ」継続不能なのかを呼び出し側が判別できる形を持つ

この要件が対象にするのは「失敗を隠す」実装であり、「失敗にどう対処するか」をユーザー向けの機能として提供すること（たとえば UI 層に明示的なリトライボタンを置く）とは別の話である。前者は本要件の対象、後者は各層の設計判断に委ねる。

## 機械強制の受け皿

- 型システム上、必須の設定値・入力値を「値が無い」状態のまま素通りさせられない形にする（欠落を型として表現し、埋めずに素通りする経路を作れないようにする）
- 例外を握り込んで無視するパターン（catch した上で何もしない、既定値を返して処理を続ける）を検査可能な規約として遮断する
- 失敗系の振る舞いを検証するテストで、「エラーが型付きで伝播すること」を外部から観測可能な契約として確認する

## レビュー観点

- ここで「継続不能」と判断している基準は妥当か。実際には継続可能な状態を、過剰に失敗扱いしていないか
- リトライや代替経路を入れたい要求が出たとき、それは「失敗を隠すため」か、それとも「失敗への対処をユーザーに委ねる機能」か。後者であれば本要件の対象外だが、その境界をコードのどこで引いているか説明できるか
- エラーの型・メッセージから、呼び出し側は次に何をすべきか判別できるか。判別できない汎用エラーに丸めていないか

## 他の原則との関係

fail fast は単独の実装規律ではなく、機械で規約を縛る（原則 4）ことの前提条件でもある。検証の仕組みは「失敗したら検出できる」ことを前提に組まれるため、失敗そのものが握り込まれて外部から観測できなくなると、検証が失敗を検出する機会自体が失われる。同様に、契約からの生成物のドリフト検査（原則 1）や秘密の参照解決（原則 9）も、「本来失敗すべき状態で黙って処理が継続してしまう」経路が残っていると機能しない。fail fast はこれらの機械強制が前提にしている土台であり、個別の原則の下に埋め込むのではなく独立した原則として扱う。
