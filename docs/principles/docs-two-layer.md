# 決定ログと現行規範の二層

## 要件

- ドキュメントを寿命の異なる二層に分ける。**決定ログ**（なぜ今の形に決めたか・どの代替案を検討し何を理由に却下したか、という経緯を積み重ねる記録）と、**現行規範**（今どういう規約になっているか、という現在の状態だけを示す記述）は別の場所に置く
- 決定ログは追記専用で、決定を消さない。決定が後で覆っても、元の決定は削除せず状態を「覆された」ことがわかる形に更新して残す（no-compatibility-layer の「痕跡を消す」対象はコードであり、決定ログの記録はその対象ではない）
- 現行規範は**上書き専用**である。現行規範に経緯や理由を書き足していくと、現行規範がもう一つの決定ログになってしまい、二層モデルが崩れる。現行規範に書くのは「今どうなっているか」だけであり、履歴は決定ログと変更履歴が持つ
- どちらの層に書くかは「この記述は将来どのタイミングで参照されるか」で決める。決定した当時の理由やトレードオフを後から追う必要があるものは決定ログへ、作業中に今の規約を確認したいものは現行規範へ
- 決定ログの各記録は、日付ではなく連番で識別する。連番は日付ベースの識別より参照の安定性が高い（「決定 N の 2 番目の項目」のような相互参照が、後から記録を追加しても壊れない）。決定が覆されても記録自体は削除せず、状態欄を「覆された（→ 新しい記録の番号で上書き）」に変えて残す

## 機械強制の受け皿

- 現行規範ファイルに「追記」ではなく「上書き」の運用を強制する構造検査（現行規範が経緯・履歴を示す節を持っていないかを検査する）
- 決定ログの連番・索引の整合性検査（決定が覆されたときに、参照している側の記述が古い決定を指し続けていないか。索引に載っていない決定が存在しないか）
- 現行規範が言及する対象（パス・コマンド等）の実在性検査は原則 11 の受け皿と共有する

## レビュー観点

- この記述は「なぜ今の形なのか」（決定ログに属する）か、「今どうなっているか」（現行規範に属する）か
- 現行規範に、決定の背景や検討した代替案の説明が混ざっていないか。混ざっていれば、それは決定ログへ移すべきサインである
- ある決定が覆ったとき、覆された決定は削除されているか、それとも「覆された」という状態を保ったまま残っているか（削除されていれば、なぜその決定が過去に必要だったのかを後から追えなくなる）
