# 拡張はファイルの追加で表現される

## 要件

- 機能を拡張するときは、既存ファイルへの追記ではなく、ファイル・ディレクトリの追加で表現する。既存ファイルの行数が純増し続けることは、責務が増えている（分割すべきタイミングが来ている）サインとして扱う
- **吹き溜まり名**（責務を明示しない名前のディレクトリ・ファイル。「とりあえず置く場所」になりがちな名前）を作らない。名前は置くものの責務を表す必要がある
- **prefix による擬似的な名前空間分割**（実質 1 ファイル・1 モジュールの責務を、prefix を変えることで分割したかのように見せること）を禁止する。分割は物理的なファイル・ディレクトリの境界で行う
- モジュール・パッケージの公開面（外部から参照してよい範囲）は明示的に宣言する。宣言の書き方が実質的に「内部の任意のファイルに到達できる」ものになっていれば、宣言は形骸化しており要件を満たさない

## 機械強制の受け皿

- 禁止する名前のパターン（責務を持たない吹き溜まり名）を構造検査で検出する
- 公開面の宣言と、実際に発生している参照経路を突き合わせ、宣言の範囲を超えた参照（宣言されていない内部ファイルへの到達）を検出する構造検査
- ファイルの行数・責務の増加を監視し、閾値を超えたことを分割の検討サインとして扱う仕組み（機械的に強制するのは閾値の検出までで、実際に分割すべきかの判断はレビュー観点に残る）

## レビュー観点

- この行数増加は新しい責務が増えたからか、それとも既存の責務を書き足しているだけか。前者なら分割を検討すべきで、後者は許容できる
- このディレクトリ・ファイルの名前は、置かれているものの責務を言い表しているか。それとも「分類に迷ったものを置く場所」になっていないか
- 公開面の宣言は、実際に外部から使われるべき範囲だけを指しているか。将来の変更を楽にする目的で範囲を広げすぎていないか

## 反例

公開面の宣言をワイルドカードで書き、内部のディレクトリ構成をそのまま外部に対して展開する構成は反例である。この書き方では、公開面を宣言する行為そのものは存在するが、宣言が実質的に「すべてを公開する」ことと同じになり、deep import（宣言の意図を超えた内部ファイルへの直接参照）を防げなくなる。公開面の宣言は「書いてあること」ではなく「範囲を絞れていること」で機能するため、宣言を形骸化させてはならない。

## 吹き溜まり名について

責務を持たない名前が生まれる典型的な経路は、「どこに置くか判断がつかないコードの避難先」を先に作ってしまうことである。避難先が用意されていると、判断を先延ばしにしたコードがそこに集まり続け、避難先自体がどんどん肥大化する。これは原則 4（機械強制）が対象にする「理由のない抑制」と同じ構造の問題であり、「とりあえずここに置く」という判断は、後から見て理由を説明できない配置と同義である。

対処は「避難先を用意しない」ことであり、置き場所に迷ったコードには、迷った時点でその責務を表す新しい名前を与える。迷いを解消する行為そのものが、拡張をファイルの追加として表現する行為と一致する。
