# 検証は 1 コマンド

## 要件

- 変更が規約を満たしているかどうかの検証は、単一のコマンドで完結する。ローカルの開発環境で実行できる検証と、外部の実行環境（継続的インテグレーション等）で実行される検証は、同じ 1 つの入口を呼ぶだけであり、検証の内容そのものを外部の実行環境側の設定に個別に書かない
- 検証ロジックの二重管理（同じ検査条件が、ローカル向けの定義と外部実行環境向けの設定の両方に書かれている状態）を禁止する。検査条件は 1 か所にだけ存在する
- 外部の実行環境側の設定に書いてよいのは、「どの検証コマンド（群）をどの順番・条件で呼ぶか」という呼び出しの配線だけであり、検証の中身（何を合格・不合格とみなすか）はそこに書かない

## 機械強制の受け皿

- 検証コマンド自体を、決定的な単一の手続きとして定義する。手続きは環境変数や実行場所に依存して結果が変わらない
- 外部の実行環境側の設定が、検証コマンドの呼び出し以外の判定ロジック（合否条件の直接記述）を持っていないかを検査する
- 複数の検証項目を並行して走らせる場合でも、それらすべてに依存する単一の集約点を置き、外部からはその集約点の成否だけを見る

## レビュー観点

- この検証は、ローカルで単一のコマンドを実行するだけで外部の実行環境と同じ結果が再現できるか。外部環境固有の設定や、そこにしか存在しない情報に依存していないか
- 検証の合否条件が、コマンド定義側と外部実行環境側の設定の両方に書かれていないか。両方に少しずつ条件が分散していると、片方だけ更新して食い違う事故が起きる
- 新しい検証項目を追加したとき、それは既存の単一の入口に接続されているか。それとも入口を経由しない別経路を新設していないか
- 外部の実行環境の設定を読んだだけで、「何を検証しているか」がコマンド名の列挙以上の情報を持っていないか。持っていれば、それは検証ロジックが漏れ出しているサインである
