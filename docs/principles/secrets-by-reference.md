# 秘密は参照だけを置く

## 要件

1. リポジトリに入るのは、秘密の実値ではなく「どの秘密管理システムのどの項目のどのフィールドを指すか」を示す**参照文字列**だけである
2. ローカルでの実行時は、実行の直前に秘密管理システムから注入する形を取り、平文の実値をファイルとして書き出さない
3. 外部の実行環境（継続的インテグレーション等）は、秘密管理システムへアクセスするための資格情報を 1 つだけ持ち、実際に使う個々の秘密はそこから展開する。個々の秘密を実行環境の設定に直接ベタ書きしない
4. クラウド上で実行されるコードがクラウド自身のリソースにアクセスするための資格情報は、長期間有効な鍵を発行せず、実行環境に紐づいた鍵レスの仕組み（実行の一時的な身元による認証）を使う
5. 秘密を新しく追加する順序は、秘密管理システム側での項目作成が先、リポジトリ側の参照追加が後である。この順序が逆になっていれば、参照先が存在しない参照が生まれる

## 機械強制の受け皿

- リポジトリ全体を対象にした秘密の実値スキャンを、変更を外部に送り出す前（ローカルの最終防衛線）と外部の実行環境側の両方に置く
- ローカルの環境変数ファイルを構造的に無視対象にし、実値の混入を防ぐ。サンプル用のファイルは参照文字列の形式だけを許可し、実値の記入を許さない
- 外部の実行環境の設定に秘密の実値が直接書かれていないことを検査する

## レビュー観点

- 秘密のローテーション（更新）が、リポジトリ側の変更を伴う設計になっていないか。伴っているなら、それは「参照化」ができておらず実質的に実値がリポジトリに紐づいているサインである
- クラウドリソースへのアクセスに、長期鍵の発行が本当に不要な形になっているか。鍵レスの仕組みが使えない特殊な事情がある場合、その事情は明示されているか

## 却下した代替案

秘密を暗号化した状態でリポジトリにコミットする方式は採らない。この方式は復号鍵の配布という別の問題をリポジトリの外に残したまま、リポジトリの中に暗号文という余分な状態を増やすことになり、参照だけを置く要件を満たさないためである。

## 他の原則との関係

秘密の参照が解決できない場合（項目が見つからない・値が空である等）に、既定値で埋めて処理を継続する実装は fail fast（原則 2）の違反でもある。秘密の欠落は「継続不能」の典型例であり、デフォルト値フォールバックで隠さず即座に失敗させる。この原則は「秘密を実値でリポジトリに置かない」ことを定め、fail fast は「置かれた参照が解決できないときにどう振る舞うか」を定めており、両者は補い合う関係にある。
