# ADR 索引

決定ログ（原則 5「決定ログと現行規範の二層」）の置き場所。**「なぜ今の形に決めたか」を積み重ねる記録**であり、「今どうなっているか」は書かない（それは `docs/design/` の役割）。

命名は `NNNN-kebab-case.md`。連番は日付ベースの識別より相互参照の安定性が高いため採用する（「ADR 0009 決定 2」のような参照が、後から別の ADR を追加しても壊れない）。

廃止された ADR は**削除せず**、状態欄を「廃止（→ NNNN で上書き）」に変えて残す。過去の決定がなぜ必要だったかを後から追えなくすることを避けるため。決定した当時の前提が変わって結論が反転することはあり得る（`docs/principles/no-compatibility-layer.md` の「却下理由が前提の変化で覆るケース」を参照）が、それでも古い決定の記録自体は消さない。

## プロジェクト開始時にまず書くもの

このテンプレートは契約層（`contract/`）を空スロットのまま同梱している（`docs/plan/Template/20260807_template-design.md` §6「契約層のレシピ」）。**プロジェクトを開始したら、まず契約層の選択を ADR として書くこと**（番号は下記索引表の最大値 + 1。決め打ちにしない）。 `docs/recipes/contract-layer/` に置かれた 2 つのレシピ（protobuf + ConnectRPC / TypeSpec → OpenAPI）のどちらを採るかを決定し、理由と却下した側の代替案を残す。

既存の番号は空いていない。テンプレートが既定のハーネスとして同梱する ramune（検証付きタスクグラフ実行機構）自身のアーキテクチャ決定・その起動経路の決定・品質ゲートの決定が占めている（下記索引表参照）。プロジェクト固有の最初の決定が索引表の続きから始まるのは、`adr` skill が定める採番規則（次の番号 = 索引表の既存最大値 + 1）をそのまま適用した結果であり、特別な予約ではない。

## テンプレート

新しい ADR を書くときは、以下の 4 節構成をコピーする。

```markdown
# NNNN. タイトル

- 状態: 提案中 / 承認済み / 廃止（→ NNNN で上書き）
- 決定日: YYYY-MM-DD

## 文脈

この決定が必要になった背景。何を解決しようとしているか。

## 決定

何を決めたか。

## 理由と捨てた代替案

この決定を選んだ理由。検討した他の選択肢と、それぞれを却下した理由。

## 影響

この決定によって、他のどの決定・どのコードに制約が生まれるか。
```

各節の役割:

| 節                 | 内容                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------ |
| 文脈               | 決定が必要になった背景。ここを読めば「なぜ決定が要ったか」が分かる                                           |
| 決定               | 結論そのもの。1 行で言えることを回りくどく書かない                                                           |
| 理由と捨てた代替案 | **決定ログの中核**。検討した選択肢と却下理由をここに残す。理由が曖昧だと、前提が変わったときに再判断できない |
| 影響               | この決定が縛る範囲。後続の ADR や現行規範（`AGENTS.md` 階層）のどこを更新する必要が生まれるかを明示する      |

ADR を追加・変更する PR は、対応する現行規範（`AGENTS.md` 階層）の更新を同梱する。決定ログと現行規範は別の場所に置くが、参照先が変わったのに片方だけが更新されない状態は正本の鮮度検査（`docs/principles/knowledge-flows-back.md`）が機械的に落とす対象になる。
