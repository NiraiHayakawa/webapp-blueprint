# 0007. 差し戻しの解決は、グラフに書き込んでから再開する

- 状態: 承認済み
- 決定日: 2026-08-12

## 文脈

ramune の原則は「状態を会話の文脈ではなくグラフに外在化する」ことである（[ADR 0001](0001-ramune-architecture.md)）。Worker が詰まったら `ramune_request_replan` でノードを `blocked` にし、Planner が `blockage`（旧 `blockedReason`）を読んで細分化するか `abort` する（[ADR 0002](0002-worker-replan-signal.md)）。

**この経路には、詰まりが「外から来た答え」で解決される場合の受け皿が無い。** `blockage` は Worker が書く「何が詰まったか」であり、それに対する**答え**をどこに置くかは定義されていない。

グラフに解決内容を記録しない運用では、次の失敗モードが生じる。

| 場面                                                                                           | 発生する問題                                                                                                                                |
| ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 未決定事項について設計決定が出た                                                               | ノードを `pending` に戻しても決定がグラフに記録されない場合、コンテキストリセット時に決定が失われ、Worker が同じ理由で再度 `blocked` になる |
| 仕様の可変性について外部から指示が出た                                                         | 決定が会話文脈にしか存在しない場合、後続のサブエージェントに正確に伝播しない                                                                |
| 否定指示（「〜を行わない」という決定）が伝達の途中で肯定（「実行してよい」）と誤解釈される危険 | 決定の中身がグラフに固定されていないと、意味の反転や認識齟齬を機械的に検証できない                                                          |

会話文脈だけに頼ると、コンテキストリセット時に状態が失われ、Worker が同じ推測を繰り返して同じ理由で `blocked` になる。ramune が状態をグラフに外在化する原則から、解決内容（resolution）は必ずグラフノード自身に書き込む必要がある。

## 決定

**決定1: `blocked` の解決は、ノード自身に書き込んでから再開（`pending` へ遷移）する。** 外から来た答え（ユーザーの決定、別セッションからの指示、レビュー結果）でノードを再開するとき、Planner はその解決内容をノードに永続化する。会話文脈や単発のプロンプトにしか存在しない状態で Worker を起動しない。

**決定2: `reopen` 操作において `resolution` を必須として機械強制する。** `blocked` ノードを `pending` に戻す操作（`reopen`）の入力として非空の `resolution` 文字列を必須とし、直前の blockage スナップショットとともに `resolutions` 履歴（`ResolutionRecord`）としてグラフに永続化する（[原則4](../principles/enforce-with-machines.md): 散文は最後の手段）。

**決定3: 外部から情報を注入する側は、送信の成功ではなく結果（グラフ・ファイルへの反映）によって確認する。** 送信コマンド自体の成功を情報伝達の完了とみなさず、意図した変更がグラフや成果物に現れたことを確認する。

## 理由と捨てた代替案

- **代替案 A: `blockedReason` / `blockage` を残したまま `pending` に戻し、そこに答えを追記する.** 採らない。`blockage` は「Worker が詰まった理由」という意味を持つフィールドであり、そこに答えを混ぜると意味が二重になる（[原則12](../principles/observable-by-design.md): message はフィールドからの描画であり乖離しない）
- **代替案 B: 決定を ADR などの別文書にのみ書き、ノードには参照だけを載せる.** 採らない。ノード実行前の Worker は実行対象ノード自身の情報から直接判断できる必要があり、ノード自身が解決内容（`resolution`）を保持しなければ自律的な実行が成立しない
- **代替案 C: 散文・プロンプトの規範だけで済ませ、機械強制しない.** 採らない。プロンプト上の指示だけではコンテキストリセットや解釈齟齬による手戻りを防止できないため、`reopen` の型・バリデーションとして `resolution` を必須化する（[原則4](../principles/enforce-with-machines.md): 散文は最後の手段）

## 影響

- `tools/ramune/graph`: `reopen` 操作において `resolution` 引数を必須とし、`ResolutionRecord` としてノードの `resolutions` に記録して `pending` へ遷移させる（実装済み）
- `.claude/agents/planner.md`: `blocked` ノードを `reopen` する際は解決内容を指定して再開する責務を明文化する
- [ADR 0002](0002-worker-replan-signal.md): 差し戻し経路（`blocked`）からの復帰において「解決の書き戻し」を必須ステップとして位置づける
- 外部連携・運用: 外から情報を注入する運用においては、送信成功ではなく成果物・グラフへの反映結果を検証する手順を含める
