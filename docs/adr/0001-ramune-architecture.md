# 0001. ramune のアーキテクチャ

- 状態: 承認済み
- 決定日: 2026-08-08

## 文脈

Claude Code のような LLM コーディングエージェントに複数ステップのタスクをまとめて任せると、
2 つの問題が起きる。

1. タスクの状態が会話履歴にしか存在しない。コンテキストがリセットされる、プロセスが落ちる、
   セッションを跨ぐ、のいずれかが起きると状態を失い、どこまで終わったかを再構築できない
2. 計画（何をやるべきか）と実行（実際にツールを叩く）が同じロールの中で混ざっている。1つの
   会話が「次に何をすべきか」を決めながら同時にファイルを編集し続けると、計画の変更が実行の
   都合に流されやすく、逆に実行中に計画そのものを書き換えてしまう事故も起きる

既存の主要なコーディングエージェント製品を見渡しても、Planner（計画者）と Worker（実行者）
を型・API・権限のレベルで構造的に分離しているものは見当たらない。役割分担はプロンプト上の
取り決めに留まり、モデルがその取り決めを守るかどうかに依存している。これが本アーキテクチャの
出発点である。

## 決定

ramune を、次の3特徴を満たす検証付きタスクグラフ実行機構として設計する。

1. **状態の外在化** — タスクの状態を LLM の会話履歴に置かず、リポジトリ内の
   `.ramune/graph.json` に DAG として保持する。グラフが唯一の真実源であり、コンテキストが
   リセットされてもプロセスが落ちても状態は残る
2. **Planner / Worker の構造的分離** — Worker はグラフの構造を変更できず、Planner はツール
   を実行できない。この分離はプロンプトではなく hook で機械強制する
3. **検証可能な差分操作** — グラフの編集は自由な書き換えではなく `insert_node` /
   `reopen` / `abort` / `set_result` の操作列に限定する。入力は JSON Schema で強制し、
   適用前に DAG 不変条件（サイクル禁止・孤立ノード禁止・start/end の保護・存在しない ID
   への参照禁止・ID の一意性）を検査し、違反は明確なエラーで拒否する

ノードの選択（`ramune_next_node`）は決定的にする。「`status` が `pending` かつ全 `deps` が
`done` のノード」を機械的に選ぶ。これは次に述べる終了判定の話とは独立である。

一方で、次の2点は**意図的に満たさない**。

- **決定的な終了判定は実装しない。** 「全ノードが done になったら機械的に終わらせる」仕組みを
  作らない。タスクグラフ全体が完了したかどうかの判断は Planner（LLM）に委ねる
- **小型ローカルモデル向けの最適化はしない。** フロンティアモデル（Claude Code）を前提にする

## 理由と捨てた代替案

### 決定的な終了判定を実装しない

終了判定を LLM に委ねると、会話ベースの実行が抱えていた「早すぎる完了宣言」のリスクが
そのまま戻るように見える。しかし ramune では Planner が判定する対象が会話履歴ではなく
グラフになるため、このリスクは緩和される。会話履歴は文脈が長くなるほど古い情報が埋もれて
判断材料から抜け落ちるのに対し、グラフは各ノードの `status` と `deps` を常に一望できる
構造化された状態であり、「本当に全部終わっているか」を Planner が確認する材料が失われない。
それでもなお終了判定自体を機械化しない理由は、「グラフに列挙されたノードが全部 done」と
「ゴールが実際に達成された」は別の命題だからである。ゴールに対してノード分解が十分だったか
を判定できるのは、ゴールの意味を理解している Planner だけであり、機械的な完了条件に置き換
えると「グラフ上は緑だがゴールは未達成」の状態を検出できなくなる。

### 小型ローカルモデル向けの最適化をしない

低コストなローカルモデルでも動く設計にする道もあったが、それには推論経路の簡略化・出力形式
の緩和・エラー処理の単純化といったトレードオフが伴う。ramune はフロンティアモデル
（Claude Code）が前提であるコーディングワークフローに組み込むことを目的にしており、
対応範囲を広げるために検証の厳密さを緩めることを避けた。

### 却下した代替案1: 耐久実行エンジン（durable execution）

状態を外部に永続化する点は同じだが、モデルが DAG ではなく逐次的な journal（実行ログの
追記列）である。journal は「次に何をすべきか」を再構築するために先頭から再生する必要があり、
グラフのように「今どのノードが `pending` で選択可能か」を直接問い合わせる形にならない。
また構造上、ステップ間の依存関係を明示的な形（`deps`）で持たないため、Planner が構造を
差分操作として安全に組み替える、という ramune の要件と噛み合わない。

### 却下した代替案2: 静的 DAG のワークフローエンジン

DAG で状態を持つ点は ramune と同じだが、実行時に計画そのものを変更できない（グラフは事前に
確定し、実行はそれをなぞるだけ）。ramune が扱うのはコーディングエージェントの計画であり、
実行の途中で新しい依存タスクが必要だと分かることが前提にある。計画を実行中に安全に変更できる
必要があるため、静的な DAG では要件を満たさない。ramune が `insert_node` という差分操作を
持つのはこのためであり、既存エッジを `from → new → to` に組み替える形にすることで、
孤立ノードが構造的に発生しないまま実行時にグラフを拡張できるようにしている。

## 影響

- `tools/ramune/graph` は DAG モデルと不変条件検査・差分操作の適用を実装する。この決定が
  変わらない限り、差分操作は `insert_node` / `reopen` / `abort` / `set_result` の4種類に
  留める
- `tools/ramune/mcp-server` は `contract/README.md` が定める JSON Schema を契約として実装し、
  `tools/ramune/hooks` は Planner / Worker のツール権限をこの ADR の分離方針に沿って機械強制する
- 終了判定を機械化する提案が今後出た場合、この ADR の「理由と捨てた代替案」節に書いた前提
  （グラフ構造の完了とゴール達成は別の命題である）が変わったかどうかをまず確認する
