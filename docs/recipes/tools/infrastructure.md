## 1. IaC（Infrastructure as Code）

| 項目           | 内容                                                                                                                                                                                                                                                   |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 何をするか     | クラウドリソースの定義をコードとして書き、`plan` / `apply` で反映する。                                                                                                                                                                                |
| いつ要るか     | クラウドリソース（Cloud Run・Firestore・IAM 等）をコードで管理したくなった時点。テンプレは `infra/` に骨格だけを持ち、クラウドプロバイダ自体は未選定（[`infra/README.md`](../../../infra/README.md) 参照）。プロバイダを選定した時点でこの骨格を埋める |
| テンプレの採否 | **Terraform を採用**（`infra/` の骨格・`.tflint.hcl`）。他の選択肢（OpenTofu / Pulumi / CDK）は特定要件に応じて検討する                                                                                                                                |

### 検討した他の選択肢

| ツール       | 何をするか                                                                   | 未確認・未採用の理由                                                                                                                                                                     |
| ------------ | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OpenTofu** | Terraform のオープンソースフォーク（HashiCorp のライセンス変更を契機に分岐） | Terraform 言語仕様とほぼ共通であり、Terraform 言語のまま OpenTofu バイナリで実行する構成も可能。テンプレートはプロバイダ・CLI とも未選定のためこの選択自体をプロジェクト開始時に持ち越す |
| **Pulumi**   | 汎用プログラミング言語（TS/Python/Go 等）で IaC を書く                       | HCL より学習コストは下がるが、コード品質規約（本テンプレートの architecture checker 等）を IaC コードにまで及ぼす設計が別途要るため未採用                                                |
| **AWS CDK**  | AWS 専用。プログラミング言語から CloudFormation を合成する                   | AWS を選ぶプロジェクトでのみ検討対象になる                                                                                                                                               |

### tflint — provider プラグインの有無で何が変わるか

`.tflint.hcl` は本テンプレートに**採用済み**（`infra/.tflint.hcl` 相当、リポジトリ直下の `.tflint.hcl`）。有効にしているのは組み込みの `terraform` ルールセット（provider 非依存、`preset = "recommended"`）だけで、`plugin "aws"` / `plugin "google"` のような provider 固有プラグインは入れていない。

| 状態                                              | 何が検査されるか                                                                                                                                     | いつ足すか                                                                                                                                                                                                                              |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **provider プラグインなし（現状）**               | Terraform 言語そのものの構文・スタイル（未使用変数・非推奨構文等）のみ。`terraform_required_version` は理由つきで無効化済み                          | -                                                                                                                                                                                                                                       |
| **provider プラグインあり（プロジェクト開始後）** | 特定クラウド（`tflint-ruleset-aws` / `tflint-ruleset-google` 等）のリソース属性の妥当性（存在しないインスタンスタイプ・非推奨 API 等）まで検査できる | クラウドプロバイダを選定し、そのプロバイダのリソースを `infra/` に実際に書き始めた時点。`.tflint.hcl` に `plugin` ブロックを追加し、`terraform_required_version` を再度有効化する（[`infra/README.md`](../../../infra/README.md) 参照） |

## 2. クラウドランタイム

**選定軸は 4 つ**: ①無料枠・コスト体系 ②ストリーミング対応（レスポンスをバッファせず配信できるか） ③コールドスタート ④課金モデル。条件はクラウド事業者の仕様改定で変わるため、実際に選定する時点で必ず一次情報を再確認すること。

| ランタイム                                | 何をするか                                                    | 選定軸ごとの特徴                                                                                       | テンプレの採否                                                                                          |
| ----------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| **Cloud Run（サービス）**                 | リクエスト駆動のコンテナ実行。scale-to-zero                   | ストリーミング対応（HTTP/1.1 のままトークン逐次配信）。課金: リクエスト処理中の wall-clock × 割当 vCPU | **未採用（プロバイダ選定待ち）**。Go/TS バックエンドの実行基盤としての有力候補                          |
| **Cloud Run（ジョブ）**                   | 有限タスクの実行。HTTP リクエストのタイムアウト制約を受けない | 長時間処理は service ではなく job に置く。Job task のタイムアウトは最大 168 時間（7 日）               | 未採用（プロバイダ選定待ち）                                                                            |
| **Cloudflare Workers（Static Assets）**   | 静的アセット配信 + エッジでのリクエスト処理                   | 静的アセット配信は無料枠が手厚い。ストリーミング対応。V8 isolate ベースでコールドスタートが極小        | **未採用（プロバイダ選定待ち）**。フロント配信基盤としての有力候補                                      |
| **Cloudflare Workers（backend として）**  | Worker 上でアプリケーションサーバーを動かす                   | エッジ実行特有の Node.js 互換性制約や SDK 依存関係に注意が必要                                         | **不採用**。バックエンド用途では制約により見送り                                                        |
| **Vercel（Fluid Compute）**               | Active CPU 課金のサーバーレス実行                             | プランの商用利用条件やベンダーロックインの検討が必要                                                   | **不採用**。プロジェクトの要件に応じて再検討の余地あり                                                  |
| **Firebase Hosting + Cloud Run rewrites** | 同一オリジン化（CORS 回避）のための rewrite                   | rewrite 経由でのストリーミングレスポンスのバッファリング挙動やタイムアウト制約に注意が必要             | **不採用**。ストリーミングが要件にないプロジェクトでは再検討の余地あり（CORS 消滅のメリットは実在する） |
| **AWS Lambda**                            | イベント駆動のサーバーレス実行                                | AWS を採用する場合の標準選択肢                                                                         | 未検討（AWS を選ぶプロジェクトでのみ比較対象になる）                                                    |
| **Fly.io / Railway / Koyeb**              | コンテナのマネージドホスティング                              | 各サービスの無料枠・課金体系の改定に注意が必要                                                         | **不採用**                                                                                              |

**組み合わせパターンの実例**: 「フロント配信は Cloudflare Workers Static Assets、バックエンドは Cloud Run」というハイブリッド構成など、静的配信とアプリケーションサーバーで異なるランタイムの強みを使い分ける選択も現実的な選択肢として記録しておく。

| **droast**（dockerfile-roast） | Dockerfile lint の inline suppression に理由を必須にする薄いポリシーレイヤ    | Dockerfile lint（hadolint 等）を導入し、抑制に理由を強制したい時点。原則4「抑制には理由を書く」の Dockerfile 版 | 未採用（Dockerfile 自体を持たないため）。**原則4「抑制には理由を書く」規律の実例の 1 つ**。Dockerfile を書くプロジェクトでは hadolint とセットで検討する                          |

## 5. 認証: Workload Identity Federation vs サービスアカウントキー

原則: [`docs/principles/secrets-by-reference.md`](../../principles/secrets-by-reference.md) 要件④「クラウドランタイムの資格情報は鍵レス」

| 方式                                    | 何をするか                                                                                  | なぜ避けるか（サービスアカウントキー）                                                                                                                                                                                                                                                  |
| --------------------------------------- | ------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Workload Identity Federation（WIF）** | CI 実行環境の一時的な身元（OIDC token 等）をクラウド側の IAM が信頼し、長期鍵なしで認証する | -                                                                                                                                                                                                                                                                                       |
| **サービスアカウントキー（長期鍵）**    | JSON 形式の鍵ファイルを発行し、実行環境の secret として保存して認証に使う                   | 鍵が漏洩すると失効させるまで無期限に有効。secret ストア・CI 設定・ローカルの `.env` 等、鍵が保存されうる場所が増えるほど漏洩経路が増える。ローテーションが手動運用に依存し、原則9のレビュー観点（「秘密のローテーションがリポジトリ側の変更を伴う設計になっていないか」）に抵触しやすい |

**テンプレの採否**: WIF を既定とする（原則9 に既に明文化済み）。

## 6. secrets: 1Password / Secret Manager / dotenvx

原則: [`docs/principles/secrets-by-reference.md`](../../principles/secrets-by-reference.md)

| ツール                                 | 何をするか                                                                           | テンプレの採否                                                                                                                                                                                            |
| -------------------------------------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1Password（CLI / Service Account）** | `op run` / `op inject` でローカル・CI に秘密を注入する。参照文字列のみを repo に置く | **採用**。CI に置く GitHub Secrets を 1Password Service Account トークン 1 本だけにし、そこから個々の秘密を展開する構成にする（[`infra/README.md`](../../../infra/README.md) 参照）                       |
| **GCP Secret Manager**                 | クラウド側のマネージド secret ストア                                                 | 未採用（クラウドプロバイダとして GCP を選んだ場合の候補。1Password と競合するのではなく、「CI から見た唯一の入口」を 1Password に置き、クラウド側の実体は Secret Manager にする、という併用構成も取れる） |
| **dotenvx**                            | 暗号化した `.env` をリポジトリにコミットし、実行時に復号鍵で復号する                 | **不採用**。理由は原則9（[`docs/principles/secrets-by-reference.md`](../../principles/secrets-by-reference.md)「却下した代替案」）に既に明記済み（暗号文という余分な状態を repo に増やさないため）        |

| --------------------- | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **Firebase emulator** | Firestore / Auth 等の Firebase 製品をローカルで模倣する | 未採用（Firestore を契約層・データストアとして選んだ場合の候補。実クラウドではなく emulator を開発・CI の主戦場にする方針を推奨） |
