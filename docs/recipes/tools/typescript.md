# レシピ: TypeScript を書く場合のツールカタログ

原則: [`docs/principles/enforce-with-machines.md`](../../principles/enforce-with-machines.md)（規約は機械で縛る）・[`docs/principles/pin-dependencies.md`](../../principles/pin-dependencies.md)（依存は完全固定する）

## このカタログの目的

`docs/plan/Template/20260807_template-design.md` §7「コンテキスト予算」の通り、常時ロードされるのはルート `AGENTS.md` だけで、ここは最も希少な枠である。ツールの選定理由・却下理由をそこに書くと枠を食い潰すため、**TypeScript を書く段になって初めて引く**このレシピに退避する。

書き方の規約: 各ツールは「何をするか」「いつ要るか(段階的開示のトリガー)」「テンプレの採否」を持つ。**採用していないツールも含めて書く** — 検討して採らなかったことの記録が、同じ調査を繰り返させないためのこのカタログの価値である。

実際に本テンプレートが今どのバージョンを pin しているかは、この文書ではなく `pnpm-workspace.yaml` の `catalog:`(実体層)を見ること。ここでのバージョン言及は「調査・確認した時点で何を使っていたか」の記録であり、実体層の現在値と食い違うことがあり得る(三層構造、design doc §1)。

### Nx を採用しない理由

design doc §3 は「Nx は generator/plugin まで抱えるため mise と責務が被る」ことを Turborepo 選定の理由に挙げているが、これは具体的なトレードオフに基づく。

- タスク実行そのものを Nx に一本化すると、`mise.toml` は Nx コマンドを叩くだけの薄いラッパーになりがちである。これは本テンプレートが守りたい「mise が唯一の入口であり続ける」設計とは逆方向(Nx が事実上の正本になってしまう)
- 大半のタスク呼び出しは `--skip-nx-cache` を明示的に付けており(`contract:generate` 等のコード生成タスク)、キャッシュを使っているのは `typecheck,lint` と `test` の 2 箇所だけというケースでは、Nx の機能のうち実際に効いているのはほぼ Turborepo と同等の「タスクキャッシュ」部分だけである
- `@nx/js:typescript-sync` generator(TS project references の自動同期)は、Nx でなければ得られない機能ではなく、本テンプレートは同種の同期を `tsconfig.json` の手動 `references` + CI drift 検査(原則1・原則11 の受け皿)で代替できる

**結論**: 「Nx はキャッシュ以外の機能(generator/sync)も実際に使われる」ものの、その機能はタスクキャッシュ目当てで Turborepo を選ぶ判断を覆すほどではない。generator 機能が必要になった時点(プロジェクト数が増えて TS project references の手動同期が壊れ始めたとき)で Nx への移行を再検討する、という退避条件として記録する。

### lint 設定は preset を extends する

`docs/plan/Template/20260807_template-design.md` §5 の該当節にすでに詳しいため、ここでは要点と実体層への参照だけを書く。

- **なぜ opt-out(全部 error → 引き算)を選ばないか**: oxlint の全カテゴリを error にすると、同時に満たす書き方が存在しないルールのペアが実測で 9 組見つかっている(ガード節の `continue` とネスト深さ、`no-void` と floating promise の推奨修正、`require-await` と `promise-function-async` など)。Go/golangci-lint の作法(`default: all` + 明示的 opt-out)を TypeScript に持ち込むと、規約として成立しない規約になる
- **ultracite の Oxlint provider をそのまま使わない理由**: `ultracite` の Oxlint provider は `oxlint.config.ts` を**生成**する方式で配布されており、vp のような「vite.config.ts の lint ブロックが lint 設定の唯一の正本」という運用とは二重管理になる。本テンプレートは vp を採らないためこの制約自体は無いが、代わりに「`oxlint.config.ts` を手書きし、preset を `extends` 配列に import する」形を採る(実体層: `oxlint.config.ts` の `import core from "ultracite/oxlint/core"`)
- **preset のバージョンは lint 本体と対で pin する**: preset が新しすぎると、oxlint 本体が知らないルール名を参照してパース時に loud fail する。この失敗は静かでないため、対で pin してさえいれば CI が不整合を機械的に検出する

### 複雑度・認知的複雑度は codopsy に委ねる

oxlint(ultracite preset)の複雑度・肥大系ルールは循環的複雑度(`complexity`)と行数・文の数(`max-lines`/`max-depth`/`max-params` 等)のみを見る。**認知的複雑度**(ネストの深さで重み付けした読みにくさ)は測れない。この穴は言語横断のツール(codopsy)で埋める。詳細・除外理由・oxlint との役割分担は [`quality-gates.md`](quality-gates.md) 参照。

### knip の運用: `--strict` を使わない

design doc §5「検出系ツールの運用方針」が原則を書いているのに対し、ここには本テンプレートの実装で確定した具体的な判断を記録する。

`mise.toml` の `knip` task は当初 `--strict` を渡していたが、2026-08-08 の整合性検証で `mise run check` を実行して失敗を確認し、外す決定をした。`--strict` は `--production` を含意し、production mode では未使用判定の対象が `package.json` の `"dependencies"` のみになる。本テンプレートは全ワークスペースが `devDependencies` のみを持つ(実行時依存を持たないツール/テンプレートリポジトリのため)ため、`--strict` では **(a)** devDependencies の未使用が一切検出できずツール導入の目的が空振りし、**(b)** テストファイルからしか使われない export やコード上正しく記載済みの devDependency が誤って「未使用」「unlisted」と検出される、の両方が起きることを実行して確認した。**「未使用検出は CI ゲートにする」という原則を、`--strict` という一見厳格な方が正しく見えるオプションが逆に無効化する具体例**として記録する。

## anti-slop — 個別の丁寧な記録

[dmmulroy/anti-slop](https://github.com/dmmulroy/anti-slop) は oxlint の `jsPlugins` に載せる自作プラグイン。**oxlint 本体にも ultracite preset にも存在しないルールを 15 個足す**ため、「既存設定のどこが緩いか」という比較にはならない。採否の判断と捨てた代替案は [ADR 0009](../../adr/0009-vendor-anti-slop-oxlint-rules.md)。

### バージョン選定(原則10: 依存 pin)

vendor 方式で配布されている(README が「固定された npm 依存ではなく、コピーして各リポジトリで手を入れて使う」ことを明示している)。したがって pin するのはプラグインのソースではなく、**プラグインの実行時 API である `@oxlint/plugins`** のバージョンになる。

- `@oxlint/plugins` は **`oxlint` と同じバージョンに固定する**。両者は同じリリース列で公開されており、ずれると実行時 API が合わなくなる。`pnpm-workspace.yaml` の catalog で隣接させているのはこのため
- プラグイン本体は `tools/oxlint/anti-slop/` に置き、`oxlint.config.ts` の `ignorePatterns` で lint 対象から外す(他所のコードであり、本テンプレートの規約で縛る対象ではない)
- upstream の更新は自動で追わない。vendor した時点のソースがこのリポジトリの正本になる
- **他のリポジトリ横断スキャナからも外す。** vendor したコードを自分の規約で測らない、という同じ判断を 3 つのツールに適用している: oxlint（`ignorePatterns`）・codopsy（`.codopsyrc.json` の `skipDirs`）・similarity-ts。similarity-ts だけはパス除外オプションを持たないため、重複している upstream のヘルパに `// similarity-ignore` コメントを直接足している（2026-08-18 実測: `no-unknown-parameters.ts` と `no-object-parameters.ts` の `parameterAnnotation` が 98.32% 一致で `--fail-on-duplicates` を落とす）。**再 vendor するときはこのコメントを付け直し、`pnpm exec oxfmt` を掛け直すこと**（oxfmt は vendor 先も整形する。upstream はタブ、本テンプレートはスペース）。 パスを列挙する形にしなかったのは、`similarity-ts .` が新規ディレクトリを自動で拾う性質を失うと、検査対象から黙って外れるディレクトリが生まれるため
- **`jsPlugins` の登録はルートの `oxlint.config.ts` に置く必要がある。** 相対 specifier を `extends` した設定側に書くと oxlint が明示的に拒否する（2026-08-18 実測: `Relative JS plugin specifiers are not supported in configs provided via extends`）。設定を分割したくなったら、vendor 先を pnpm の workspace パッケージにしてパッケージ名で参照する形になる

### 15 ルールのうち、何が実際に落ちたか(2026-08-18 実測)

全ルールを "error" で回した時点の違反は **152 件 / 9 ルール**。残る 6 ルールは素で緑だった。

| 発火したルール                              | 件数 | 何を指していたか                                      |
| ------------------------------------------- | ---- | ----------------------------------------------------- |
| `no-unknown-parameters`                     | 34   | 手書きの境界パーサが `unknown` を受けている           |
| `no-shape-in-symbol-names`                  | 33   | 型述語名(`isGraphShape` 等)と、viewer の SVG 図形名   |
| `no-runtime-typeof`                         | 33   | 同じ境界パーサ内の `typeof` 絞り込み                  |
| `no-unsafe-dictionary-type`                 | 15   | `Record<string, unknown>`(大半はログの追加フィールド) |
| `require-safety-comment-for-type-assertion` | 14   | 根拠コメントの無い `as`                               |
| `no-known-value-widening`                   | 10   | 既知のキーを持つリテラルへの広い型注釈                |
| `no-unknown-returns`                        | 8    | `unknown` を返す関数契約                              |
| `no-reflect-get`                            | 3    | 動的プロパティ読み出し                                |
| `no-object-parameters`                      | 2    | `object` 型の引数                                     |

150 件はコードの側で直した。残る 2 件（`tools/ramune/hooks/src/role.ts`）は ADR 0004（hook のソースは `node_modules` を要する import を持たない）と衝突するため、**行単位で抑制して理由をコードに書いてある**。`no-runtime-typeof` の `allowInTypeGuards: true` は解にならない — 型述語の中の `typeof` は許されるが、その述語の `unknown` 引数が `no-unknown-parameters` で落ちる（2026-08-18 実測）。**この 2 ルールは組で、スキーマライブラリ無しの境界パースを原理的に禁じている。**

**素で緑だった 6 ルール**: `no-module-mocking` `no-chained-type-assertions` `no-widen-then-assert` `no-conditional-empty-object-spread` `no-unknown-type-aliases` `no-reflect-apply`。

このうち `no-module-mocking`(`vi.mock` 等の禁止)が 0 件だったことには意味がある。本テンプレートは DDD の port / adapter で実物の差し替え口を持つため、モジュールモックを必要としない構造に既になっていた。**別々に設計された規約が同じ結論に収斂した箇所**であり、以後この構造を崩す変更はこのルールが機械的に止める。

### 既存ルールとの衝突

`typescript/consistent-indexed-object-style`(ultracite preset で "error")は index signature を嫌い、**help に「`Record<string, unknown>` を使え」と書いてある**。この help にそのまま従うと `no-unsafe-dictionary-type` が落ちる。

両方を満たすのは `Record<string, JsonValue>`(JSON 値の union)であることを実測で確認した。ログの追加フィールドはもともと JSON に直列化される契約なので、これはルールへの譲歩ではなく型が正確になった側の変更である(原則 12)。

### コスト

`oxlint --type-aware` 全体の所要は **1799ms → 1898ms**(+100ms、2026-08-18 実測)。`mise run check` の他のゲートに埋もれる差であり、常時有効で問題にならない。

## vp (VITE+) — 個別の丁寧な記録

`dev`/`build`/`test`/`lint`/`fmt`/`check` を 1 CLI に統合するツールチェーンとして検討された。

### なぜテンプレートが採らなかったか

**pre-1.0 であること自体がリスクになる。** 「vp は pre-1.0(0.2.4)。詰まった場合に pnpm + 素の vite CLI へ退避できるよう、vp 固有機能への依存はタスク定義に閉じる」という退避計画が前提になるツールを、テンプレートの既定にはできない。加えて `@cloudflare/vite-plugin`(Vite 6+ 必須)との共存が未検証だったことも、pre-1.0 特有の統合リスクの一例である。

### vp を採る場合に何が変わるか

vp を選択したプロジェクトのために、変更点を具体的に記録する:

| 項目                               | vp を採らない場合(本テンプレートの既定)                                       | vp を採る場合                                                                                                                                                                                     |
| ---------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| lint 設定の正本                    | `oxlint.config.ts`(oxlint 自身が自動探索する設定ファイル)                     | **ルート `vite.config.ts` の `lint` ブロック**。vp 公式が「`oxlint.config.ts`/`.oxlintrc.json` と `vite.config.ts` の併用は非推奨」と明言しているため、oxlint 単体の設定ファイルを作らない        |
| ultracite preset の扱い            | `oxlint.config.ts` が `ultracite/oxlint/core` を `extends` 配列で import する | ultracite の Oxlint provider は `oxlint.config.ts` を生成する方式のため vp の運用と二重管理になる。preset の**中身だけ**を `vite.config.ts` の `lint.categories` に手で移植するか、見送るかの二択 |
| フォーマット・型検査・テストの実行 | oxfmt / `tsc --noEmit` / vitest をそれぞれ個別に mise task から呼ぶ           | `vp fmt` / `vp check`(型)/ `vp test` に統合される。CI ステップも `vp check` 1 本に集約できる(想定パイプライン: `vp check` → `tsc --noEmit` → `depcruise` → `knip` → `ast-grep scan` → `vp test`)  |
| タスクグラフとキャッシュ           | Turborepo(上記参照)                                                           | **vp 内蔵の Vite Task が既に依存グラフのタスク順序 + 入力追跡キャッシュを持つ**。Turborepo を足すと三重管理になるため入れない                                                                     |
| 退避のしやすさ                     | (該当なし)                                                                    | vp 固有機能への依存をタスク定義に閉じ込め、詰まったら pnpm + 素の vite CLI へ退避できるようにしておく設計が必須                                                                                   |

## Turborepo を採用する理由 — 却下判断の前提が壊れていた

design doc §5「Turborepo を採用する理由」に経緯の全文がある。ここでは、それが「却下理由が前提の変化で覆るケース」であることの要旨だけを記録し、詳細は設計文書を正とする。

- **元の判断**: 過去の検討では Turborepo を却下していたが、理由は「Nx/Turborepo は採らない」ではなく「vp の Vite Task が既にタスク順序 + 入力追跡キャッシュを持つため、Turborepo を足すと三重管理になる」だった
- **前提の消滅**: 本テンプレートは vp を採用していない(上記)。比較対象の vp Vite Task が存在しない以上、この却下理由は最初から成立しない。退避条件として「vp の Vite Task キャッシュが信頼できない場合、TS 側限定で Turborepo を退避先として再検討する」とされており、vp ごと落とした本テンプレートはこの退避条件より強い状態にある
- **実測で残った採用理由**: `pnpm -r` は依存グラフ順の解決をカバー済みだが、`mise.toml` には入力追跡キャッシュの宣言が 1 つも無く、同じソースに対して `mise run check` を繰り返しても `typecheck`/`test` は毎回フルスキャンし直す。この欠落だけが実質的な採用理由であり、「三重管理」の懸念とは別の理由で採用する
- **境界(原則8「検証は1コマンド」を壊さないための線引き)**: mise が唯一の入口であり続ける。turbo に載せるのは per-package のタスク(`typecheck`/`test`/`build`)だけで、リポジトリ全体を 1 回舐めるツール(oxlint/oxfmt/secretlint/similarity-ts/knip/architecture checker/policy-as-test)は turbo に載せず mise が直接呼ぶ。リモートキャッシュは個人利用前提のため使わない(`remoteCache.enabled = false` を明示し、既定値への暗黙依存を作らない)。テレメトリも `TURBO_TELEMETRY_DISABLED=1` で明示的に止める(Vercel Inc. への匿名使用状況送信を避ける、blume・codegraph と同じ「送らない」既定の考え方)
