# レシピ: Python を使う場合のツール選定

原則: [`docs/principles/enforce-with-machines.md`](../../principles/enforce-with-machines.md)(規約は機械で縛る)・[`docs/principles/pin-dependencies.md`](../../principles/pin-dependencies.md)(依存は完全固定)・[`docs/principles/one-command-verification.md`](../../principles/one-command-verification.md)(検証は1コマンド)・[`docs/principles/secrets-by-reference.md`](../../principles/secrets-by-reference.md)(secrets は参照のみ)。このレシピはこれらの原則を Python エコシステムでどう満たすかのカタログであり、原則の内容自体はここに書き写さない。

## 何のためのレシピか

テンプレート本体(`docs/plan/Template/20260807_template-design.md`)は TypeScript の monorepo を前提にしている。しかし ML・データ処理・画像処理のような領域は Python になることが多く、その場合にテンプレートの規律(機械強制・完全 pin・1 コマンド検証・secrets 参照化)を Python 側でどう再現するかをまとめる。

このファイルは「Python を使うサブプロジェクトを作る」と決めた時点で初めて引く前提で書く(§7 コンテキスト予算の on-demand 枠)。**テンプレート本体には Python 用の実体(`pyproject.toml` 等)は同梱しない**。契約層と同じ「レシピは手順の雛形までで、動く例は持たない」という扱いに揃える。

Python を足す場合は、メインのスタックに同居するサブディレクトリ（独自の `pyproject.toml` + 独自の CI ジョブ）として構成する。

## パッケージ管理 / 仮想環境

| ツール     | 何をするか                                                                                   | いつ要るか                                 | テンプレの採否                                                                                                           |
| ---------- | -------------------------------------------------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| **uv**     | 依存解決・仮想環境・Python バージョン管理・lockfile 生成を 1 バイナリで行う(Rust 製、Astral) | Python サブプロジェクトを作る時点で常に    | **採用(既定)**                                                                                                           |
| pip + venv | 標準ツールのみで依存解決と仮想環境を作る                                                     | 外部ツールを一切追加できない制約下のみ     | 未採用。lockfile の標準形式を持たず、依存解決も uv より遅い。原則10(完全 pin)を uv の `uv.lock` ほど機械的に保証できない |
| poetry     | 依存解決・仮想環境・ビルド・PyPI 公開を 1 ツールで担う                                       | 既に poetry で運用中のライブラリを触るとき | 未採用。新規プロジェクトでは uv を優先する。PyPI への正式公開ワークフローが要る場面では再検討の余地を残す                |
| rye        | uv 登場以前に Astral が提供していた一括ツール                                                | (現在は非該当)                             | 未採用。開発元 Astral 自身がリポジトリを archive し read-only 化した。後継は uv であり、選択肢として並べる意味がない     |

**uv を既定にする理由**: 高速な依存解決・仮想環境管理・lockfile 品質に加え、後述の `UV_EXCLUDE_NEWER` が原則10の待機期間をエコシステム標準の設定 1 行で実現できる点が決め手となる。

## アーキテクチャ境界: import-linter

**`pyproject.toml` に layers 契約と forbidden 契約を書くだけで CI ゲートになる。** これは、本テンプレートが TS 側で ts-morph を使って自作している architecture checker(レイヤ依存方向の検査・サードパーティ SDK import の隔離検査)とまったく同じ問題を、設定ファイルだけで解いている。TS 側は「checker 自体を 1 本のプログラムとして実装し、fixture テストを持たせる」というコストを払っているのに対し、Python エコシステムでは import-linter という既製品が同じ役割を宣言的な設定として提供する。

| 項目       | 内容                                                                                                                                                   |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| パッケージ | `import-linter`                                                                                                                                        |
| 契約の種類 | `layers`(上位→下位の一方通行を強制)/ `forbidden`(特定モジュールから特定モジュールへの import を禁止)/ `independence`(モジュール間の相互 import を禁止) |
| 実行       | `lint-imports` コマンド 1 本。CLI が pyproject.toml の `[tool.importlinter]` を読む                                                                    |

**テンプレの採否**: **採用(既定)**。理由は上記の通り、TS 側の自作 checker が解いている問題を設定ファイルだけで解けるため、Python サブプロジェクトに ts-morph 相当の自作ツールを作る必要がない。

**落とし穴**: `include_external_packages = true` を明示しないと、外部パッケージを `forbidden_modules` に指定できない(自プロジェクト内モジュールしか見えない既定動作のため)。

## サプライチェーン: 新規バージョンの待機期間

原則10 の「公開から一定期間(既定 7 日)未満のバージョンは自動採用しない」を、Python エコシステムでは `UV_EXCLUDE_NEWER` 環境変数(または `--exclude-newer` / `pyproject.toml` の `[tool.uv] exclude-newer`)で実現する。

| 項目     | 内容                                                                                                               |
| -------- | ------------------------------------------------------------------------------------------------------------------ |
| 指定形式 | RFC 3339 タイムスタンプ・ローカル日付(`2026-08-01`)・cooldown 形式(`"7 days"` / ISO 8601 duration `P7D`)のいずれか |
| 効果     | 依存解決の対象から、指定日時より後に公開されたディストリビューションを除外する                                     |
| 無効化   | `false` を指定すると exclude-newer 自体を無効化できる(セキュリティ更新の迂回に相当)                                |

**原則10 の背景**: 設計ドキュメント(`docs/plan/Template/20260807_template-design.md` §2「原則10の要件詳細」)が記す「7 日」という既定値は、この `UV_EXCLUDE_NEWER` と、TypeScript 側の Dependabot cooldown 設定が、エコシステムもツールも異なるまま独立に同じ数値へ収斂したことに基づく。

**テンプレの採否**: **採用(既定)**。Python サブプロジェクトの CI には必ず `UV_EXCLUDE_NEWER: "7 days"` を設定する。

## 依存の健全性検出(knip 相当)

| ツール | 何をするか                                                                                                                | いつ要るか                                    | テンプレの採否                     |
| ------ | ------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- | ---------------------------------- |
| deptry | 未使用依存・未宣言依存(import しているが依存に無い)・誤配置(本番コードが dev 依存を使っている)・stdlib の誤宣言を検出する | Python サブプロジェクトの依存が増えてきたとき | **条件付き採用を推奨**。理由は下記 |

テンプレートに Python サブプロジェクトを足す場合、knip と同じ運用方針(検出したら CI を落とす。除外は理由コメント付きで個別に)を deptry にもそのまま適用することを推奨する。

決め手にすべきは**ツールの選定ではなく、選んだ SDK をどう隔離するか**というパターンの方である。

### 合成ルートへの SDK 隔離パターン(採用・既定)

外部 SDK を導入する場合、次の設計パターンを適用する:

- **隔離ファイル**: `composition.py` (合成ルート)
- **SDK import の位置**: 関数内で遅延 import する (`build_tracker` 等の中で `from clearml import Task` など)
- **未指定/未知の値への対応**: 未知の設定値は `ValueError` で fail-fast に落とす (silent fallback 禁止、原則2)
- **機械強制**: import-linter の `forbidden` 契約で `domain` / `ports` から外部 SDK への import を禁止する

**テンプレの採否**: SDK そのもの(ClearML/MLflow/W&B のいずれか)は選ばない。**合成ルート 1 ファイルに SDK import を閉じ、import-linter で機械強制し、未知の設定値は fail-fast にする、というパターンだけを既定にする**。これは `docs/plan/Template/20260807_template-design.md` §3 が言う「サードパーティ SDK / SaaS クライアントの import は合成ルート 1 ファイルに閉じる」の Python 版の具体化であり、TS 側の合成ルート規律と同型である。

## policy-as-test による依存 pin の機械検査

Python コードベースでは、`pyproject.toml` や `tox.toml` の依存指定を `tomllib` で読み込み、正規表現で「完全 pin(`==`)以外」を検出したら `assert unpinned == []` で落とすテストを書くことができる。lint ルールではなく **pytest のテストとして** CI 構造・依存 pin を固定するこの発想は、`docs/plan/Template/20260807_template-design.md` §2「原則4の要件詳細 — policy-as-test」および [`docs/principles/enforce-with-machines.md`](../../principles/enforce-with-machines.md) の具体例そのものである。

## まとめ: このレシピの配線状況

このファイルはカタログであり、**テンプレート本体には Python 用の実体を一切配線しない**(`pyproject.toml` も `.github/workflows/*.yml` の Python ジョブも同梱しない)。Python サブプロジェクトを実際に作る際は、このレシピの「採用」列に従って `pyproject.toml` / `tox.toml` / import-linter 契約 / CI ジョブを新規に書き起こし、`mise.toml` から呼び出す形で configure する。
