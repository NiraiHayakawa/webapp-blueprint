# レシピ: Go を backend に選ぶ場合のツールカタログ

原則: [`docs/principles/enforce-with-machines.md`](../../principles/enforce-with-machines.md)（規約は機械で縛る）/ [`docs/principles/pin-dependencies.md`](../../principles/pin-dependencies.md)（依存は完全 pin）/ [`docs/principles/fail-fast.md`](../../principles/fail-fast.md)（silent fallback 禁止）/ [`docs/principles/test-public-contract-only.md`](../../principles/test-public-contract-only.md)（公開契約のみテスト）/ [`docs/principles/contract-is-ssot.md`](../../principles/contract-is-ssot.md)（契約が単一の真実源）

## 何のためのレシピか

テンプレート本体は TypeScript 前提（`docs/plan/Template/20260807_template-design.md` §3）だが、契約層を protobuf + ConnectRPC で始めた場合（[`contract-layer/protobuf-connectrpc.md`](../contract-layer/protobuf-connectrpc.md)）、backend は Go に逃がす選択肢が構造的に残る。**Go を選んだ瞬間に必要になる周辺ツールをここに集約する。** 選ばない限りこのレシピは読まなくてよい。

Go backend を採用する場合に必要となる周辺ツールと設計判断をここに集約する。

## Go を選ぶ理由・選ばない理由

- **選ばない方がよい既定**: TS で全部書けるなら言語を増やさない方がよい。1 言語構成はツールチェーン・CI・エージェント向け規約（AGENTS.md 階層）を単純に保てる。streaming が無く、backend を他言語に逃がす予定も無いなら TypeSpec → OpenAPI レシピ（TS 完結）を選ぶ方が構造がシンプルになる
- **それでも Go を選ぶ状況**: ① 将来 backend を TypeScript 以外の言語に切り出す道を残したい ② streaming RPC がある(ConnectRPC の bidi/server streaming は Node よりリソース効率が良く、型付き契約との相性も良い) ③ Firestore 等のドキュメント DB に対して型安全なトランザクション処理を書きたい

## 設計方針とツールの位置づけ

このカタログでは、Go backend を採用した際に必要となる linter、formatter、アーキテクチャ検査、エラー処理、テスト、コンテナ化、およびコード生成ツールの推奨構成と設計判断をまとめる。

## lint: golangci-lint

| 項目           | 内容                                                                                                                 |
| -------------- | -------------------------------------------------------------------------------------------------------------------- |
| 何をするか     | 多数の Go linter を束ねて 1 コマンドで実行するメタ linter。v2 系で `modernize`(Go イディオムの現代化提案) も統合済み |
| いつ要るか     | Go backend を書き始めた時点で即導入する。TS の oxlint に相当する必須ゲート                                           |
| テンプレの採否 | 条件付き採用（Go を選んだ場合の既定）                                                                                |

### opt-out 方式である理由（TS とは作法が違う）

Go では `linters.default: all` を宣言し、そこから明示的に `disable` する**opt-out 方式**を採る。これは `docs/plan/Template/20260807_template-design.md` §5 が指摘する通り、**TS 側（oxlint + ultracite preset extends、opt-in 寄りの和集合方式）とは真逆の作法**である。

理由は言語ごとの curated set の性質差にある。golangci-lint の `all` は「有効化して壊れないことが検証された curated set」であり、oxlint のように全カテゴリを機械的に有効化すると両立不能なルールペアが生じる、という問題が Go 側では起きにくい。**「全部有効化してから引き算する」が Go では規約として成立するが、TS では成立しない** — これは片方が優れているという話ではなく、curated set の作り方がエコシステムごとに違うという事実である。

### 意図的に無効化する内部 linter の例とその理由

| linter           | 無効化理由                                                                                                                                                                                                 |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `varnamelen`     | 誤検知過多。`i`/`ok`/`tx` 等の短い慣用変数名まで潰してしまう                                                                                                                                               |
| `wsl` / `wsl_v5` | 非推奨化 + 後継も含め cuddle 系の空行強制が可読性より体裁を優先するため有効化しない                                                                                                                        |
| `gomodguard`     | golangci-lint v2.12 で非推奨化。`depguard` の import boundary ルールで代替（後述）                                                                                                                         |
| `contextcheck`   | 誤検知過多。context 伝播は ast-grep の `context.Background()` 禁止ルールで別途担保                                                                                                                         |
| `err113`         | エラーは `morikuni/failure` でコード分類する設計の場合、静的なセンチネルエラー比較の強制は不要                                                                                                             |
| `misspell`       | コメントが日本語主体で英単語スペルチェックの実益が薄い                                                                                                                                                     |
| `wrapcheck`      | エラーは生成時点で `failure` によりコード分類され、呼び出し元での再ラップを設計上行わない。この設計を `wrapcheck` は区別できないため無効化                                                                 |
| `exhaustruct`    | proto 生成型とサードパーティ Config は非 export な内部フィールドを持ち原理的に全フィールド指定不可能。domain の state machine は未到達状態を zero value で表現する意図的設計の場合など、誤検知になりやすい |
| `gosmopolitan`   | 日本語を扱うアプリケーションで、文字列リテラルに日本語が含まれる場合に誤検知となる                                                                                                                         |
| `ireturn`        | ポートパターン（`app/port` の interface を返すコンストラクタで DI する設計）そのものが検出対象になってしまうため                                                                                           |

**このリストの価値は「無効化した」ことではなく「理由が書いてある」ことにある**（`docs/principles/enforce-with-machines.md` の「抑制には理由を書く」規律）。ルールごと off にするのは「そのルールが設計と構造的に噛み合わない」と説明できるときだけ、という基準を満たしている。理由の無い disable を追加してはならない。

複雑度・認知的複雑度(`gocognit`/`gocyclo`/`cyclop`)は `linters.default: all` の opt-out 方式により既に有効化されている。TypeScript(oxlint)と違い、Go は最初から認知的複雑度の受け皿を持つ。言語横断ツール(codopsy)との役割分担は [`quality-gates.md`](quality-gates.md) 参照。

### 内蔵設定の使いどころ

- `exhaustive.default-signifies-exhaustive: true` — switch の `default:` 節を意図的な catch-all として許容する（未網羅の警告を握り潰すのではなく、default 節の存在自体を「網羅した」の証跡にする）
- `tagliatelle` — YAML フィクスチャが snake_case である命名規約を機械強制
- `exclusions.presets` に `comments` / `std-error-handling` / `common-false-positives` / `legacy` を使う。ゼロから exclusion を書き下ろすより、golangci-lint 公式 preset を土台にする
- テストファイル（`_test.go`）だけ `cyclop` / `gocognit` / `funlen` / `goconst` を除外する（テーブル駆動テストは分岐・行数が自然に増えるため。本番コードは対象外のまま維持）

### depguard: import 境界の第二防衛

`golangci-lint` 内蔵の `depguard` を、後述の go-arch-lint と二重に運用する構成例:

```yaml
depguard:
  rules:
    gen-go-import-boundary:
      list-mode: lax
      files:
        - "$all"
        - "!**/services/api/internal/adapter/connectapi/**"
        - "!**/services/api/httpapi/**"
        - "!**/services/api/cmd/**"
      deny:
        - pkg: "example.com/project/gen/go"
          desc: "gen/go の import は adapter/connectapi・httpapi・cmd に限る。詳細な依存表は go-arch-lint が権威を持つ。これは第二防衛"
```

`go-arch-lint` が依存表の**権威**であり、`depguard` はそれと独立した経路で同じ制約の一部を再確認する二重防衛として機能する。

## アーキテクチャ境界: go-arch-lint

| 項目           | 内容                                                                                                                                     |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 何をするか     | パッケージ間の依存方向を YAML で宣言し、違反を検出するアーキテクチャテスト専用ツール                                                     |
| いつ要るか     | レイヤードアーキテクチャ（domain/app/adapter 等）を Go で組む時点。TS 側の ts-morph 製 architecture checker に相当する Go 版の必須ゲート |
| テンプレの採否 | 条件付き採用（Go でレイヤードアーキテクチャを組む場合の既定）                                                                            |

### 依存表を YAML に 1:1 で書き下ろす

レイヤ依存表を `.go-arch-lint.yml` の `components` / `deps` に定義する。`components` でディレクトリをコンポーネントとして宣言し、`deps.<component>.mayDependOn` で許可する依存先を列挙する。**YAML 側を権威にして文書側は「なぜその表なのか」の理由だけを持つ**という役割分担にする。

自前の vendor ライブラリ（domain 層で許可する `morikuni/failure` 等）は `vendors` セクションで個別に宣言し、`deps.<component>.canUse` で明示的に許可する。ワイルドカードで「なんでも許可」にしないのが要点。

### 運用知見

- **`allow.deepScan: false`**: go-arch-lint の deep scan（メソッド呼び出し・DI value-flow まで見る解析）は、コンストラクタ注入の配線層（`cmd/`）が driven adapter を app 層のコンストラクタに渡すだけの操作を、あたかも adapter 自体が app に依存しているかのように誤検知することがある。deep scan を明示的に off にし、base の import-path チェックを基本とする
- **`excludeFiles: [".*_test\\.go$"]`**: テストファイルは httptest 等での blackbox 検証のためレイヤを正当に横断するので、アーキテクチャルールは本番コードだけを対象にする
- **driving adapter の例外を明示的に許可する**: driving adapter（Connect ハンドラ）が use case の具象型を直接呼ぶ構成を許容する場合がある。例外を作る場合は YAML のコメントで「なぜこの component だけ緩いか」を明示する

## プロジェクト固有ルール: ast-grep

| 項目           | 内容                                                                                                                                                            |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 何をするか     | AST パターンマッチによる静的解析。tree-sitter ベースで多言語対応                                                                                                |
| いつ要るか     | golangci-lint の汎用ルールでは表現できない、プロジェクト固有の禁止パターン（特定関数の直接呼び出し禁止、特定シグネチャの引数禁止 等）を機械強制したくなった時点 |
| テンプレの採否 | 条件付き採用（Go でも TS と同じ仕組みが使える）                                                                                                                 |

**Go は ast-grep が tree-sitter ビルトインサポートを持つ言語であり、TS で書くルールと全く同じ YAML 構文（`language: go` に変えるだけ）でプロジェクト固有ルールを書ける。** 新しい言語ランタイムやパーサ導入が要らないため、「TS では ast-grep を使っているが Go でも同じ運用ができるか」を心配する必要が無い。

プロジェクト固有ルールの例（`rules/go/*.yml`）:

| ルール                              | 意図                                                                                                                                                        |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `no-context-background-outside-cmd` | `context.Background()` を `cmd/` とテスト以外で禁止。受信リクエストの context を伝播させ、trace 伝播の前提を守る                                            |
| `no-firestore-update`               | Firestore の `.Update(` を `adapter/store/**` で禁止。ドキュメント不存在時に `NOT_FOUND` でコミット全体が失敗するため。`Set(..., MergeAll)` を使う          |
| `no-os-getenv-outside-config`       | `os.Getenv` を `internal/config` 以外で禁止。環境変数の読み込みと必須検証を 1 箇所に集約し、デフォルト値 fallback を構造的に禁止する                        |
| `no-raw-error-construction`         | `fmt.Errorf` / `errors.New` の直書きを domain/app/adapter で禁止。エラーは `failure.New` 等のコード付き生成のみ許可                                         |
| `no-store-string-uid`               | `adapter/store/**` の関数が生の `string` 型 `uid` 引数を受け取ることを禁止。`auth.VerifiedUID` / `authz.Grant` を経由しない認可バイパスを型で防ぐ最終防衛線 |
| `no-time-now-outside-clock`         | `time.Now()` の直接呼び出しを禁止。テスト可能性のため、時刻は注入経路（`clock` を名前に含むファイル以外全面禁止）経由でのみ取得させる                       |

いずれも `selector: call_expression` や `parameter_declaration` に `context:` で最小の Go スニペットを与えるパターンで、`files:` / `ignores:` で適用範囲を絞り込む。TS 側の ast-grep ルールと同じ書き方の流儀がそのまま通用する。

## エラー処理: morikuni/failure / cockroachdb/errors / 標準 errors

### morikuni/failure

| 項目           | 内容                                                                                                                                                                                                       |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 何をするか     | エラーにコード（`errcode.Code` 相当）を紐付けて生成・伝播するための依存ゼロの薄いライブラリ。`failure.New` / `failure.Translate` / `failure.Wrap` / `failure.Unexpected` の 4 パターンで生成手段を統一する |
| いつ要るか     | エラーの「種類」を呼び出し元が分岐したい場合（HTTP/RPC ステータスへの変換、ログのレベル分けなど）で、`errors.Is`/`errors.As` によるセンチネルエラー比較より、コードによる分類を一元管理したい場合          |
| テンプレの採否 | 条件付き採用（Go を選んだ場合の既定候補）                                                                                                                                                                  |

**エラーコード registry という考え方**: `internal/domain/errcode` に全エラーコードを一元管理する。特定ドメインに紐付けず、API 全体で共有する 1 つのレジストリにする。`Code` 型は `type Code string` + `ErrorCode() string` メソッドだけで `failure.Code` インターフェースを構造的に満たし、値は UPPER_SNAKE で AIP-193 の `ErrorInfo.reason` 制約(`^[A-Z][A-Z0-9_]+[A-Z0-9]$`)を満たす。**「エラーの種類」を型として持ち、契約(google.rpc.ErrorInfo)にまでその語彙を一貫して流す**設計である。

**既知リスク**: `morikuni/failure` は最終コミットが古く事実上メンテ停止状態(v2 は rc のまま停止)。ただし依存ゼロ・小規模で枯れているため、壊れた場合は同一 API の自前 thin wrapper(~100 行)に差し替える退避経路を確保しておく。

### cockroachdb/errors

| 項目           | 内容                                                                                                                             |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 何をするか     | スタックトレース・PII 分離・network-portable なエラーエンコーディング等、高機能なエラーライブラリ                                |
| いつ要るか     | 分散システムでエラーをプロセス間で受け渡す必要がある、詳細なスタックトレースが常に要る、といった大規模運用に踏み込んだ場合       |
| テンプレの採否 | 未採用。理由: 「高機能だが重量級。エラーコード + Wrap という要件には `failure`(または自前 wrapper)で足りる」。小規模には式典過剰 |

### 標準 errors

| 項目           | 内容                                                                                                                                                                   |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 何をするか     | Go 標準ライブラリの `errors` パッケージ(`errors.New` / `errors.Is` / `errors.As` / `errors.Join`)                                                                      |
| いつ要るか     | エラーコードによる分類が要らない、ごく単純な CLI ツールや使い捨てスクリプトなど、レイヤ分割の要らない小規模な Go コード                                                |
| テンプレの採否 | 条件付き採用。**レイヤードアーキテクチャを組む場合は `morikuni/failure` 等のコード付きエラーに一本化し、標準 `errors` の直接使用は配線層に限定する**という境界線を推奨 |

## DI: 手組み / google/wire / uber-fx

### 手組み(constructor injection)

| 項目           | 内容                                                                                                                   |
| -------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 何をするか     | DI コンテナやコード生成を使わず、`cmd/` の `main`/`run` 関数でコンストラクタを手で呼んでオブジェクトグラフを組み立てる |
| いつ要るか     | 常時。これを既定にする                                                                                                 |
| テンプレの採否 | **採用(既定)**                                                                                                         |

**手組みを既定にする理由**: 「フル DDD/4 層以上」「DI コンテナ」のような追加抽象は小規模〜中規模では式典が多すぎる。`.go-arch-lint.yml` も `cmd:` コンポーネントだけを `anyProjectDeps: true` で無制限にし、**配線がどこで起きるかを 1 箇所に固定する**ことでコンテナ抽象なしでも見通しを保てる。オブジェクトグラフが小さいうちは、DI コンテナが解決する「配線の自動化」自体が不要である。

### google/wire

| 項目           | 内容                                                                                                                           |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 何をするか     | コンパイル時コード生成による DI。`wire.Build` で依存グラフを宣言し、`wire_gen.go` を生成する                                   |
| いつ要るか     | コンストラクタの数が数十を超え、手組みの配線コードそのものが可読性を失った場合。生成コードなのでランタイムオーバーヘッドが無い |
| テンプレの採否 | 未採用。**コンストラクタが増えて手組みが辛くなった時点で初めて検討する退避先**として記録しておく                               |

### uber-go/fx

| 項目           | 内容                                                                                                                                           |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 何をするか     | リフレクションベースのランタイム DI。ライフサイクルフック(起動/終了処理)込みのアプリケーションフレームワーク寄り                               |
| いつ要るか     | 複数の長時間稼働コンポーネント(バックグラウンドワーカー等)を持ち、起動順序とグレースフルシャットダウンを DI フレームワークに任せたい大規模構成 |
| テンプレの採否 | 未採用。google/wire よりさらにフレームワーク色が強く、手組みで足りる規模を超えたとしても、まず wire を検討する方が既存設計との差分が小さい     |

## コンテナ化: ko / 素の multi-stage Dockerfile

### ko

| 項目           | 内容                                                                                                                         |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 何をするか     | Dockerfile を書かずに Go バイナリを直接コンテナイメージ化するツール。distroless ベースイメージに Go バイナリだけを詰める     |
| いつ要るか     | Go backend を Cloud Run 等のコンテナランタイムにデプロイする時点。ビルドステージを持つ Dockerfile を自前で保守したくない場合 |
| テンプレの採否 | 条件付き採用(Go backend を実際にコンテナデプロイする段階になったら配線する)。Dockerfile を持たず純 Go イメージを保てる       |

### 素の multi-stage Dockerfile

| 項目           | 内容                                                                                                                             |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 何をするか     | `FROM golang:X AS build` でビルドし、`FROM gcr.io/distroless/static` 等の軽量イメージにバイナリだけをコピーする、素の Dockerfile |
| いつ要るか     | ko が対応しない要件(Go 以外のファイルをイメージに含める、ビルド時に追加のシステムパッケージが要る 等)が出た場合の退避先          |
| テンプレの採否 | 未採用(ko を優先する)。ko で表現できない要件が出た時点でのみ検討する                                                             |

## 脆弱性: govulncheck

| 項目           | 内容                                                                                                                                                                                                                |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 何をするか     | Go 公式の脆弱性スキャナ。既知脆弱性のあるパッケージを import しているだけでなく、**その脆弱な関数に実際に到達するコールパスがあるか**まで解析する到達性ベースの検査(単純な依存リストの脆弱性突合より偽陽性が少ない) |
| いつ要るか     | Go の依存を持つ時点で CI に入れる。TS 側の `pnpm audit`/Dependabot alerts に相当する必須ゲート                                                                                                                      |
| テンプレの採否 | 条件付き採用。ツール自体は Go 公式・無料・到達性ベースで偽陽性が少なく、採用理由(到達性ベース)は正当。採用時は `mise.toml` への追加と CI ステップの実装を伴わせる                                                   |

## API: api-linter / buf / protoc-gen-go / protoc-gen-connect-go

| 項目           | 内容                                                                                                                                                                                                                                                                                                                   |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 何をするか     | `api-linter` は Google AIP(API Improvement Proposals)準拠をチェックする静的解析。`buf` は protobuf のビルド・lint・breaking change 検出・codegen オーケストレーション。`protoc-gen-go`/`protoc-gen-connect-go` はそれぞれ protobuf メッセージ型と ConnectRPC のハンドラ/クライアントコードを生成する protoc プラグイン |
| いつ要るか     | 契約層に protobuf + ConnectRPC を選んだ時点(`contract-layer/protobuf-connectrpc.md` 参照)。Go 側の実装コードを生成する経路がこの 4 点セット                                                                                                                                                                            |
| テンプレの採否 | **採用**(protobuf + ConnectRPC レシピを選んだ場合の必須構成要素。TS 側の `contract-layer/protobuf-connectrpc.md` が持つ `@bufbuild/buf` 等の TS 生成系と対になる Go 生成系)                                                                                                                                            |

`api-linter.yaml` では、ConnectRPC が POST 固定である以上不要な HTTP transcoding アノテーション検査(`core::0127`)や、言語別 file option 検査(`core::0191`。buf managed mode が一元管理するため)を無効化する。無効化には理由コメントを付与する。

## ランタイム: Go のバージョン管理(mise)

| 項目           | 内容                                                                                                                                                                                      |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 何をするか     | `mise.toml` の `[tools]` に `go = "X.Y.Z"` と書くだけで、そのバージョンの Go ツールチェーンを `mise install` 一発で用意する                                                               |
| いつ要るか     | Go を使う時点で常に。`docs/plan/Template/20260807_template-design.md` §5 が定める「`mise.toml` を唯一のタスク正本とする」方針の延長で、言語ランタイムのバージョン管理も mise に一元化する |
| テンプレの採否 | **採用**。テンプレート本体がすでに mise を唯一のタスク正本にしているため、Go を追加する場合も同じ `mise.toml` に go/golangci-lint 等の行を足すだけで一貫性が保たれる                      |
