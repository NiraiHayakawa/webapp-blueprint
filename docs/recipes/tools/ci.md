# ツールカタログ: CI を組む場合

原則: [`docs/principles/one-command-verification.md`](../../principles/one-command-verification.md)（検証は1コマンド）、[`docs/principles/pin-dependencies.md`](../../principles/pin-dependencies.md)（依存は完全固定する）、[`docs/principles/enforce-with-machines.md`](../../principles/enforce-with-machines.md)（抑制には理由を書く・規約のメタテスト）

このファイルは `docs/plan/Template/20260807_template-design.md` §7「コンテキスト予算」が言う on-demand 枠に置くカタログである。CI ワークフローを新設・変更するタスクに着手する前に読む。**採用していないツールも含めて選択肢を網羅し、「検討したか」を毎回調べ直さないことが目的。**

## 1. workflow lint: actionlint / ghalint

| ツール         | 何をするか                                                                                                                                                                                                                                                                 | いつ要るか                                                                                                                                                                 | テンプレの採否                                                                                                                                                                                                                                                                                                 |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **actionlint** | `.github/workflows/*.yml` の構文・型（`${{ }}` 式の型不整合・存在しないコンテキスト参照等）を静的検査する                                                                                                                                                                  | `.github/workflows/` を書き始めた時点                                                                                                                                      | **採用**（`mise.toml` に `actionlint = "1.7.12"` pin 済み。`mise run check:workflows` から呼び、`check` にも含める。下記「actionlint が pin されているだけで呼ばれていなかった穴」参照）                                                                                                                       |
| **ghalint**    | ワークフロー・composite action の**セキュリティポリシー**準拠を検査する（job の permissions 最小化・action 参照のフル SHA pin 強制・タイムアウト必須化等、2026-08-08 に GitHub 公式リポジトリで確認した限りでは 12 種類のワークフローポリシーと 5 種類の action ポリシー） | actionlint がカバーしない**セキュリティ**観点（過剰な `permissions`・タグ参照の action 等）まで機械強制したくなった時点。actionlint は構文・型の検査であり守備範囲が異なる | 未採用。actionlint と役割が重複しないため排他的な選択ではないが、本テンプレートの CI は permissions を各 job で明示的に絞る運用を手で行っており（`ci.yml` の `permissions: contents: read`）、機械強制の必要性が今のところ顕在化していない。導入条件は「permissions の絞り込み漏れが実際に事故を起こしたとき」 |

### 例: actionlint のバージョンが新しい YAML 構文に追従できないケース

`.github/actionlint.yaml` の設定例:

```yaml
# actionlint 1.7.12 predates the parallel-step keys GitHub shipped on
# 2026-06-25 and rejects them as unknown step keys. Scoped to the one workflow
# that uses them so every other workflow still gets a real malformed-step check.
paths:
  .github/workflows/ci.yml:
    ignore:
      - 'step must run script with "run" section or run action with "uses" section'
```

GitHub Actions の構文は継続的に追加されており、外部ツール（actionlint）の追従が追いつかず、特定ファイルだけルールを無効化する事態が起きる。**この抑制は理由つきであり、原則4「抑制には理由を書く」を満たす正しい形の一例である。** ただし「そもそも外部ツールへの追従コストが構造的に発生する」こと自体は避けられない — バージョンを上げれば直る類の抑制ではなく、GitHub 側の仕様追加が続く限り再発しうる。

### actionlint が pin されているだけで呼ばれていなかった穴

`mise.toml` の `[tools]` に `actionlint = "1.7.12"` が pin されていたにもかかわらず、それを呼ぶ mise task が存在せず、`.github/workflows/*.yml` の lint が一度も走っていなかった事例があった。原則4（機械強制）と原則8（検証は1コマンド）の両方に対する穴であり、**`[tools]` に pin されているだけで呼ぶ task が無いツールは、存在しないのと同じ**という教訓を残す。`mise.toml` に `[tasks."check:workflows"]`（`run = "actionlint"`。引数無しで最も近い `.github/workflows` を自動検出する）を追加し、`check` の依存にも含めて塞いでいる。

## 2. workflow のローカル実行: act / actrun

**両方とも「採らない」。** 理由は導入コストではなく、**外部ツールの追従コストが構造的に高いこと**にある。GitHub Actions の構文は継続的に追加されており（上記 actionlint の実例が示すとおり）、ワークフローの意味を丸ごとローカルで再現しようとするツールほど乖離の影響を強く受ける。actionlint のような静的検査は「知らない構文を見逃す/エラーにする」で済むが、ローカル実行系は「実行できない」という致命的な失敗になる。

| ツール                      | 何をするか                                                                                                | テンプレの採否                                                                    |
| --------------------------- | --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| **act**（nektos/act）       | Docker コンテナ上で GitHub Actions ワークフローをローカル実行する、最も広く使われているローカル実行ツール | **不採用**                                                                        |
| **actrun**（mizchi/actrun） | GitHub Actions 互換のローカルランナー。gh 互換 CLI でワークフローを実行・デバッグする                     | **不採用**（act と同じ理由：GitHub Actions の全構文への追従コストが構造的に高い） |

### actrun で生じる追従コストの課題

ローカルランナーは GitHub Actions の全構文（`workflow_dispatch` 専用ワークフローや新しいマトリクス構文等）に対応しきれない場合があり、ワークフローの種類によってツールを使い分けたり回避策が必要になることがある。ローカル実行系に過度に依存せず、別の手段で品質を担保する。

### 代わりに何で担保するか

1. **policy-as-test による workflow 構造の検証**（`tests/policy/`）。CI の構造（ゲートジョブの存在・`needs` による依存）はワークフロー YAML を解析するテストとして固定し、ローカル実行で「動くかどうか」を確認する代わりに「構造が正しいか」を機械的に検査する
2. **集約ジョブ**（`ci-required`）。個々のジョブをローカルで再現するのではなく、CI 上で集約ジョブが全ジョブの成否を判定する構造そのものをテストする
3. **実際に PR を出して回す**。ワークフローの実行結果そのものを確認したい場合、ローカル実行系で近似するのではなく、実際に GitHub Actions 上で実行して確認する。乖離のリスクを引き受けるより、実行環境そのもので確認する方が確実

## 3. 依存更新: Dependabot / Renovate

原則: [`docs/principles/pin-dependencies.md`](../../principles/pin-dependencies.md) 要件②（新規公開バージョンの待機期間、既定 7 日）

両者とも「公開から一定期間未満のバージョンを採用しない」設定を持つが、**設定名が異なる**。

| ツール         | 該当設定                                                                                   | 挙動                                                                                                                                                                            |
| -------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Dependabot** | `cooldown`（`default-days` / `semver-major-days` 等のサブフィールドを持つ）                | バージョン更新にのみ適用（セキュリティ更新には適用されない）。明示設定しなくても既定で 3 日のクールダウンが働く。`include` / `exclude` で対象パッケージを絞れる                 |
| **Renovate**   | `minimumReleaseAge`（旧称 `stabilityDays`。2026-08-08 に Renovate 公式ドキュメントで確認） | 「公開から X 経過していないパッケージの branch/PR 作成を抑制する」という文言で説明されている。設定名が変わった経緯があるため、古い記事の `stabilityDays` 表記に惑わされないこと |

**テンプレの採否**: Dependabot を採用（`docs/principles/pin-dependencies.md` の既定値 7 日は、Dependabot の `cooldown` と uv の `UV_EXCLUDE_NEWER` という独立した 2 つのパッケージ管理ツールが同じ値に収束した一貫性を根拠にしている。Renovate の `minimumReleaseAge` も同じ値を設定できるため、Renovate を選ぶこと自体は原則に反しない。乗り換える場合は `cooldown` の各フィールドを `minimumReleaseAge` の対応する粒度設定に読み替える）。

**もう 1 つの待機期間の実装**: `mise.toml` の `[settings] minimum_release_age = "7d"` は、Dependabot/Renovate が扱う**アプリケーション依存**とは別に、mise が管理する**ツールチェーン自体のバージョン**（node / pnpm / actionlint 等）に同じ 7 日待機を適用する。3 つ目の異なる仕組みが同じ「7 日」という値に収束している。

## 4. 脆弱性 / SAST: CodeQL / govulncheck / secretlint / gitleaks / trivy

| ツール          | 対象                                                           | テンプレの採否                                                                                                                                                                                                                                                                                                    |
| --------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **CodeQL**      | ソースコードの意味解析による脆弱性検出（GitHub 公式）          | **CLI をローカルで採用、CI ワークフローは不採用**（CodeQL はローカル CLI タスク（`mise run check:codeql`）として提供し、実行の重さから既定の高速な `check` タスクからは分離している。public リポジトリでは必要に応じて GitHub ホストの Code Scanning を Actions 経由で有効化できる。詳細は下記「CodeQL の配線」） |
| **govulncheck** | Go の既知脆弱性データベースと依存関係を突き合わせる（Go 公式） | 未採用・未検討。Go をバックエンドに選ぶプロジェクトでの候補として記録                                                                                                                                                                                                                                             |
| **secretlint**  | リポジトリ全体を対象にした秘密の実値スキャン                   | **採用**（原則9の機械強制の受け皿。テンプレートの `.secretlintrc.json` / `mise run check:secrets` に実装済み）                                                                                                                                                                                                    |
| **gitleaks**    | secretlint と同種の秘密スキャン（Go 製、独立ツール）           | 未採用。secretlint と役割が重複するため、両方入れる積極的な理由がない限り 1 本化する。                                                                                                                                                                                                                            |
| **trivy**       | コンテナイメージ・IaC・依存関係の脆弱性を横断スキャンする      | **採用**（`trivy.yaml` / `.trivyignore` / `mise.toml` の `[tasks."check:vulnerabilities"]`。対象は依存(SCA。`pnpm-lock.yaml`)と Terraform 設定ミス(`infra/`)のみに絞る。コンテナイメージはビルドしないため対象外、秘密スキャンは secretlint と重複するため明示的に無効化した。詳細は下記「Trivy の配線」）        |

### secretlint / CodeQL / Trivy の守備範囲の違い

3者は同じ「セキュリティ関連のゲート」という括りに見えるが、担当する軸が異なり、互いに重ならない。

| ツール     | 見るもの                                                                                                                          | 見ないもの                           |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| secretlint | **秘密の混入**（API キー・トークン等の実値がリポジトリに紛れ込むこと）                                                            | コードの欠陥・依存の脆弱性           |
| CodeQL     | **コードの欠陥**（SQL インジェクション・パストラバーサル・安全でない deserialization 等、ソースコードの意味解析で見つかる脆弱性） | 秘密の実値・依存パッケージの脆弱性   |
| Trivy      | **依存の既知脆弱性**（`pnpm-lock.yaml` に固定されたバージョンに CVE が付いていないか）と Terraform の設定ミス                     | 秘密の実値・自分で書いたコードの欠陥 |

### 原則10「依存 pin」との関係

原則10の pin + cooldown（新規公開から7日待つ）は「**新しすぎるものを入れない**」ための仕組みである。これは「**入れたものが後から脆弱と判明する**」ことには効かない — むしろ完全 pin しているぶん、対策を挟まなければ古い脆弱なバージョンに固定され続ける。Trivy はこの逆方向（pin した後に脆弱と判明したもの）を埋める補完関係にある。両者は「採用前」と「採用後」で時間軸が逆であり、片方だけでは依存の健全性を保てない。

### CodeQL の配線と位置づけ

CodeQL はソースコードの意味解析による脆弱性検出（SQL インジェクション・パストラバーサル等）を行う静的解析エンジンである。

本テンプレートでは、CodeQL を**ローカル CLI タスク（`mise run check:codeql`）として提供し、実行の重さから既定の高速な `check` タスクからは分離している**。CI の既定ワークフローにも CodeQL ジョブは配置していない。

- **実行の重さによる分離**: データベース作成と意味解析はコードベースの規模に応じて時間を要するため、日常的に叩く `mise run check` や高速な PR ゲートからは外し、独立した検証タスクとして定義している
- **ローカルでの実行**: `mise run check:codeql` で手元で実行可能。データベース作成と SARIF 解析を行い、結果をテンポラリディレクトリに出力する
- **public リポジトリでの利用**: public リポジトリでは GitHub ホストの Code Scanning を無償で利用できるため、必要に応じて `.github/workflows/codeql.yml`（言語 `javascript-typescript`、クエリセット `security-extended`）を追加して Actions 上で定期実行・PR 検査を回す運用に拡張できる

### CodeQL のローカル実行手順

`mise run check:codeql` がローカルにおける CodeQL の実行経路となる。

- **CLI 本体の入手**: mise の central registry に登録済み。`mise.toml` の `[tools]` に `codeql = "2.26.2"` として exact pin されている
- **クエリパックのダウンロード**: `codeql/javascript-queries`(`security-extended` スイートを含む)は `codeql database analyze` の初回実行時に自動ダウンロードされ、`~/.codeql/packages` にキャッシュされる（要ネットワーク）
- **実行結果の出力**: データベースおよび SARIF は `mktemp -d` で作成した一時作業ディレクトリに出力されるため、リポジトリを汚さない
- **ローカル実行コマンド**:
  ```bash
  mise run check:codeql
  ```

### Trivy の配線

- バージョン: `0.72.0`（exact pin）
- スキャン対象: `vuln`(依存。`pnpm-lock.yaml`)+ `misconfig`(Terraform。`infra/` のみに `misconfig-scanners` を絞る)。コンテナイメージ・秘密はスキャンしない(前者はビルドしないため対象が無い、後者は secretlint と重複する)
- `--include-dev-deps` が必須: 本リポジトリは全ワークスペースが devDependencies のみのため、このフラグが無いと全パッケージが除外され「対象ゼロで緑」になる。設定ファイル(`trivy.yaml`)経由では反映されないため CLI フラグで渡す
- しきい値: `HIGH,CRITICAL`
- `mise run check` には含めない。脆弱性 DB(約100MB)のダウンロードにネットワークが必要で、オフラインだと fail-fast で落ちるため。CI 専用ジョブ(`ci.yml` の `check-vulnerabilities`)として配線し、こちらは `ci-required` の判定対象に含める
- 抑制の管理: `.trivyignore` に CVE 単位で理由つき抑制として記録する(原則4)

## 5. キャッシュ: actions/cache / turbo のローカルキャッシュ

| 方式                               | 何をするか                                                                                             | テンプレの採否                                                                                                                                                                                                         |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **actions/cache**                  | GitHub Actions のジョブ間でファイル（`node_modules` 等）をキャッシュする汎用アクション                 | 未採用。本テンプレートは CI を全実行に固定しており（§4「差分実行」参照）、キャッシュ層より先に検証すべきはタスク自体の要否                                                                                             |
| **Turborepo のローカルキャッシュ** | パッケージ単位の入力追跡キャッシュ（変更のないパッケージの `typecheck`/`test`/`build` を再実行しない） | **採用**（`turbo.jsonc`）。ただし**リモートキャッシュは使わない**（`remoteCache.enabled = false` を明示。個人利用が前提で、複数開発者間のキャッシュ共有が要らないため。既定値への暗黙依存を避ける原則4の実践でもある） |

**リモートキャッシュを採らない理由**: Turborepo のリモートキャッシュは複数開発者・複数 CI 実行間でキャッシュを共有する仕組みだが、共有先（Vercel のリモートキャッシュサービス等）への依存を増やし、個人利用が前提の本テンプレートでは恩恵よりも「意図しない外部通信」のリスクが上回る。`mise.toml` が `TURBO_TELEMETRY_DISABLED = "1"` を明示しているのも同じ判断（匿名テレメトリという意図しない外部通信を止める）の一貫である。

## 6. 差分実行: paths-filter / turbo の affected / 自前スクリプト

**テンプレは全実行が既定。** 差分実行への移行は既存レシピ [`docs/recipes/affected-ci.md`](../affected-ci.md) に手順がある。移行トリガー（**CI 所要 10 分超え**）を満たした場合にのみ検討する。差分検出のバグは検査漏れに直結するため、速いうちからこのリスクを背負わない、という判断は `docs/plan/Template/20260807_template-design.md` §5「CI の実行範囲」を正本とする。

| ツール                                             | 何をするか                                                           | テンプレの採否                                                                                                               |
| -------------------------------------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `dorny/paths-filter`                               | 変更されたパスに基づいて後続ジョブの実行要否を判定する GitHub Action | 未採用（個々の workflow で `paths:` フィルタを直接使う構成を基本とする）                                                     |
| Turborepo の affected 実行                         | ワークスペースの依存グラフから影響パッケージを算出する               | 未採用（退避先候補として記録）                                                                                               |
| 自前スクリプト（`resolve-affected-apps` パターン） | マージコミットの第 1 親を基点に影響ワークスペースを算出する          | **条件付き採用**（CI 所要が 10 分を超えた場合のレシピとして用意）。詳細は [`docs/recipes/affected-ci.md`](../affected-ci.md) |

## 7. PR 自動レビュー: Claude Code Action / Codex Cloud

詳細設計（diff SHA256 による重複抑止・delta/full mode の切替・marker upsert・未解決スレッドの一括 resolve 等）は `docs/plan/Template/20260807_template-design.md` §6「PR 自動レビュー」に既にあるため、ここでは重複させない。このカタログで書くのは要件の骨子だけ。

| 要件                             | 何を指すか                                                                                                                                                         |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **重複抑止**                     | 同一 diff（コミット SHA 等）への重複レビューを、隠しコメントに埋めたハッシュで検出して抑止する                                                                     |
| **sensitive path 判定**          | 変更行数・新規ファイル・sensitive path（auth / migrations / infra / workflows）で delta mode と full mode を切り替え、sensitive path があれば full mode を強制する |
| **実行の機械検証**               | レビュー実行後に「ターン数が 0 でないこと」「要約マーカーが実際に投稿されたこと」を検証し、空振りのまま緑になることを防ぐ                                          |
| **bot イベントからの再発火許可** | 自 workflow が作ったコミットで次のレビューが止まらないよう、bot が起こしたイベントでも発火できる許可リストを持つ                                                   |

Claude と Codex の 2 系統を `.github/workflows/pr-review-claude.yml` / `pr-review-codex.yml` として実装済み。テンプレートはこの 2 ファイルを同梱するが、**有効化には各プロジェクトでの認証情報の設定が必要**（README に明記する前提）。

## 8. reusable workflow: deploy / preview / cleanup の 1 本化

deploy / preview / cleanup を reusable workflow 1 本にまとめ、各アプリは path フィルタと入力だけの薄いラッパーにするパターンは [`docs/recipes/preview-environments.md`](../preview-environments.md) に既に記録済み。重複させずリンクのみ置く。
