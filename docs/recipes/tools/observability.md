### canonical work observer の設計

`observe(context, work)` / `observeResult(context, work, classify)` という関数が処理単位そのものを包み、内部で例外が起きても起きなくても、包んだ関数を抜ける時点で構造化された記録を 1 本だけ出す。テストは記録が複数本に分裂しないことを直接検証している。シリアライザは安全なフィールドしか生成しない実装になっており、生の例外オブジェクトの `cause` のような任意のプロパティを構造体にそのまま含めない。加えて禁止キー(`apikey` / `authorization` / `cookie` / `prompt` / `completion` / `secret` / `token` / `credential` / `signedurl` / `headers` 等)を検出したら、マスキングして続けるのではなく throw する。**この 2 層(安全なフィールドしか作らない生成 + 禁止パターンの事後検査)が、原則 4・5 の機械強制の受け皿を実装レベルでどう満たすかの一次資料である。**

## 3. 送り先(クラウド選定に従属)

送り先を選ぶための**判断材料**を先に示す(3.1〜3.4)。手順(どう設定してどう起動するか)はここには書かない — 差し替え点は合成ルート(`apps/api/src/composition.ts`)のコメントが唯一の場所として持っており、選ぶための判断だけをここに置く。**空スロットにするのは exporter(送り先)だけである(2026-08-09 改訂)。** API/SDK 本体は前節のとおり常時ロードして配線済みであり、空スロットの対象ではない。選定はプロジェクト開始時の ADR に委ね、テンプレート本体には特定の送り先を配線しない。既定は開発向けの `ConsoleSpanExporter`(合成ルートが選ぶ唯一の場所。「6. 実体層の配線」参照)。

候補は SaaS 4 種(Cloud Trace / Honeycomb / Datadog / Grafana Cloud)と自己ホストの OTLP + Jaeger。Sentry は送り先ではなくエラー追跡 SaaS のため「5. エラー追跡 SaaS」で別途扱う。

### 3.2 サンプリング: head か tail か、tail なら collector が要るか

トレースを全量送ると量に比例して課金が増えるため、量を減らす手段としてサンプリングを検討する。**head サンプリング**(リクエスト受信時にクライアント側で決める)はどの送り先でも OTel SDK で完結するが、**tail サンプリング**(処理が終わってから遅延・エラーの有無で残す/捨てるを決める)は「誰が」その判断をするかで構成が変わる。

| 送り先                        | head サンプリング                 | tail サンプリング                                                                                                                                                                                                                                                     | tail の実行場所                                                                                              |
| ----------------------------- | --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **Cloud Trace**               | 対応                              | **非対応**。公式ドキュメント: "Cloud Trace doesn't support tail-based sampling"                                                                                                                                                                                       | 該当なし。tail が要るなら自前で OpenTelemetry Collector + tail-sampling processor を構成し、判断後に転送する |
| **Honeycomb**                 | 対応                              | 対応(Refinery)                                                                                                                                                                                                                                                        | **顧客側が Refinery を自己ホスト**・運用する。Honeycomb の取り込みサービスに内蔵されたマネージド機能ではない |
| **Datadog**                   | 対応(Agent がレートを SDK へ配信) | Retention Filters / Intelligent Retention Filter で取り込み後に選別。ドキュメントの文言("after spans have been ingested")からサーバー側処理と読めるが、明示的に断定した記述は無く**未確認**。OTel Collector の Tail Sampling Processor を使う経路も別途案内されている | 一部サーバー側(未確定)。OTLP 経由で自前構成する場合は顧客側                                                  |
| **Grafana Cloud(Tempo)**      | 対応                              | 対応。Tempo 自体は原則全件を安価に保存する設計で、tail サンプリングは Grafana Alloy か OpenTelemetry Collector という別コンポーネントが担う。マネージドの "Adaptive Traces" という tail sampling 機能もある(契約条件は**未確認**)                                     | 自前 collector、または Grafana 管理の Adaptive Traces(詳細未確認)                                            |
| **OTLP + Jaeger(自己ホスト)** | 対応(SDK 側)                      | 対応可能(自前で OTel Collector を足す)                                                                                                                                                                                                                                | 顧客側。もとから自己ホストのため、collector を足すこと自体の構成変更は他候補より小さい                       |

**いつ効くか**: トレース量が多く保持コストが問題になった段階で tail サンプリングを検討する。**tail サンプリングを自前で持つ場合、collector という追加コンポーネントの運用が要る**(Cloud Trace・Honeycomb・Grafana Cloud の自前構成が共通してこの形。Datadog はサーバー側で完結する可能性があるが未確定)。「まず head サンプリングだけで様子を見る」を既定にし、tail が要ると分かった時点で構成(collector を増やすか、マネージドの tail サンプリング機能に乗るか)を選び直すのが妥当な順序になる。

### 3.3 ベンダーロックインの度合い: OTLP で出しておけば送り先を変えても計装は無傷

4 者とも OTLP を直接受け付けるが、**「OTLP を受け付ける」ことと「OTLP だけで全機能が完結する」ことは別**であり、ここに度合いの差がある。

- **Cloud Trace**: OTLP のみで完結。ネイティブ OTLP エンドポイント(`telemetry.googleapis.com`)を持ち、Google 固有のエージェントは不要
- **Honeycomb**: OTLP ネイティブが訴求点そのもの("no vendor lock-in" を明言。OTel 本体へのコントリビュート実績も公言)
- **Datadog**: OTLP の直接送信(intake endpoint)は可能だが、「メタデータ強化・シグナル正規化・集中サンプリング」等は Agent/Collector 経由でないと得られないとドキュメントが明記している。dd-trace SDK との完全な機能パリティの有無は明示的な比較記述が見つからず**未確認**
- **Grafana Cloud(Tempo)**: ストレージ(オブジェクトストレージ + Parquet)はポータブルなオープンフォーマットだが、クエリ言語 TraceQL は Grafana 独自仕様。移行時はクエリ資産の書き換えが発生する
- **OTLP + Jaeger(自己ホスト)**: ロックインという概念自体が無い(OSS を自分で運用する)。その代わり運用の全責任を自分が持つ

**いつ効くか**: 「将来送り先を変える可能性がある」プロジェクトほど、OTLP 直送だけで機能が完結する送り先(Cloud Trace・Honeycomb)を優先する。Datadog を選ぶ場合は Agent/Collector 前提の機能差を採用前に確認する。Grafana Cloud を選ぶ場合はクエリ層(TraceQL)の移行コストを織り込む。これが「OTel を入れてもクラウド選定を強制しない」(1・2 節)の実質であり、API/SDK を常時配線する判断の根拠でもある。

### 3.4 ログとの相関: trace_id で行き来できるか

送り先によってはログとトレースが別サービスになり、相関の手間が変わる。

| 送り先                        | ログ側                        | 相関の仕組み                                                                           | 自動か手動か                                                                         |
| ----------------------------- | ----------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| **Cloud Trace**               | Cloud Logging                 | LogEntry の `trace` / `spanId` / `traceSampled` フィールドで相関                       | 手動寄り(構造化ログクライアントの一部ケースを除き、アプリ側でのフィールド設定が要る) |
| **Honeycomb**                 | 同一データセット(wide events) | ログも span 属性・span event として同じデータセットに取り込む設計                      | 自動。ただし全システムを同一データセットに載せる前提が要る                           |
| **Datadog**                   | Log Management                | trace_id/span_id をログ属性に含めれば相関。**OTLP 経由(Agent 不要)でも動作する**と明記 | 半自動(フォーマット要件はあるが Agent は必須ではない)                                |
| **Grafana Cloud(Tempo)**      | Loki                          | Tempo データソースの trace-to-logs 設定 / Loki 側の derived fields                     | 手動設定。**同一 Grafana Cloud スタックである必要はなく**、self-hosted Loki でも動く |
| **OTLP + Jaeger(自己ホスト)** | 自分で選ぶ                    | 自分で trace_id をログ基盤(Loki/ELK 等)に載せる配線を作る                              | 完全手動                                                                             |

**いつ効くか**: 障害調査でログとトレースを往復する頻度が高いプロジェクトほど、同一 UI 内で trace_id からジャンプできることの価値が上がる。Honeycomb は設計上ログとトレースを区別しないため相関コストが最も低いが、全シグナルを 1 つのデータセットに集約する制約を受け入れる必要がある。

## 4. ローカル開発: Jaeger

`docker.io/jaegertracing/all-in-one` イメージを使うと、外部のトレースバックエンドに接続せずローカルでトレースの実装を検証できる。

- このイメージを **sha256 ダイジェストで固定**して使用する(原則 10「依存は完全固定する」のコンテナイメージへの適用そのもの。タグではなくダイジェストを使うのは、`latest` や可変タグが指す内容が後から変わり得るため)
- **testcontainer として**(テストのセットアップ時にだけ Docker コンテナとして起動し、テスト終了時に破棄する仕組み)使う形は、テンプレート本体には配線しない(下記「まとめ」)。トレースの実装を持つ段階になった時点で、このパターンごと導入する
- **手動でトレースを目視するだけ**なら、testcontainer ではなく `mise run trace:local` で同じイメージ(sha256 固定済み)を起動できる。UI は `http://localhost:16686`、OTLP は既定で有効(gRPC 4317 / HTTP 4318)。実行確認済み(2026-08-09)。exporter の差し替え(既定の `ConsoleSpanExporter` → OTLP)は含まない — 差し替え方は「6. 実体層の配線」参照

## 6. 実体層の配線（2026-08-09 追加）

原則12がログの横断境界として既に持っていた canonical observer（`apps/api/src/logging/observe.ts` の `observeResult`）に、そのままトレースを統合した。新しい並行系統は作らない（`withBoundarySpan` パターンと同じ構図）。

| 対象                                                            | 置き場所                                                  | 役割                                                                                                                                                  |
| --------------------------------------------------------------- | --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NodeSDK` の起動 + 既定 exporter（`ConsoleSpanExporter`）の選択 | `apps/api/src/composition.ts`（合成ルート）               | exporter を選ぶ唯一の場所。実際の送り先（Cloud Trace / OTLP 等）へ差し替えるときはここだけを変更する                                                  |
| span を開く/閉じる・trace_id/span_id をログへ載せる             | `apps/api/src/logging/observe.ts`                         | `observeResult` が `tracer.startActiveSpan` で span を開始し、成功・失敗どちらでも `span.end()` を呼んでから canonical log line を書く                |
| span 属性の禁止キー検査                                         | 同上（`redact.ts` の `assertNoForbiddenFields` を再利用） | ログの属性とまったく同じ禁止語彙をトレースにも適用する。ログだけ守ってトレースから秘密が漏れるのでは意味がない                                        |
| W3C trace context の検証つき抽出                                | `apps/api/src/logging/trace-context.ts`                   | `traceparent` / `tracestate` / `baggage` を正規表現・文字コード検査で検証してから運ぶ。carrier が無いこと（新規リクエスト）と壊れていることを区別する |

**exporter の差し替え方**: `apps/api/src/composition.ts` の `spanProcessors` に渡す exporter を差し替える。例えば OTLP + Jaeger へ切り替えるなら、`@opentelemetry/exporter-trace-otlp-http` を追加インストールし、`new SimpleSpanProcessor(new ConsoleSpanExporter())` を `new BatchSpanProcessor(new OTLPTraceExporter({ url: "..." }))` に置き換える。この 1 ファイルの外に OpenTelemetry SDK / exporter の import が漏れていないことは architecture checker が強制する（下記）。ローカルで Jaeger 自体を立てるだけなら `mise run trace:local`(「4. ローカル開発」参照)で足り、この差し替えとは独立に実行できる。

**architecture checker のルール（新しいルールファイルは追加していない）**: 既存の汎用ルール 2 つに実際のパッケージ名を設定として渡すだけで、原則12の境界を機械強制できた（原則8「検査ロジックの二重管理を禁止」）。

| ルール                                                                                 | 使う既存ルール                     |
| -------------------------------------------------------------------------------------- | ---------------------------------- |
| `@opentelemetry/sdk-node` / `@opentelemetry/sdk-trace-base` の import は合成ルートのみ | `third-party-sdk-composition-root` |
| `@opentelemetry/api` の import は `logging/` 境界からのみ                              | `logging-implementation-location`  |

**`@opentelemetry/api` を業務コードへ解放しない理由**: API 自体はどこから呼んでも安全（ベンダー中立の契約）だが、呼び出し箇所を観測境界に絞ることで「span を開く/閉じる場所」が canonical observer 1 箇所であり続けることを構造的に保証できる。業務コードに解放すると、業務コードが独自に span を開始する経路が生まれ、「1 リクエスト = 1 ワイドイベントと同じ境界で span を張る」という前提が崩れる（trace 相関目的の呼び出しを logging 境界に絞る設計と同じ判断）。

**`third-party-sdk-composition-root` の判定はファイル名（既定 `composition.ts`）のみで行う**（2026-08-09 に「application レイヤ配下」要件を撤廃）。この最小の縦切りの合成ルートは DDD レイヤの外側で全レイヤを束ねる 1 ファイルであり、"application" セグメントの祖先を持たないため、旧要件のままでは合成ルート自身が誤検知されていた（実測）。

## 7. 監査ペイロードの分離

本文(リクエスト・レスポンスの生データ、生成された文章など)を丸ごとログやトレースの属性に載せると、原則の要件 5(秘密や本文をログの属性として存在させない)に反する。これを次の形で解く。

- 本文そのものはオブジェクトストア(クラウドのオブジェクトストレージ)に書き込む
- ログ・トレースの属性には、本文の**ハッシュ値または参照キー**だけを載せる
- 調査時は、ログから拾った参照キーでオブジェクトストアを引き、本文を後から取得する

**インターフェース(「本文は属性に直接載せず、参照キーだけを載せる」という形)は今すぐ設計できる。** 具体的な保存先(どのオブジェクトストレージを使うか)はクラウド選定に従属するため、送り先と同じく空スロットとして扱う。

## まとめ: このレシピの採否（2026-08-09 改訂）

契約層(§3)と同じ構造を観測性にも適用する。**ただし空スロットにする範囲は当初の想定より狭い。** OpenTelemetry は API と SDK が分離されているため（1 節・2 節）、SDK を入れてもクラウド選定を強制しない。空スロットにすべきなのは **exporter（送り先）だけ**であり、API/SDK 自体は常時ロードして配線する。テンプレート本体に今すぐ配線するのは次の 3 つである。

1. **ログの形の規約**(原則 1〜8 が要件として定める、記録の形・文言と属性の関係・失敗理由の語彙・重大度の導出根拠)
2. **OpenTelemetry API/SDK + 既定 exporter**(§6「実体層の配線」。合成ルートが唯一の配線場所であり、既定は開発向けの `ConsoleSpanExporter`)
3. **機械強制**(型による分離・import 境界の検査・禁止キーの検査・呼び出し口の一元化・トレース相関の検査。具体的な検査対象は architecture checker と policy-as-test に置く)

**送り先(3 節)と testcontainer 統合(4 節)だけが空スロットのままである。** `mise run trace:local` によるトレースの目視自体は配線済みだが、これは Jaeger を起動するだけであり、exporter を Jaeger 向けに差し替える配線(6 節)とテストへの testcontainer 統合は含まない。選定はプロジェクト開始時の ADR に委ねる。構造化ログのライブラリ(1 節)・エラー追跡 SaaS(5 節)・監査ペイロードの保存先(7 節)も同様に空スロットであり、テンプレート本体が特定の実体を選ばなくても規約自体は成立する。プロジェクト開始時に実体を選んだら、この表の「採否」欄をプロジェクト側の ADR で上書きすること。
