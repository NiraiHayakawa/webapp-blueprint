# レシピ: フロントエンドを書く場合のツールカタログ

原則: [`docs/principles/enforce-with-machines.md`](../../principles/enforce-with-machines.md)（規約は機械で縛る）

TypeScript 横断のツール(パッケージマネージャ・lint・テストランナー等)は [`docs/recipes/tools/typescript.md`](typescript.md) を参照。このファイルはフロントエンド固有の選定だけを扱う。

design doc 冒頭「非対象」節の通り、**UI コンポーネントライブラリの選定は本テンプレートの非対象**である。ここに書くのは「何を検討したか」のカタログであり、フレームワーク自体は各プロジェクトが `docs/adr/` で選ぶ。

フロントエンドの選定カタログであり、UI フレームワークから状態管理、スタイリング、アニメーション、テストモック等の選択肢と知見をまとめる。

## フレームワーク / ルーティング

**SSR が要るかどうかが最初の分岐点である。** SSR 不要なら SPA(Vite + React 系)、SSR/SSG が要るならメタフレームワーク(Next.js 等)という単純な二分になる。

| ツール                                  | 何をするか                                                                                                       | いつ要るか                                                                                     | テンプレの採否                                                                                                                                                         |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| React                                   | UI ライブラリ                                                                                                    | 常時(既定候補)                                                                                 | **条件付き採用の既定候補**。テンプレート本体は選定を空スロットにするが、他フレームワーク(Vue/Svelte/Solid)を積極的に検討する理由が無い限りの既定値として記録する       |
| Vue / Svelte / Solid                    | React 以外の UI ライブラリ                                                                                       | React 以外のエコシステム(既存チームの知見・特定ライブラリの対応状況)に理由があるとき           | **未採用**。connect-query が React 専用であることも React 以外を選びにくくする要因                                                                                     |
| **TanStack Router**(file-based routing) | 型安全な search params・loader を持つルーター。URL → 検証済み state → loader データ → UI という state-first 設計 | SPA で型安全性を重視するとき(常時、既定候補)                                                   | **条件付き採用の既定候補**。connect-query が React 専用な上に TanStack Query との親和性が高いため、契約層に protobuf + ConnectRPC を選んだ場合は自然な組み合わせになる |
| React Router                            | UI ファーストのルーター(URL → コンポーネント、データ取得は後付け)。Remix を統合した v7 以降は SSR モードも持つ   | 既存の React Router 資産がある、またはアプリが小さく安定していて型安全性の投資が見合わないとき | **未採用**。TanStack Router の方が compile-time の型検証(path params・search params・loader データ)が強い                                                              |
| Next.js 等のメタフレームワーク          | SSR/SSG・ファイルベースルーティング・API Routes 等を統合するフレームワーク                                       | SSR/SSG が要るとき、または BFF 層を同じリポジトリに同居させたいとき                            | **条件付き採用**。SSR の要否で判断する                                                                                                                                 |

## グローバル状態

**まず入れない、が既定の立場である。** サーバー状態はサーバー状態管理ライブラリに任せ、クライアントローカルな UI 状態は React 標準の state/context で足りることが多い。

| ツール                | 何をするか                                                             | いつ要るか                                                                                                                                                        | テンプレの採否                                                                                                                                                                                                                                                                                                                                                |
| --------------------- | ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| zustand               | 最小限の API を持つ、Redux より軽量なグローバル状態管理                | props drilling が深くなり、かつサーバー状態ではない**クライアントローカルな**状態(例: ストリーミング進行中の一時状態)を複数コンポーネントで共有する必要が出たとき | **未採用(必要になったら ADR で追加)**。「グローバル状態ライブラリ(zustand 等)は入れない。ストリーム進行状態は feature に閉じる。必要になったら ADR で追加」という方針があり、テンプレートの既定には含めない。**判定基準**: 状態がある 1 つの feature に閉じるなら feature-local state で足りる。複数 feature をまたいで同期が必要になった時点で初めて検討する |
| jotai                 | atomic な単位で状態を持つ、ボトムアップ設計の状態管理                  | zustand のストア単位より細かい粒度で、コンポーネント単位の購読最適化をしたいとき                                                                                  | **未採用**                                                                                                                                                                                                                                                                                                                                                    |
| Redux (Redux Toolkit) | 単一ストア・reducer パターンの状態管理。DevTools・時系列デバッグに強み | 大規模なチームで状態変更の追跡可能性(action ログ)を重視するとき                                                                                                   | **未採用**。`docs/principles`(手組み DI・薄いレイヤ優先の思想)とも噛み合わない大きめのボイラープレートを持つ                                                                                                                                                                                                                                                  |

## スタイリング / デザインシステム

**トークン経由・one-off 禁止という規律は、どのシステムを選んでも効く。** これは特定のライブラリの機能ではなく運用規律であり、Tailwind でも astryx でも CSS Modules でも同じ形で強制できる: 色・間隔・角丸を CSS 変数(デザイントークン)で参照し、コンポーネントへの raw hex/px の直書きや `:root` の個別上書きを禁止する。

| ツール                                             | 何をするか                                                                                                                                                            | いつ要るか                                                                                                        | テンプレの採否                                                                                                  |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Tailwind CSS                                       | ユーティリティクラスベースの CSS フレームワーク                                                                                                                       | 既存のデザインシステムが無く、ユーティリティクラスの組み合わせで素早く UI を組みたいとき                          | **未採用**。消費側にコンパイラが不要という astryx の利点を考慮                                                  |
| CSS Modules                                        | コンポーネントスコープの CSS をビルド時にハッシュ化するネイティブ機構                                                                                                 | 追加ライブラリを増やしたくない最小構成のとき                                                                      | **未採用**                                                                                                      |
| vanilla-extract                                    | TypeScript で書く、ゼロランタイムの CSS-in-JS                                                                                                                         | 型安全なテーマ定義とゼロランタイムを両立したいとき                                                                | **未採用**                                                                                                      |
| **astryx**(`@astryxdesign/core` + `theme-neutral`) | Meta OSS のデザインシステム。CSS 変数(`--color-*`/`--spacing-*`/`--radius-*`)でトークンを参照し、CLI(`astryx build`/`template`/`component`)でコンポーネントを生成する | UI を「使い捨てだが構造は本採用」として扱いたいとき(mock UI 方針)、または消費側にコンパイラを持ち込みたくないとき | **条件付き採用**。詳細は下記「astryx を詳しく見る」                                                             |
| shadcn/ui                                          | コンポーネントの**ソースをコピーして**手元に配置する形式のコンポーネント集(npm パッケージとして実行時に依存しない配布モデル)                                          | Tailwind ベースでカスタマイズ前提の UI を素早く組みたいとき                                                       | **未採用**(テンプレートの既定としては)。**astryx が立ち行かなくなった場合の明示的な退避先**として記録されている |

### astryx を詳しく見る

astryx は v0.1(2026-06-24 公開)と非常に若い OSS であり、採用と同時にリスクの引受け方を明記している。**「トークン経由・one-off 禁止」の規律をシステムを問わず適用する**という本カタログの立場を、astryx の実例で具体化すると:

- **`<div>` 禁止**: レイアウトはコンポーネントが担う(astryx 自身の規約)
- **フレーム先行**: AppShell / Layout から書き始める
- **discover-don't-guess**: `astryx build` → `template` → `component` の順で調べてから書く。既存コンポーネントを推測で作らない
- **全スタイリングをトークン経由に**: raw hex/px 禁止、`--color-*` の `:root` 上書き禁止、テーマ変更は `astryx theme` 経由。component への one-off スタイル直書きも禁止
- **ライト・ダーク両対応はトークン層で最初から**: 後付けはテーマ層を経由しない直書きより高くつく

**リスクの引受け**: (a) 破壊的変更は `astryx upgrade --apply` の追従を前提にする、(b) コンポーネント不足は `astryx swizzle`(ソース eject)で埋める、(c) 立ち行かなくなった場合の退避先は shadcn/ui + Tailwind(トークン経由・one-off 禁止の規律は退避後も同一)。CLI が生成するファイルは ASTRYX マーカーで管理され、規約に従って手編集しない。

## テストのモック

**契約層の選択でどちらが正解か変わる**(design doc §4「外部境界の扱い」)。ここでの選択はフロントエンドだけで閉じず、契約層のレシピと対になっている。

| ツール                                  | 何をするか                                                                                       | いつ要るか                                                                                                             | テンプレの採否                                                                                                                                                                                                                                              |
| --------------------------------------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `connect-es` の公式インメモリ transport | protobuf 契約から生成された型をそのまま使い、ネットワークを経由せずにクライアント/サーバーを繋ぐ | 契約層に protobuf + ConnectRPC を選んだとき                                                                            | 契約層レシピ [`docs/recipes/contract-layer/protobuf-connectrpc.md`](../contract-layer/protobuf-connectrpc.md) の「テストでの外部境界の扱い」に**採用済み**として詳述。契約から型が生成されるためモック drift が構造的に起きない、という理由も同所に記載済み |
| **MSW**(Mock Service Worker)            | Service Worker/interceptor レベルで HTTP リクエストを横取りしてモックする                        | 契約層に TypeSpec → OpenAPI を選んだとき(HTTP という契約を持たない境界の上でリクエスト/レスポンスを模倣する必要がある) | 契約層レシピ [`docs/recipes/contract-layer/typespec-openapi.md`](../contract-layer/typespec-openapi.md) に**採用済み**として詳述。**ここでは重複させない**                                                                                                  |
| 手書きフェイク                          | インターフェースを満たすだけのリテラルオブジェクトを手で書く                                     | 外部境界がまだ小さく(ハンドラ 1 つ等)、モックライブラリを導入するコストが見合わないとき                                | **採用(最小の縦切り限定)**。§9 の「最小の縦切り」は契約層を選ぶ前の段階であり、モックライブラリを固定しない手書きフェイクが最も選択を先送りできる。契約層を選んだ時点で上記 2 つのいずれかに置き換わる                                                      |
