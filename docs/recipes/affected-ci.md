# レシピ: CI が 10 分を超えたときの差分実行への移行

原則: [`docs/principles/one-command-verification.md`](../principles/one-command-verification.md)(検証は1コマンド)

実体層には配線しない。`docs/plan/Template/20260807_template-design.md` §5「CI の実行範囲」が定める見直しトリガー(**CI 所要 10 分超え**)に達した時点で、このレシピを見て移行する。

## 前提: なぜ最初から入れないか

CI は全実行が既定である(`.github/workflows/ci.yml` の `checks` job は `mise.toml` の `[tasks.check].depends` を matrix にそのまま列挙し、差分検出を行わない)。理由は差分検出のバグが検査漏れに直結するためで、速いうちからこのリスクを背負わない。全実行が遅くなって初めて、差分実行のコストを払う判断をする。

## 移行先: resolve-affected-apps パターン

`scripts/ci/resolve-affected-apps.mjs` のように影響アプリを算出し、matrix に渡す方式を採用する。移行するときはこの形を土台にする。

要点:

1. 変更されたファイルの差分から、影響を受けるワークスペースパッケージを算出するスクリプトを 1 本持つ(`pnpm-workspace.yaml` の依存グラフを解析する)
2. **マージコミットの第 1 親を基点にする**。PR の diff base を単純に「直前の commit」にすると、複数コミットを含む PR や、force-push を経た PR で正しい差分が取れない。この実測を踏まえ、マージコミットの第 1 親を基点に取ることで安定させる
3. 算出結果を CI の matrix に渡す。matrix の生成ロジックは 1 つのスクリプトに閉じ、workflow YAML 側には算出結果を受け取って matrix に展開する配線だけを書く(検証ロジックの二重管理を避ける。原則8)
4. `mise.toml` 側のタスク定義は変えない。「どのパッケージに対して実行するか」が変わるだけで、「何を検証するか」は変えない

## 機械強制

差分実行への移行は、検査対象が意図せず 0 件になるリスクを新たに持ち込む(受入条件1「対象ゼロの緑は不合格」と同じ考え方がここにも当てはまる)。移行時に:

- 影響算出スクリプト自身に、意図的に影響ゼロになるケースと影響ありのケースの両方を確認する fixture テストを持たせる
- 「全パッケージに影響する変更」(ルートの `package.json` やワークスペース共通設定の変更など)を検出したら、差分算出を通さず全実行にフォールバックする経路を明示的に持つ。これはフォールバックではあるが「失敗を隠す」フォールバック(原則2 が禁止する対象)ではなく、「差分算出が信頼できない状況を検知して、より安全な全実行に倒す」という意図的な安全側の切替であるため、原則2の禁止対象とは区別される。ただしこの切替が発生したこと自体はログに残し、握り込まない

## 落とし穴

- 第 1 親の取り方を間違えると、squash merge を使っているリポジトリでは「マージコミット」自体が存在せず、この手法がそのままでは使えない。採用前に自分たちのマージ戦略(merge commit / squash / rebase)を確認すること
