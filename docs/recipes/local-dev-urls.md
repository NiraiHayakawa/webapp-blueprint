# レシピ: portless によるローカル開発 URL の統一

本テンプレートは**今すぐ導入しない**（下記「導入しない理由」）ため、原則層ではなくレシピ層に置く。

実体層には配線しない（clone 直後は動かない）。「いつ導入すべきか」に挙げた条件に達した時点でこのレシピを見て導入する。

## 何を解くツールか

`portless` はローカル開発のポート番号を廃し、安定した名前付き `.localhost` URL に統一するリバースプロキシである。素の状態では、ローカルで複数サービス（フロントの dev server・バックエンド・エミュレータ等）を同時に立てると次の問題が起きる:

- どのサービスがどのポートかを覚えていないと動かせない（`localhost:3001` と `localhost:8080` の対応を人間が記憶する）
- ポート競合（`EADDRINUSE`）が、無関係なプロジェクトを同時に開いているだけで発生する
- ブラウザのタブを再読み込みすると、別のサービスに切り替わった同じポートの内容が表示される
- CORS allowlist・OAuth redirect・`.env` のような設定にポート番号を書き込むと、ポートが変わるたびに壊れる
- cookie が `localhost` 全体で共有され、サービスをまたいで衝突する

`portless <name> <cmd>` がサービスごとに非公開ポートを自動割当てし、`https://<name>.localhost`（または固定ポートを使う運用では `http://<name>.localhost:<port>`）という安定した名前付き URL の後ろに隠す。

## 設計パターン

`portless` を導入する際は次の 3 点のプラクティスが有効である。

| プラクティス / 観点                                             | 実装・運用の指針                                                                                                                     | 具体的な構成例                                                                                                                     |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| **非特権ポートに固定し、sudo / trust store 変更を前提にしない** | proxy port を `1355` や `1356` などの非特権 high port に固定。443 bind に必要な sudo 昇格や trust store 変更を開発開始時に要求しない | 非特権の high port・loopback bind・TLS なしを明示し、port 80/443・sudo・trust store 変更を local 起動の前提にしない                |
| **複数サービスに名前付き URL を与える**                         | Vite dev server、API サーバー、各種エミュレータなどの HTTP プロセスに安定した `.localhost` name を与える                             | `web.localhost:1355`、`api.localhost:1355`、`emulator.localhost:1355` 等の各コンポーネントを独立 URL 化                            |
| **CI / テスト正しさの依存にしない**                             | E2E や統合テストは直接 loopback port / Testcontainers 等に接続し、portless はローカル開発体験専用に留める                            | 統合テストは CI で portless を必須とせず、architecture checker 等で統合テストハーネスからの `import "portless"` を機械的に禁止する |

3 番目の点が特に重要である。**portless は人間と coding agent のローカル開発体験を安定させるためのものであり、CI やテストの正しさが依存する対象にしてはならない**、という境界を機械強制することが推奨される。

## 導入しない理由（今のテンプレートの状態）

契約層が空スロットで（`contract/` は ADR 0001 待ち）、backend の実体も §9「最小の縦切り」が意図的に配線を避けている（フロントとバックエンドを契約層の境界を越えて繋がない）。**ローカルで複数サービスを同時に立てる構成がまだ存在しない**ため、今 portless を導入しても解く問題がない。

## いつ導入すべきか

次のいずれかに達した時点でこのレシピに戻る:

1. **ローカルで複数サービスを同時に立てる構成になった時点**（契約層を選定し、フロントとバックエンドを実際に繋いだとき。エミュレータを追加したときも同様）
2. **cookie の `Secure` 属性をローカルで検証したくなった時点**（`Secure` cookie は HTTPS でしか送られないため、`http://localhost:<port>` では検証できない。portless の HTTPS リバースプロキシはこれを素の `localhost` の外側で解決する）

## 導入するときの選択肢

採用するときは次を最初に決める:

- **proxy port を非特権ポートに固定する**（`1355` や `1356` のような 1024 以上のポート）。既定の 443/80 のまま導入すると、開発開始のたびに sudo 昇格を要求することになる
- **CI では使わない。** CI は各サービスに直接 loopback port で接続し、portless は開発ループ専用に留める。この境界を機械強制したい場合、例えば architecture checker で「特定のディレクトリ（統合テストハーネスや CI 専用コード）から `portless` を import したら落とす」ルールを tools/architecture 側に足す
- **実行の入口を mise task に閉じる**（package.json scripts や生の `portless` CLI 直叩きに分散させない）。原則8「検証は1コマンド」・原則4「規約は機械で縛る」と同じ発想を、開発体験のツールにも適用する

具体的な固定 port 番号・named URL の割当ては、導入するプロジェクトの構成（サービス数・使うエミュレータ）に依存するため、ここでは値を決め打ちしない。
